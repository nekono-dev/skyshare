# クリエイターモード 要件定義書

## 1. 背景・目的

現在の投稿フォーム（`src/components/post/PostForm`）は、Blueskyへのテキスト・画像・OGPリンク投稿という基本機能に特化している。一方で、より作り込んだ投稿（装飾文字・複数リンク・スレッド形式の連投など）を行いたいユーザー向けに、リッチな編集機能を備えた「クリエイターモード」を新設する。

クリエイターモードは既存の投稿フォームを置き換えるものではなく、**既存PostFormと同じ基本機能（本文入力・画像添付・OGP・返信/引用設定・自己ラベル・言語選択・下書き等）をすべて継承した上で**、追加の高度な編集機能を利用できるフォームとして提供する。

さらに、追加機能自体は将来的に通常のPostFormへ「逆輸入」（機能を段階的に取り込むこと）できるよう、クリエイターモード専用フォームに直接結合せず、**独立した機能コンポーネント＋関連関数のセット**として実装する。

**前提: 本要件はEditorToolbox（[`specs/editor-toolbox`](../editor-toolbox/requirements.md)）が実装済みであることを前提とする。** 各機能（FR1〜FR4）の入り口となる「ボタン列＋クリックで展開するパネル」の共通UI基盤（EditorToolbox）は、クリエイターモード固有の知識を持たない独立した共通コンポーネントとして別途仕様化・実装するため、本書では以後「EditorToolboxが提供するツール登録の仕組みを利用する」という前提でFR1〜FR4を記述する。EditorToolbox自体の要件・設計・タスクは `specs/editor-toolbox/` を参照すること。

## 2. 用語定義

| 用語               | 意味                                                                                                            |
| ------------------ | --------------------------------------------------------------------------------------------------------------- |
| PostForm           | 既存の投稿フォーム本体（`src/components/post/PostForm`）。                                                      |
| クリエイターモード | 本要件で新設する、PostFormの機能を継承しつつ追加編集機能を持つ投稿UI一式。                                      |

| facet              | `app.bsky.richtext.facet`。投稿本文中の特定バイト範囲に対する注釈（リンク・メンション・ハッシュタグ）。         |
| record             | `app.bsky.feed.post` のレコード本体（Bluesky投稿そのもの）。                                                    |
| 逆輸入             | クリエイターモード用に独立実装した機能コンポーネントを、後日通常のPostFormへ組み込むこと。                      |
| セグメント         | スレッド投稿における個々の投稿単位（1スレッド内の1投稿）。                                                      |

## 3. スコープ

### 3.1 対象

要件定義書・設計書・タスク一覧は、以下の機能について **フロントエンド・バックエンド（skyshareサーバサイド）双方の変更を対象スコープに含める**。

1. テキスト範囲選択によるURLリンク設定機能
2. recordへの任意カスタムパラメータ付与機能
3. YayText変換（Unicode装飾文字への変換）機能
4. skyshare entryのheading/caption/cover画像の任意設定機能
5. スレッド投稿機能

### 3.2 対象外

- **EditorToolbox共通コンポーネント自体の要件・設計・実装。** これは [`specs/editor-toolbox`](../editor-toolbox/requirements.md) に独立した仕様として切り出しており、本書はその成果物（実装済みであること）を前提として利用する側の要件のみを扱う。
- 既存PostForm自体の挙動変更（クリエイターモード側の機能コンポーネントを使って将来的に逆輸入する作業自体は別途スコープとし、本タスク一覧には「逆輸入可能な形で作る」ところまでを含め、実際にPostFormへ組み込む作業は含めない）。
- Bluesky公式クライアント・他社クライアントとの相互運用性検証（本機能で付与したカスタムパラメータ・装飾文字が他クライアントでどう見えるかの検証は行うが、対応改修は行わない）。
- クロスポスト先（Taittsuu/Mastodon/X）側でのリッチテキスト・スレッド表現の高度化（既存のインテント連携の範囲を超えない）。

## 4. 前提条件・現状整理

- 本アプリはCloudflare Workers上で動作するため、Node.js固有APIは使用不可。
- APIはコードファースト（`src/lib/api/schema/**` のZodスキーマが単一の真実の源）。
- facetsの組み立て（URL/メンション/ハッシュタグ検出）はすでにクライアント側の責務に分離済み（`src/lib/atproto/richtext.ts` の `detectFacetsForSubmission`）。バックエンド（`validateFacets`）は本文バイト長に収まっているかの境界防御のみ行う。この分離により、機能1（手動リンクfacet編集）はバックエンド変更なしで実現可能な状態が整っている。
- `via: "Skyshare"` はBluesky公式lexicon（`app.bsky.feed.post`）には存在しないフィールドだが、PDSのレコード検証は未定義プロパティを許容するため実際に投稿できている。この事実は機能2（カスタムパラメータ）の実現可能性の技術的根拠となる。
- skyshare entryのheading/captionは現在 `createSkyshareEntry`（`src/lib/entry/skyshareRecord.ts`）内でサーバ側が `"${userName} 's Post"` / 投稿本文 に自動生成しており、クライアントから指定する手段がない（`PUT /v2/entry` は投稿後の事後編集のみ対応）。
- cover画像（`manifest.visual`）は現在、`ImagePicker` が生成する `thumbnailBlob`（投稿画像から自動クロップ）を流用しており、投稿画像と独立に指定する手段がない。
- Bluesky投稿のreply（スレッド化、`app.bsky.feed.post#replyRef`）は、skyshareのAPI（`POST /v2/entry`、`POST /v2/bsky/record`）・`createBskyPost` のいずれにも実装されていない。機能5（スレッド投稿）には新規のバックエンド対応が必須。

## 6. 機能要件

以下FR1〜FR4は、いずれも `EditorToolbox`（[`specs/editor-toolbox`](../editor-toolbox/requirements.md)）へ1つの「ツール」として登録される形で提供する。EditorToolbox自体の挙動（ボタン列表示・パネル開閉制御・アクセシビリティ等）は同仕様書を参照し、本書では繰り返さない。

### FR1. テキスト範囲選択によるURLリンク設定機能

**概要**: 本文中の任意のテキスト範囲を選択し、その範囲に対して手動でURLを設定できる。設定した範囲は投稿時に `app.bsky.richtext.facet#link` として送信される。

**詳細要求**:

- 本文欄（contentEditableベース）でテキストを範囲選択した状態でEditorToolbox上の「リンク」ツール（パネル型）を押すと、URL入力パネルが展開する。
- パネルでURLを確定すると選択範囲に対して手動リンクfacetが1件登録される。
- 登録済みの手動リンクfacetは本文中で視覚的に区別できる（下線・色付け等、既存の `facetHighlightSegments` の仕組みを拡張）。
- 登録済みのリンクを編集・解除できる（再度選択してURLを変更、または削除ボタン）。
- 本文編集（前後への文字挿入・削除）が行われた場合、既存の手動リンクfacetの範囲は編集内容に追従して自動調整される。facetの範囲そのものが編集（一部でも削除）された場合は当該facetを失効させる。
- 投稿時、手動リンクfacetと自動検出facet（`detectFacetsForSubmission` によるURL/メンション/ハッシュタグ検出）をマージする。範囲が重複する場合は手動リンクfacetを優先する。
- バックエンド（`validateFacets` によるバイト範囲の境界防御）は変更不要（既存の防御ロジックがそのまま機能する）。

**受け入れ条件**:

- 任意のテキスト範囲（URLに見えない文字列も含む）にリンクを設定し、投稿後、Bluesky上でリンクとして機能する。
- 本文編集後も、編集箇所と無関係な既存リンクの位置がずれない。
- 編集によって破壊された範囲のリンクは投稿時に含まれない。

### FR2. recordへの任意カスタムパラメータ付与機能

**概要**: 投稿本文とは別に、キー・バリューのペアを任意の数だけ追加入力できるUIを設け、投稿するBluesky recordの直下に付与する。

**詳細要求**:

- EditorToolbox上の「カスタムパラメータ」ツール（パネル型）を押すとパネルが展開し、その中で「+」ボタンでキー・バリュー入力行を追加、「−」ボタン（または各行の削除ボタン）で行を削除できる。
- キーはドット区切り（例: `promo.code`）を許容し、投稿時にネストしたオブジェクトへ変換する。
- 生成される最終的なJSON構造は record 直下にマージされる（例: キー `campaign`＝値`summer2026`、キー `promo.code`＝値`XYZ` → `{ ..., campaign: "summer2026", promo: { code: "XYZ" } }`）。
- 以下のキーは予約済み（lexicon既定フィールド、または既存サーバ実装が使用中のフィールド）として使用を禁止し、入力時にエラー表示する: `text`, `facets`, `reply`, `embed`, `langs`, `labels`, `tags`, `createdAt`, `via`, `$type`。
- キー名の各セグメントに `__proto__` / `constructor` / `prototype` を許可しない（プロトタイプ汚染対策）。
- 空のキー、重複するキー（同一ネスト構造での衝突）はエラー表示し送信をブロックする。
- 本機能はバックエンドが現状 `text/facets/langs/selfLabels/gate/images/...` 以外の任意フィールドを受理していないため、`POST /v2/entry` 及び `POST /v2/bsky/record` のリクエストスキーマ・ハンドラ改修が必要。

**受け入れ条件**:

- 追加したキー・バリューが、実際に作成されたBluesky投稿recordに反映される（`com.atproto.repo.getRecord` 等で確認可能）。
- 予約キー・不正キーを入力した場合、投稿ボタン押下前にエラーが表示され送信されない。

### FR3. YayText変換機能

**概要**: 選択した英字テキスト範囲を、Unicodeの装飾文字（太字・イタリック・太字イタリック・サンセリフ太字・筆記体・等幅・二重線）に変換するボタンを提供する。

**詳細要求**:

- 本文中でテキスト範囲を選択した状態でEditorToolbox上の「装飾」ツール（パネル型）を押すと、7種のスタイル（Bold / Italic / Bold Italic / Sans-serif Bold / Script（筆記体） / Monospace（等幅） / Double-struck（二重線））に対応するボタンを含むパネルが展開する。
- スタイルボタン押下で、選択範囲の文字列をUnicode対応文字へ置換した文字列に差し替える（不可逆な文字置換。Blueskyの太字/イタリック用暫定Markdown記法とは異なる、恒久的な文字コード置換として実装する）。
- 変換対応する文字種は基本ラテンアルファベット（A-Z, a-z）及び数字（0-9）を基本とする。対応するUnicodeコードポイントが存在しない文字（記号・非ASCII文字等）はそのまま変換せず残す。
- 変換によって選択範囲の前後にある既存facet（リンク等）の位置が本文全体のバイト長変化に応じてずれるため、変換確定時に影響を受けるfacetのbyteStart/byteEndを自動再計算する（FR1と共通のfacet位置調整ロジックを利用する）。
- 既に装飾済みの文字列を選択して別スタイルへ再変換すること（上書き）も許容する（変換前の装飾文字も対象コードポイントの逆引きテーブルで通常文字へ正規化してから変換する、または単純に非対応として残る点は許容する。詳細は設計書で判断）。

**受け入れ条件**:

- 選択範囲が装飾文字に置き換わり、文字数カウント（`countGraphemes`/`countWeightedTweetLength`）にも反映される。
- 変換後、既存のリンクfacetが指す文字範囲がずれずに正しく機能する。

### FR4. skyshare entryのheading/caption/cover画像 任意設定機能

**概要**: 画像投稿時に自動生成されているheading・caption・cover画像（`manifest.visual`）を、ユーザーが自由に指定できるようにする。

**詳細要求**:

- 画像投稿時、EditorToolbox上の「entry詳細設定」ツール（パネル型）を押すとパネルが展開し、以下を編集可能にする（画像投稿でない場合はツールを無効化する）。
  - heading（最大100文字、未入力時は現行同様の自動生成 `"${表示名} 's Post"` にフォールバック）
  - caption（最大300文字、未入力時は現行同様、投稿本文にフォールバック）
  - cover画像（投稿画像とは独立の画像を選択・クロップして指定可能。未指定時は現行同様、投稿画像から自動生成したサムネイルを使用）
- 本機能は画像投稿（skyshare entryを作成する投稿）にのみ適用する。OGPリンク投稿・テキストのみ投稿では対象外（entry自体を作成しないため）。
- バックエンド（`POST /v2/entry`）に `manifestHeading` / `manifestCaption` の任意フィールドを追加し、`createSkyshareEntry` へ受け渡して既定値を上書きできるようにする。
- cover画像自体は既存の `ogImage` フィールド（すでに `images` とは独立したフィールド）をそのまま利用できるため、バックエンドのスキーマ変更は不要。フロントエンドで「投稿画像から自動生成」以外に「別画像をアップロード」を選べるUIを追加する。

**受け入れ条件**:

- heading/captionを入力して投稿すると、作成されたskyshare entryにその内容が反映される。
- 未入力の場合は現行の自動生成ロジックと同じ結果になる（後方互換）。
- 投稿画像とは別の画像をcoverとして指定した場合、entry一覧・詳細でその画像が表示される。

### FR5. スレッド投稿機能

**概要**: Blueskyのスレッド（reply chain）形式で、複数の投稿をあらかじめ作成しておき、ユーザーが1件ずつボタン操作で順に投稿していく機能。

**詳細要求**:

- クリエイターモードに「スレッドに追加」導線を設け、投稿フォームを複数（セグメント）並べられるようにする。各セグメントは1投稿目（PostForm相当のフル機能）と同一の機能（本文・画像・OGP・URLリンク・YayText・カスタムパラメータ・返信/引用設定・自己ラベル・entry詳細設定を含む）を持つ。
- セグメントは「+」ボタンで追加、不要なセグメントは削除できる。
- 本機能を有効化した場合、自動ポップアップ（クロスポスト等の自動遷移）は行わない。各セグメントに個別の「投稿」ボタンを表示し、ユーザーが1件ずつクリックして投稿する。
- 投稿順序を担保するため、セグメントNへの投稿操作は、セグメントN-1が投稿完了するまで無効化（またはボタン非表示）する。
- 2件目以降の投稿は、1件目の投稿を `root`、直前の投稿を `parent` とする `app.bsky.feed.post#replyRef` を付与して作成する。
- 各セグメントが画像投稿であれば、そのセグメントごとにskyshare entryが作成される（スレッド全体で1つに限定しない）。
- バックエンドの `POST /v2/entry` 及び `POST /v2/bsky/record` に、任意の `reply`（`{ root: {uri, cid}, parent: {uri, cid} }`）フィールドを追加し、`createBskyPost` の投稿レコードに反映する。

**受け入れ条件**:

- 3件以上のセグメントを作成し、1件目→2件目→3件目の順に投稿すると、Bluesky上で正しくスレッド（リプライチェーン）として表示される。
- 途中のセグションが未投稿の間、後続セグメントの投稿ボタンは操作できない。
- 各セグメントの返信/引用設定・自己ラベル・カスタムパラメータ・URLリンク・YayTextがそれぞれ独立して機能する。

## 7. 非機能要件

- **既存機能への影響最小化**: 既存PostForm・関連API（`/v2/entry`, `/v2/bsky/record`）の既存フィールドの挙動・レスポンス形状は後方互換を維持する（新規フィールドはすべて任意項目として追加する）。
- **Cloudflare Workers制約**: 新規バックエンドロジックはNode.js固有APIに依存しないこと。
- **コードファースト原則の踏襲**: 新規APIフィールドは `src/lib/api/schema/**` のZodスキーマを単一の真実の源として追加し、`npm run codegen` でフロント用クライアントを再生成する。
- **再利用性（逆輸入可能性）**: FR1〜FR5の機能コンポーネント・関連関数は、クリエイターモード専用フォームに直接結合せず、独立したモジュールとして実装し、通常のPostFormからも将来利用できる構造にする。
- **コンポーネント実装方針**: 新規UIは可能な限り既存の共通コンポーネント（`Overlay`, `ToggleSwitch`, `Collapsible`, `CountedTextInput` 等）を再利用して構成する。FR1〜FR4の入り口は、独立仕様化済みの共通コンポーネント `EditorToolbox`（[`specs/editor-toolbox`](../editor-toolbox/requirements.md)）を前提として利用する。
- **アクセシビリティ**: 新規UI要素（ツールボックス・パネル・ダイアログ等）は既存コンポーネント（`Overlay`, `ToggleSwitch`, `Collapsible` 等）の実装方針・ARIA属性の付け方に準拠する。
- **テスト**: 新規バックエンドロジック（record組み立て・facet再計算・カスタムフィールドのマージ処理等）は `tests/` 配下に分岐網羅レベルの単体テストを追加する（`tests/README.md` の方針に従う）。
- **セキュリティ**: カスタムパラメータのキー解析においてプロトタイプ汚染を防止する。

## 8. 未決事項・リスク

- YayText変換で生成されるUnicode装飾文字は、一部書体で文字化け・視認性低下（アクセシビリティ低下、スクリーンリーダーでの読み上げ不能）が既知の問題として存在する。注意喚起UIの要否は設計時に検討する。
- カスタムパラメータで付与した内容は、Bluesky公式クライアントを含む多くのAppViewでは無視される（表示されない）。ユーザーへの期待値調整（UI上の説明文言）が必要。
- スレッド投稿中に一部セグメントの投稿が失敗した場合のリトライ・ロールバック方針は設計書で詳細化する。
- YayText変換と手動リンクfacetの「重なりを許容し自動再計算する」方針により、装飾後の文字列が元のURLと一致しなくなるケース（意図せずリンク切れになる）が起こり得る。UI上での警告表示要否は設計時に検討する。
