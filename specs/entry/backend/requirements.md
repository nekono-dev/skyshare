# v2/entry API 要件定義

`/v2/entry`エンドポイントが満たすべき機能要件・非機能要件・受け入れ条件を定義する。

## 1. 背景・スコープ

- Skyshareは、Bluesky投稿とそれに紐づく「skyshare entry」（画像ギャラリー的な独自メタデータレコード、`dev.nekono.skyshare.entry`）を管理するサービスである。
- `/v2/entry` は、投稿の作成・entryの発行・entryの編集・entryの削除という、entryのライフサイクル全体を1つのリソースエンドポイントに集約する。
- 旧`/v2/bsky/record`はこのエンドポイントへ統合され廃止されている（[design.md §1](design.md#1-概要)）。後方互換のためのラッパーは設けない（`[[prerelease_architecture_over_minimal_diff]]`方針に整合）。

## 2. 機能要件

### FR-1: 新規Bluesky投稿の作成（単発）

- ユーザーは、テキストのみ／OGPリンクカード付き／画像付きのいずれかの形式でBluesky投稿を1件作成できる。
- 画像投稿の場合、投稿と同時に「skyshare entry」の作成を任意で指定できる（`createEntry`フラグ）。
- テキストのみ・OGPリンクカードのみの投稿には、entry作成機能を提供しない（画像を伴わないentryは意味を持たないドメイン制約）。

### FR-2: 新規Bluesky投稿の作成（スレッド）

- ユーザーは、複数件の投稿を1回のリクエストでスレッド（reply chainで連結された投稿群）として作成できる。
- スレッド内の各投稿は独立して、テキストのみ／OGPリンク／画像のいずれかの形式・`createEntry`指定を持てる（要素ごとに異なる組み合わせが混在してよい）。
- スレッド全体は原子的に作成される。1件でも不正であれば、スレッド全体を作成しない（部分成功状態を許さない）。
- スレッドは既存の投稿（他リクエストで作成済みのBluesky投稿、または他スレッド）へ接続（reply）できる。

### FR-3: 返信可否・引用可否の制御（gate）

- ユーザーは、スレッド内の各投稿ごとに個別に返信可否（threadgate）・引用可否（postgate）を設定できる。

### FR-4: 既存投稿からのentry発行（from-post）

- ユーザーは、自分が過去に作成した画像付きBluesky投稿を指定し、新規投稿を作らずにskyshare entryのみを事後的に発行できる。
- 発行対象は画像投稿でなければならない（テキストのみ・OGPリンクの投稿からは発行できない）。

### FR-5: skyshare entryの編集

- ユーザーは、自分が所有するskyshare entryの見出し（heading）・説明文（caption）を事後的に編集できる。
- 見出しは100文字、説明文は300文字を上限とする。
- entryの他の要素（visual画像、紐づくBluesky投稿の参照）は編集対象に含まない。

### FR-6: skyshare entryの削除

- ユーザーは、自分が所有するskyshare entryを削除できる。
- entry削除時、紐づくBluesky投稿を同時に削除するかどうかを選択できる（既定は削除しない＝entryのみ削除）。
- 紐づくBluesky投稿の削除に失敗しても、entry自体の削除操作は成功として扱われなければならない（利用者から見て「entryを消したのに何も起きない」事故を避ける）。
- entryの`source`がスレッド先頭投稿を指す場合（`entrySource: "threadRoot"`で作成された、スレッド全体を代表するentry。FR-7参照）、紐づくBluesky投稿の削除にあたり、「`source`の投稿1件のみ削除」（既定の1対1挙動）に加えて、「`source`を起点とするスレッド全体（entry所有者自身が投稿した後続投稿すべて）を削除」する選択肢を用意する（詳細は[specs/entry/frontend/requirements.md](../frontend/requirements.md)参照。フロントエンドからの要望を受けた拡張）。
  - この選択肢は、`source`がスレッド先頭ではない場合（＝スレッド構造を持たない単発投稿、または`entrySource: "self"`で作成された個別entry）には提供しない。この場合は常に「その投稿1件のみ」を削除する既存の挙動（1対1対応）を維持する。
  - スレッド全体削除の対象は、entry所有者自身が投稿した投稿のみとする。第三者による返信は削除できないため対象に含めない。

### FR-7: entryの`source`とスレッド構造の関係（`entrySource`）

skyshareアプリケーションが自らスレッドを作成できるようになった（FR-2）ことに伴い、entryの`source`をスレッド全体の代表（先頭投稿）とみなすか、投稿ごとの個別のものとみなすかという設計判断が生じる。これを解決するため、APIリクエストの`entrySource`フィールドで明示指定できるようにする。

- skyshareアプリケーションとしての「通常機能」では、entryの`source`はスレッドそのもの（＝スレッド先頭投稿）を示す。ただし、投稿ごとに個別の`source`を持たせる方針もバックエンドとしては選択可能なままとし、どちらの方針を採るかはAPIリクエストの`entrySource?: "self" | "threadRoot"`フィールドで明示指定できる。
- `entrySource`は`createEntry: true`の投稿にのみ意味を持ち、次の2経路の両方に存在する（DELETEはこの設計の対象外。常に`source`が指す投稿1件のみを扱う）。
  - **新規投稿・スレッド（`POST /v2/entry`の`posts[i]`、3分岐すべて）**:
    - `"self"`: その投稿自身の（事前計算済み）`uri`/`cid`を`source`にする。
    - `"threadRoot"`: スレッド先頭（`posts[0]`）の（事前計算済み）`uri`/`cid`を`source`にする。`i === 0`自身が対象の場合は`self`と等価になる。
    - 省略時のデフォルト: `posts.length > 1`（スレッド）なら`"threadRoot"`、`posts.length === 1`（単発投稿）なら`"self"`。単発投稿の既存挙動には影響しない。
    - 1リクエスト内で`createEntry: true`な要素が複数あってもよく、それぞれが独立して`entrySource`を選べる。バックエンドはentry作成件数を制限しない。「通常機能ではスレッドにつき1entry（`threadRoot`を選んだもの1件のみ）」という運用上の使い方は、フロントエンド側のUXの制約として実現する（[specs/entry/frontend/design.md](../frontend/design.md)参照）。
  - **既存投稿からのentry発行（from-post、`{uri, ogImage}`分岐）**:
    - 対象投稿（`getRecord`で取得済みの投稿レコード）が`reply.root`を持ち、かつ`reply.root.uri`の repo（DID）が呼び出し者自身と一致する場合のみ、`"threadRoot"`は有効に機能し、その`root`のuri/cidを`source`として採用する。
    - `reply.root`が無い場合、または`reply.root`のrepoが呼び出し者自身と異なる場合（他人が起点のスレッドへ返信した投稿だった場合）は、`entrySource: "threadRoot"`を指定しても`"self"`と同じ挙動にフォールバックする（エラーにはしない）。他人が起点のスレッドを自分のentryの`source`にすり替えることを防ぐための安全側のデフォルトである。
    - 省略時のデフォルトは「`reply.root`が存在し、かつ自分自身のrepoである場合は`threadRoot`、それ以外は`self`」。
- `entrySource`が影響するのは「skyshareアプリケーションとしての表示・意味付け」のみであり、`dev.nekono.skyshare.entry`lexicon自体に「`source`はスレッド先頭でなければならない」という制約を持ち込むものではない（`source`は引き続き汎用`strongRef`のまま、[specs/entry/lexicons/design.md](../lexicons/design.md)参照）。lexiconの後方互換性・汎用性は損なわない。

## 3. 非機能要件

### NFR-1: 認可・所有権保護

- 本人が作成した投稿・entry以外に対する操作（reply接続・entry編集・entry削除・元投稿削除・from-post発行）を一切許可してはならない。
- クライアントから送られるURI（`uri`、`reply.root.uri`、`reply.parent.uri`）は、サーバ側で必ずcollection種別と所有者（DID）を検証してから使用する。
- entry削除に伴う元投稿削除では、クライアントが送った値をそのまま信用せず、entryレコードに記録された`source`から削除対象を導出する。スレッド全体削除（FR-6）でも同様に、削除対象の後続投稿群はクライアントが送った一覧を信用せず、サーバ側が`source`から辿って導出し、各投稿の所有者（DID）を1件ずつ検証してから削除対象に含める。

### NFR-2: データ整合性（原子性）

- 複数の投稿・gate・entryレコードにまたがる書き込みは、全件成功か全件失敗のいずれかでなければならない。
- atproto（AT Protocol PDS）の`com.atproto.repo.applyWrites`が持つ単一トランザクション保証を利用し、アプリケーション層で部分ロールバックを実装しない。
- スレッド全体削除（FR-6）における複数のBluesky投稿の削除は、1回の`applyWrites`により全件成功か全件失敗のいずれかでなければならない（スレッドの一部投稿だけが削除された状態を許さない）。ただし、この投稿削除の失敗が、entry自体の削除の成功可否に影響してはならない（既存のentry削除の不変条件を維持する。[§6 設計上の重要な不変条件](../backend/design.md#6-設計上の重要な不変条件テストが担保している性質)参照）。

### NFR-3: 楽観的排他制御

- entry編集（PUT）は、読み取り時点のレコードと書き込み時点のレコードが一致することを保証してから更新する（`swapRecord`によるCAS）。同時編集による更新の消失（lost update）を検出する。

### NFR-4: エラーの一貫性

- 全メソッドで、認証・入力検証・対象未検出・外部連携失敗のエラー分類を統一する（400/401/404/429/500）。
- エラーレスポンスは`{ error: string }`形式に統一し、`cache-control: no-store`を付与してキャッシュされないようにする。

### NFR-5: Cloudflare Workers実行環境制約

- Node.js固有APIに依存しない実装であること（[AGENTS.md](../../../AGENTS.md)の全社方針）。

### NFR-6: スキーマ・ドキュメントの単一の真実の源

- リクエストボディの検証ルールは、OpenAPIドキュメント生成にもそのまま使われる同一のZodスキーマから導出されなければならない（バリデーション用とドキュメント用でスキーマを分岐させない）。

### NFR-7: スレッド投稿数上限の一貫性

- スレッドとして作成できる投稿数には上限を設ける（既定値: 100件）。
- この上限値は、新規投稿作成（本エンドポイント）とスレッド下書きの双方で同一の値を用いなければならない。両者は「スレッドの1セグメント」という同一概念を扱うため、上限値が食い違ってはならない。
- フロントエンドがスレッド作成UIで上限件数を表示・制御する場合も、同じ上限値を参照しなければならない。

### NFR-8: レート制限（429）の発生源

- アプリケーション層は独自の投稿頻度制限を設けない。レート制限は、連携先プラットフォーム（Bluesky PDS）が課す制限にのみ依拠する。

## 4. 明示的な非対応・意図的な制約（実装から読み取れる仕様上の判断）

| 項目                                       | 内容                                                                                                                                                                  |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| facetsの自動検出                           | サーバはfacets（URL/メンション/ハッシュタグのリッチテキスト注釈）を自動検出しない。クライアントが組み立てたものをそのまま受け取り、本文バイト長との整合性のみ検証する |
| 画像とOGPの同時指定                        | 両方指定された場合は画像embedのみ採用し、OGPは無視される（Blueskyの仕様上、1投稿に画像embedと外部リンクembedは共存できないため）                                      |
| entry作成対象                              | 画像投稿のみ（テキスト投稿・OGPリンク投稿からのentry作成は不可）                                                                                                      |
| スレッド内の`reply`はトップレベルに1つのみ | スレッド内2件目以降の接続関係はサーバが自動的に組み立てるため、クライアントが指定すべきは「スレッド全体がどこに接続するか」のみ                                       |
| entry編集の対象フィールド                  | heading/captionのみ。visual・source（紐づく投稿）は不変                                                                                                               |
| entry削除時のreply chain補正・警告         | `source`1件のみの削除（既定の1対1挙動）・スレッド全体削除（FR-6）のいずれでも、削除対象外の投稿（第三者の返信、スレッド全体削除を選ばなかった場合の後続投稿）のreply参照を書き換えたり、「スレッドが分断されます」といった警告を出す機能は持たない。reply chainの欠落はAT Protocol側の投稿削除一般に伴う挙動であり、Bluesky公式クライアントからの直接削除でも同じことが起きるため、Skyshareのentry削除機能だけがこれを特別扱いする理由がない |

## 5. 受け入れ条件（Acceptance Criteria）

- 認証: cookie無し→400、未認証（session未確立）→401 が POST/PUT/DELETE すべてで一貫している
- POST: multipart以外のContent-Type、パース不能なbodyは400
- POST(from-post): 所有者不一致→400、対象投稿なし→404、画像なし投稿→400、ogImage欠落→400、アップロード失敗→500、成功→200＋skyshareEntry
- POST(新規/単発): createEntry:trueの制約（画像＋ogImage必須）違反→400、画像枚数とメタ不一致→400、facets範囲外→400、各アップロード失敗→500、embed優先順位（画像＞OGP）が保たれる、reply所有者不一致→400
- POST(スレッド): 複数件が1回のapplyWritesで作成される、reply chainが正しく連結される、gate指定が該当rkeyのみに適用される、一部要素のみcreateEntry:trueの場合は該当要素のみentryが返る
- POST(スレッド異常系): 途中要素の検証エラーで全体が400になりapplyWritesが呼ばれないこと、途中要素のアップロード失敗で500になること
- PUT: スキーマ不正→400、所有者不一致→400、対象なし→404、成功→200
- DELETE: スキーマ不正→400、所有者不一致→400、deleteBskyPost指定時に対象entryなし→404、元投稿削除失敗でもentry削除は200、deleteBskyPost=falseでは元投稿を削除しない
- スレッドの中間投稿・末尾投稿から`createEntry:true`でentryを作成できる（先頭投稿と同じ条件で成功する）
- スレッドの中間投稿・末尾投稿を対象にfrom-post発行ができる（`POST /v2/entry`に`uri`指定）
- `entrySource`省略時、スレッド（`posts.length > 1`）では`source`がスレッド先頭投稿の`uri`/`cid`になり、単発投稿（`posts.length === 1`）では従来通り自身の`uri`/`cid`になる
- `entrySource: "self"`を明示指定した場合、スレッド内のどの位置の投稿でも、`source`はその投稿自身の`uri`/`cid`になる（従来の挙動を維持できる）
- from-postで対象投稿が自分自身の`reply.root`を持つ場合、`entrySource`省略時は`source`がその`root`の`uri`/`cid`になる。`reply.root`が無い、または他人のrepoの場合は`entrySource`の指定に関わらず対象投稿自身が`source`になる
- entry削除（`deleteBskyPost:true`、スレッド全体削除を指定しない場合）時、`source`以外の投稿のレコードには一切書き込みが発生しないことをテストで確認する
- スレッド中間投稿の削除後も、他のentry（同一スレッドの他投稿由来）の`orphaned`フラグは変化しない
- entry削除でスレッド全体削除を指定した場合、`source`を起点にentry所有者自身が投稿した投稿がすべて削除され、第三者の返信・自分以外が所有する投稿には一切操作が行われない
- entry削除でスレッド全体削除を指定した場合でも、`source`が単発投稿（後続投稿を持たない）であれば`source`1件のみが削除される（1対1挙動と結果が一致する）
- entry削除でスレッド全体削除を指定し、投稿削除の一部が失敗しても、entry自体の削除は200として成功する
