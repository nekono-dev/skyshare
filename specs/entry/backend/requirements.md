# v2/entry API 要件定義

`/v2/entry`エンドポイントが満たすべき機能要件・非機能要件・受け入れ条件を定義する。

## 1. 背景・スコープ

- Skyshareは、Bluesky投稿とそれに紐づく「skyshare entry」（画像ギャラリー的な独自メタデータレコード、`dev.nekono.skyshare.entry`）を管理するサービスである。
- `/v2/entry` は、投稿の作成・entryの発行・entryの編集・entryの削除という、entryのライフサイクル全体を1つのリソースエンドポイントに集約する。
- 旧`/v2/bsky/record`はこのエンドポイントへ統合され廃止されている（[design.md §1](design.md#1-概要)）。後方互換のためのラッパーは設けない（`[[prerelease_architecture_over_minimal_diff]]`方針に整合）。
- 本書は、投稿ごとに個別のskyshare entryを作り分ける機能（旧仕様で提供していた、投稿単位でentryの生成元を選択する機能）を廃止し、「1回の投稿作成リクエスト（1件、またはスレッド）につきentryは最大1件、必ずスレッド全体を代表する投稿を`source`とする」という設計に統一する（[FR-2](#fr-2-entryのsourceの自動解決)）。

## 2. 機能要件

### FR-1: 新規Bluesky投稿の作成（単発／スレッド共通）

- ユーザーは、1件または複数件（スレッド、reply chainで連結された投稿群）のBluesky投稿を1回のリクエストで作成できる。各投稿は独立して、テキストのみ／OGPリンクカード付き／画像付きのいずれかの形式を持てる（要素ごとに異なる組み合わせが混在してよい）。
- スレッド全体は原子的に作成される。1件でも不正であれば、スレッド全体を作成しない（部分成功状態を許さない）。
- スレッドは既存の投稿（他リクエストで作成済みのBluesky投稿、または他スレッド）へ接続（reply）できる。
- リクエスト全体につき、skyshare entryの作成要否は**1回だけ**指定できる（`createEntry`フラグ。投稿ごとに個別指定するものではない）。`createEntry: true`の場合、entryの代表画像（visual）を1点あわせて指定する。
- entry作成対象は、リクエストに含まれる投稿群（1件またはスレッド）のうち**画像投稿を最低1件含む**場合に限る。画像投稿を1件も含まない投稿・スレッド（テキストのみ・OGPリンクカードのみで構成される）には、entry作成機能を提供しない（画像を伴わないentryは意味を持たないドメイン制約）。visualとして使う画像がリクエスト中のどの投稿の画像と一致するかをサーバは検証・関知しない（クライアントが指定したvisual画像をそのまま採用する）。

### FR-2: entryの`source`の自動解決

- 新規に作成されるskyshare entryの`source`（紐づくBluesky投稿への参照）は、常にサーバが自動的に解決する。クライアントが`source`の解決方針を選択する手段は提供しない（投稿ごとに個別のentryを作る、という運用はできない）。
- 解決の結果は常に「スレッド全体を代表する投稿（スレッド先頭）」を指すこと。ただし、他人が起点のスレッドを自分のentryの`source`にすり替えることは、いかなる経路でも許可してはならない（悪意の有無を問わず、安全側に倒す）。具体的な解決規則（新規投稿・スレッド作成時／既存投稿からの発行時それぞれの判定条件）は[design.md §7](../backend/design.md#7-sourceの解決ロジック)が定める。
- 上記の自動解決は「skyshareアプリケーションとしての表示・意味付け」のみに影響し、`dev.nekono.skyshare.entry`lexicon自体に「`source`はスレッド先頭でなければならない」という制約を持ち込むものではない（`source`は引き続き汎用`strongRef`のまま、[specs/entry/lexicons/design.md](../lexicons/design.md)参照）。lexiconの後方互換性・汎用性は損なわない。

### FR-3: 返信可否・引用可否の制御（gate）

- ユーザーは、スレッド内の各投稿ごとに個別に返信可否（threadgate）・引用可否（postgate）を設定できる。

### FR-4: 既存投稿からのentry発行（from-post）

- ユーザーは、自分が過去に作成した画像付きBluesky投稿を指定し、新規投稿を作らずにskyshare entryのみを事後的に発行できる。
- 発行対象は画像投稿でなければならない（テキストのみ・OGPリンクの投稿からは発行できない）。対象投稿がスレッドの先頭・中間・末尾のいずれであっても区別しない。
- `source`の解決は[FR-2](#fr-2-entryのsourceの自動解決)に従う（対象投稿が自分自身のスレッドの一部であれば、そのスレッド先頭が`source`になる）。

### FR-5: skyshare entryの編集

- ユーザーは、自分が所有するskyshare entryの見出し（heading）・説明文（caption）を事後的に編集できる。
- 見出しは100文字、説明文は300文字を上限とする。
- entryの他の要素（visual画像、紐づくBluesky投稿の参照）は編集対象に含まない。

### FR-6: skyshare entryの削除

- ユーザーは、自分が所有するskyshare entryを削除できる。
- entry削除時、紐づくBluesky投稿を同時に削除するかどうかを選択できる（既定は削除しない＝entryのみ削除）。
- 紐づくBluesky投稿の削除に失敗しても、entry自体の削除操作は成功として扱われなければならない（利用者から見て「entryを消したのに何も起きない」事故を避ける）。
- entryの`source`がスレッド先頭投稿であり、かつentry所有者自身による後続投稿が実際に存在する場合、紐づくBluesky投稿の削除にあたり、「`source`の投稿1件のみ削除」（既定の1対1挙動）に加えて、「`source`を起点とするスレッド全体（entry所有者自身が投稿した後続投稿すべて）を削除」する選択肢を用意する（詳細は[specs/entry/frontend/requirements.md](../frontend/requirements.md)参照。フロントエンドからの要望を受けた拡張）。
  - `source`が単発投稿（後続投稿を持たない）である場合は、この選択肢を提供する意味がなく、常に「その投稿1件のみ」を削除する既存の挙動（1対1対応）に帰着する。
  - スレッド全体削除の対象は、entry所有者自身が投稿した投稿のみとする。第三者による返信は削除できないため対象に含めない。

## 3. 非機能要件

### NFR-1: 認可・所有権保護

- 本人が作成した投稿・entry以外に対する操作（reply接続・entry編集・entry削除・元投稿削除・from-post発行）を一切許可してはならない。
- クライアントから送られるURI（`uri`、`reply.root.uri`、`reply.parent.uri`）は、サーバ側で必ずcollection種別と所有者（DID）を検証してから使用する。
- entry削除に伴う元投稿削除では、クライアントが送った値をそのまま信用せず、entryレコードに記録された`source`から削除対象を導出する。スレッド全体削除（FR-6）でも同様に、削除対象の後続投稿群はクライアントが送った一覧を信用せず、サーバ側が`source`から辿って導出し、各投稿の所有者（DID）を1件ずつ検証してから削除対象に含める。

### NFR-2: データ整合性（原子性）

- 複数の投稿・gate・entryレコードにまたがる書き込みは、全件成功か全件失敗のいずれかでなければならない。原子性は外部PDSのトランザクション保証に委ね、アプリケーション層で独自の部分ロールバックを行わない（具体的な実現方法はdesign.md参照）。
- スレッド全体削除（FR-6）における複数のBluesky投稿の削除も、全件成功か全件失敗のいずれかでなければならない（スレッドの一部投稿だけが削除された状態を許さない）。ただし、この投稿削除の失敗が、entry自体の削除の成功可否に影響してはならない（既存のentry削除の不変条件を維持する。[§6 設計上の重要な不変条件](../backend/design.md#6-設計上の重要な不変条件テストが担保している性質)参照）。

### NFR-3: 楽観的排他制御

- entry編集（PUT）は、読み取り時点のレコードと書き込み時点のレコードが一致することを保証してから更新する（`swapRecord`によるCAS）。同時編集による更新の消失（lost update）を検出する。

### NFR-4: エラーの一貫性

- 全メソッドで、認証・入力検証・対象未検出・外部連携失敗のエラー分類を統一する（400/401/404/429/500）。
- エラーレスポンスは`{ error: string }`形式に統一し、`cache-control: no-store`を付与してキャッシュされないようにする。

### NFR-5: Cloudflare Workers実行環境制約

- Node.js固有APIに依存しない実装であること（[AGENTS.md](../../../AGENTS.md)の全社方針）。

### NFR-6: スキーマ・ドキュメントの単一の真実の源

- リクエストボディの検証ルールは、OpenAPIドキュメント生成にもそのまま使われる単一のスキーマ定義から導出されなければならない（バリデーション用とドキュメント用でスキーマを分岐させない。採用する実装手段はdesign.md参照）。

### NFR-7: スレッド投稿数上限の一貫性

- スレッドとして作成できる投稿数には上限を設ける（既定値: 100件）。
- この上限値は、新規投稿作成（本エンドポイント）とスレッド下書きの双方で同一の値を用いなければならない。両者は「スレッドの1セグメント」という同一概念を扱うため、上限値が食い違ってはならない。
- フロントエンドがスレッド作成UIで上限件数を表示・制御する場合も、同じ上限値を参照しなければならない。

### NFR-8: レート制限（429）の発生源

- アプリケーション層は独自の投稿頻度制限を設けない。レート制限は、連携先プラットフォーム（Bluesky PDS）が課す制限にのみ依拠する。

## 5. 受け入れ条件（Acceptance Criteria）

認証・スキーマ不正・所有者不一致・対象未検出等に対する個別のステータスコード対応は、NFR-4が定める分類方針に従い[design.md](design.md)のステータスコード対応表（§3.7・§4.3・§5.3）が具体化する。本節では、それらのステータス対応表だけでは表現しきれない、業務的に重要な受け入れ条件のみを列挙する。

- POST（新規投稿・スレッド）は原子的に作成される。途中の1件でも検証・アップロードに失敗すれば、スレッド全体が作成されない（部分成功状態が発生しない）
- 画像とOGPを同時指定した投稿は画像embedが優先され、gate（threadgate/postgate）指定は該当投稿にのみ適用される
- `createEntry:true`によるskyshare entry作成は、リクエスト全体（1件またはスレッド）につき常に高々1件のみ返る
- スレッドの中間投稿・末尾投稿に画像があれば、その投稿の画像を`source`（スレッド先頭）から独立した状態で`createEntry:true`によりentry作成できる
- スレッドの中間投稿・末尾投稿を対象にfrom-post発行ができる。作成されたentryの`source`はスレッド先頭になる
- 新規投稿・スレッドで`createEntry:true`を指定すると、`source`は常にスレッド先頭（単発投稿では自身）になる。投稿ごとに`source`を選ぶ手段は存在しない
- from-postで対象投稿が自分自身の`reply.root`を持つ場合、`source`はその`root`になる。`reply.root`が無い、または他人のrepoの場合は対象投稿自身が`source`になる
- entry削除（`deleteBskyPost:true`、スレッド全体削除を指定しない場合）時、`source`以外の投稿には一切影響が及ばない
- スレッド中間投稿の削除後も、他のentry（同一スレッドの他投稿由来）の`orphaned`フラグは変化しない
- entry削除でスレッド全体削除を指定した場合、`source`を起点にentry所有者自身が投稿した投稿がすべて削除され、第三者の返信・自分以外が所有する投稿には一切操作が行われない
- entry削除でスレッド全体削除を指定した場合でも、`source`が単発投稿（後続投稿を持たない）であれば`source`1件のみが削除される（1対1挙動と結果が一致する）
- entry削除でスレッド全体削除を指定し、投稿削除の一部が失敗しても、entry自体の削除は成功として扱われる
