# Bluesky OAuth クライアント 要件定義書

## 1. 目的

Bluesky の OAuth のクライアントとして、ログインと予約投稿の許可に共通の、クライアントの識別・認可サーバーの探索・トークンの要求・PDS への要求・認可の画面からの戻りの受け渡しを提供する。開発用の手元の環境でも、本番と同じ認可サーバーで認可を受けられるようにする。

## 2. スコープ

### 2.1 対象

- 配信元ごとのクライアントの識別子・戻り先・メタデータ・公開鍵の一覧。
- 手元の開発環境での、開発用の公開クライアントと戻り先の中継。
- 認可サーバーの探索と、DID から PDS の解決。
- 認可の要求の事前送信・認可コードの交換・トークンの更新・取消と、DPoP の証明。
- PDS への、DPoP に結び付けたアクセストークンでの要求。
- 認可の画面からの戻りを、許可を始めたページへ用途とともに渡すこと。

### 2.2 対象外

- 得たトークンの保管と、ログインや予約での使い方。
- 認可の画面の表示と、利用者の認証。

## 3. 前提

- なし

## 4. 機能要件

- FR-1: 配信元のオリジンごとに、クライアントの識別子・戻り先・要求しうるすべての権限を載せたメタデータと、署名の公開鍵の一覧を提供する。
- FR-2: 配信元がループバックのホストのとき、権限と戻り先を識別子に含む開発用の公開クライアントとして振る舞い、戻り先にループバックの IP の http の住所を使う。
- FR-3: トークンの要求には、開発用の公開クライアントならクライアントの識別子だけを、それ以外ならクライアントの秘密鍵で署名した証明を付け、秘密鍵が無いときは要求しない。
- FR-4: 認可サーバーは、PDS の保護されたリソースのメタデータか認可サーバーの識別子から探し、メタデータの識別子の一致と、必要な端点と方式があることを確かめる。
- FR-5: DID から DID ドキュメントに書かれた PDS を解決する。
- FR-6: 認可サーバーと PDS への要求に DPoP の証明を付け、nonce を求められたら受け取った nonce で1回だけやり直す。
- FR-7: 認可の要求の事前送信・認可コードの交換・更新用トークンによる更新・取消を提供し、トークンの応答は種類・持ち主・アクセストークン・更新用トークンがそろうものだけを受け付ける。
- FR-8: PDS への要求に、DPoP に結び付けたアクセストークンと、そのハッシュを入れた証明を付ける。
- FR-9: 認可の画面からの戻りは、開始時に戻り先だけへ送る cookie に入れた用途とページへ、既知の項目だけを住所のフラグメントに移して転送する。
- FR-10: 戻り先の cookie の用途が不正なときは予約の設定のページへ、ページだけが不正なときは用途ごとの既定のページへ転送し、別のオリジンへは転送しない。
- FR-11: 開発サーバーは、ループバックの戻り先への遷移を、同じパスとクエリのまま開発サーバーのオリジンへ転送する。

## 5. 非機能要件

- NFR-1: OAuth のクライアントの処理で、atproto のライブラリを読み込む箇所を0件にする。
- NFR-2: トークン・認可コード・鍵を含む文字列を、ログに出力する箇所を0件にする。

## 6. 受け入れ条件

- AC-1 (FR-1): 本番のオリジンのメタデータが、そのオリジンの識別子と戻り先と公開鍵の一覧の住所と、ログインと予約の両方の権限を含む。
- AC-2 (FR-1): 公開鍵の一覧に秘密鍵の成分が含まれない。
- AC-3 (FR-2): ループバックのオリジンでは、識別子が権限と戻り先を含む開発用の形になり、戻り先がループバックの IP の http の住所になる。
- AC-4 (FR-3): 開発用の公開クライアントの証明が識別子だけになり、それ以外では署名した証明が付き、秘密鍵が無ければ要求できない。
- AC-5 (FR-4): メタデータの識別子が違う認可サーバーと、必要な端点が欠けた認可サーバーは使われない。
- AC-6 (FR-4): 認可サーバーの識別子から、その端点が得られる。
- AC-7 (FR-5): DID ドキュメントの PDS が解決され、解決できない DID では何も返らない。
- AC-8 (FR-6): nonce を求められた要求が、受け取った nonce を入れて1回だけやり直される。
- AC-9 (FR-7): 認可コードの交換で、DPoP 型で持ち主と2つのトークンがそろう応答だけがトークンとして返る。
- AC-10 (FR-7): 更新用トークンの失効が、再度の許可が必要な失敗として返る。
- AC-11 (FR-8): PDS への要求に、アクセストークンとそのハッシュを入れた証明が付き、nonce を求められると1回だけやり直す。
- AC-12 (FR-9): ログインの用途で始めた戻りが、そのページのフラグメントへ用途と既知の項目だけを移して転送される。
- AC-13 (FR-10): 用途の無い戻りは予約の設定のページへ、別のオリジンへ向かうページの戻りは用途の既定のページへ転送される。
- AC-14 (FR-11): ループバックの戻り先への遷移が、同じパスとクエリのまま開発サーバーのオリジンへ転送される。
- AC-15 (NFR-1): OAuth のクライアントの処理が、atproto のライブラリを読み込まない。
- AC-16 (NFR-2): 認可とトークンの要求に失敗しても、トークン・認可コード・鍵がログに現れない。
