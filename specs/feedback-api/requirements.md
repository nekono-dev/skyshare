# 不具合報告と機能提案の受付 要件定義書

## 1. 目的

ログイン中の利用者から不具合の報告と新機能の提案を受け付け、報告者のアカウントと動作中の版と環境の情報を添えて、ソースコードのリポジトリに Issue として登録し、開発者が再現と検討に使えるようにする。

## 2. スコープ

### 2.1 対象

- 報告と提案の入力の検証と、アカウントごとの送信回数の制限。
- Issue の件名・本文・ラベルの組み立てと、GitHub への登録。
- 動作中のビルドの版・コミット・リポジトリの埋め込み。

### 2.2 対象外

- 報告と提案の入力画面と、環境の情報の収集。
- スクリーンショットの添付。
- 登録した Issue の更新と削除。

## 3. 前提

- なし

## 4. 機能要件

- FR-1: 受付はログイン中の利用者に限り、報告者の DID とハンドルはログインのセッションから取り、入力からは受け取らない。
- FR-2: 入力は種別（不具合か新機能の提案）・件名・種別ごとの本文・環境の情報からなり、種別に合わない本文の項目を拒否する。
- FR-3: 不具合の本文は操作した内容と再現の頻度（毎回・ときどき・起きない・試していない）を必須とする。
- FR-4: 新機能の提案の本文は機能の内容を必須とし、技術的な補足を任意とする。
- FR-5: 件名と本文の各項目は空白だけの入力を拒否し、件名は100文字、本文の各項目は2000文字を上限として書記素で数える。
- FR-6: 送信は同じアカウントから60秒に1件までとし、超えた送信は登録せずに回数の超過を返す。
- FR-7: Issue には不具合なら bug、新機能の提案なら enhancement のラベルを付け、件名は利用者の件名を1行にしたものとする。
- FR-8: Issue の本文は、入力の本文・報告者のハンドルと DID・版とコミット・OS とブラウザとホーム画面からの起動か・ブラウザの識別文字列を載せる。
- FR-9: 利用者の入力は、メンション・リンク・画像・HTML として解釈されない形で本文に載せる。
- FR-10: 版とコミットは受け付けたサーバーのビルドの値を載せ、画面が送った値が異なるときは画面の値も並べて載せる。
- FR-11: ビルドは版・コミット・リポジトリを埋め込み、CI では実行中のワークフローの値を、手元では Git の値を使う。
- FR-12: 登録先のリポジトリか GitHub の認証情報が未設定のときは受付を停止し、GitHub の登録が失敗したときは失敗を返す。

## 5. 非機能要件

- なし

## 6. 受け入れ条件

- AC-1 (FR-1): セッションのない送信は401になり、入力に別の DID を含めても本文の報告者はセッションのアカウントになる。
- AC-2 (FR-2): 不具合の種別に新機能の提案の本文を付けた送信は400になる。
- AC-3 (FR-3): 再現の頻度が4つの値以外の不具合の送信は400になる。
- AC-4 (FR-4): 技術的な補足を省いた新機能の提案が登録され、本文から補足の見出しが除かれる。
- AC-5 (FR-5): 101文字の件名と空白だけの本文は400になり、結合文字を含む絵文字100個の件名は登録される。
- AC-6 (FR-6): 同じアカウントの2件目の送信が60秒以内なら429になり、GitHub への登録が行われない。
- AC-7 (FR-7): 不具合の Issue に bug、新機能の提案に enhancement のラベルが付き、件名の改行が空白になる。
- AC-8 (FR-8): Issue の本文に、入力の本文・ハンドル・DID・版・コミット・OS・ブラウザ・起動の形態・識別文字列が含まれる。
- AC-9 (FR-9): バッククォートとメンションと HTML を含む入力が、閉じられないコードブロックの中に載る。
- AC-10 (FR-10): 画面のコミットがサーバーと異なるときだけ、本文に画面のコミットが並ぶ。
- AC-11 (FR-11): CI の値があるときはその値を使い、ないときは Git の値を使い、どちらもないときは不明とする。
- AC-12 (FR-12): 認証情報がないときは503、GitHub が失敗を返したときは500になる。
