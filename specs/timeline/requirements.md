# Timeline コンポーネント 要件定義書

## 1. 背景・スコープ

- Timeline（`src/components/post/Timeline`、`/`ページに表示される自分の投稿一覧）は、`GET /v2/entries`（`app.bsky.feed.getAuthorFeed`ベース）で取得した自分の投稿を新しい順に一覧表示する。
- スレッド投稿機能（[specs/threadpost](../threadpost/requirements.md)）により、複数のBluesky投稿が1回のリクエストでスレッド（reply chain）として作成できるようになったことに伴い、Timeline一覧上でスレッドをどう表示するか、投稿時にskyshare entryを作らなかった画像投稿に対して事後的にentryを作成する導線をどう提供するかを本書で定める。
- 本書の対象は、Timeline一覧（`/`ページ）のみである。投稿フォーム自体（`ThreadComposer`）は[specs/threadpost](../threadpost/requirements.md)、entry詳細ページ（`entries/[slug].astro`）は[specs/entry/frontend](../entry/frontend/requirements.md)が対象とし、本書では扱わない。
- 本書は、スレッド構造の判定（グルーピング・後述の「メインスレッド」選出）はバックエンドが権威的に行う一方、skyshare entryを作成してよいか・どの範囲を対象にするかの判断はクライアントが行う、という責務分担を前提にする。entry作成APIそのものの仕様は[specs/entry/backend/requirements.md](../entry/backend/requirements.md)が定める。

## 2. 用語定義

| 用語                 | 意味                                                                                                                                                                                                                                    |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| プロトコルルート     | AT Protocol上、投稿レコード自身が持つ`record.reply.root`が指す、スレッド全体で共有される唯一の起点。返信でない投稿では、その投稿自身がプロトコルルートになる。スレッドがどこで分岐していても、分岐後の投稿からも常に同じ投稿を指す（分岐を区別しない）。                                          |
| 自分起点スレッド     | プロトコルルートが自分自身の投稿であるスレッド。Timeline上での表示・entry作成の対象になりうるのはこの種のスレッドのみ（FR-1）。                                                                                                                     |
| 他者起点スレッド     | プロトコルルートが自分以外の投稿であるスレッド。自分の投稿が他人の投稿への返信から始まっている場合（その投稿へさらに自分が返信を重ねている場合を含む）はすべてこれに該当する。Timeline上に一切表示せず、entry作成の対象にもしない（FR-1・FR-3）。                              |
| メインスレッド       | 自分起点スレッドにおいて、分岐点ごとに「直前の投稿との投稿日時の差が最も近い」側を辿ることで一意に選ばれる、投稿者自身の投稿のみで構成された直線的な投稿列。1つの自分起点スレッドにつき常に1系統だけが選ばれる。Timeline上のスレッドグループとして表示されるのはこの系統のみ（FR-1）。                    |
| サブスレッド         | 自分起点スレッドの分岐点で、メインスレッドの選出において採用されなかった側の投稿群。Timelineには一切表示しない（FR-1）。                                                                                                                      |
| スレッドグループ     | Timeline一覧上で1つの表示単位としてまとめられ、折りたたみ/展開の対象になる投稿群。自分起点スレッドのメインスレッドを構成する投稿（ルート投稿＋現在Timeline上に表示されている全replies）がこれにあたる。他者起点スレッドの投稿・サブスレッドの投稿はTimelineに表示されないため、スレッドグループを構成しない。1件のみの単独投稿も、便宜上1件から成るスレッドグループとして扱う（FR-1・FR-2）。 |
| ルート投稿           | スレッドグループのうち、時系列上最も古い投稿。自分起点スレッドである以上、常にプロトコルルート自身がルート投稿になる。                                                                                                    |
| 事後entry作成        | 投稿時にはskyshare entryを作成しなかった画像投稿に対して、後からentryを発行する機能（既存のfrom-post機能をTimeline上で使う導線）。                                                                                                              |

## 3. 機能要件

### FR-1: メインスレッドのグルーピング表示

- Timeline一覧は、自分起点スレッドのみを対象とする。他者起点スレッド（自分の投稿が他人の投稿への返信から始まっている場合。その投稿からさらに自分が返信を重ねている場合を含む）は、Timeline上に一切表示しない。
- 自分起点スレッドのうち、reply chainで連結された自分自身の投稿群（メインスレッド）を1つのスレッドグループとしてまとめて表示する。
- スレッドを構成する投稿の一部が、一覧データの取得元（Bluesky AppView）の都合で取得できない場合であっても、そのスレッドのプロトコルルート投稿自体が取得できている限り、欠落した投稿を補い、メインスレッドを構成する投稿すべてを1つのスレッドグループとして表示する（NFR-3参照）。
- ページング境界をまたぐなど、スレッドのプロトコルルート投稿自体が特定できない場合は、グルーピングを行わず独立した投稿として表示する（無理に遡って取得することはしない）。
- スレッドが途中で分岐する場合（同一投稿に対し、自分自身が複数回返信しているケース。例: A→B→Cに加え、Aから別途A→D→Eが存在するパターン）、それぞれの分岐点で、直前の投稿との投稿日時が最も近い1系統を、その分岐点までの系統の直接の続きとして採用する（メインスレッドの選出規則。`specs/entry/backend/design.md §7.3.1`の`extractOwnedLinearReplyChain`が持つ選択規則と共通）。候補が1件しかない分岐点（実在する分岐ではない）では、投稿日時の近さを問わずそのまま採用する（既存の投稿に事後で新規スレッドを継ぎ足す正当な操作を、時刻の乖離を理由に誤って除外しないため）。
- 上記の選択で採用されなかった側の投稿群（サブスレッド）は、Timeline上に一切表示しない。単独投稿としても、独立したスレッドグループとしても表示しない。同一プロトコルルートに複数の分岐点がある場合、また1つのメインスレッド候補内でさらに分岐する場合（多段分岐）も同様に、メインスレッドの選出で採用されなかった側はすべて非表示になる。
- メインスレッドを構成する投稿の一部が削除されるなどして構成が変化した場合、次回のTimeline一覧取得時に、その時点で残存する投稿群から改めてメインスレッドの選出（投稿日時差分が最も近い1系統の選出）をやり直す。それまでサブスレッドだった系統が、再選出の結果メインスレッドとして採用されれば、その系統が新たにTimeline上のスレッドグループとして表示される（動的な再評価・昇格）。メインスレッドかどうかを示す永続的な状態はどこにも保持されず、Timeline一覧取得のたびに毎回この選出をやり直す。

### FR-2: スレッド展開表示

- 2件以上の投稿から成るスレッドグループは、既定で折りたたみ表示（ルート投稿のみを表示し、後続投稿の件数を示す）とする。
- ユーザーが折りたたみ表示を操作すると、グループ内の全投稿が時系列順（古い→新しい）に展開表示される。
- 1件のみのスレッドグループ（reply chainを持たない単独投稿）は、従来通り単一の投稿カードとして表示する（折りたたみ表示にはしない）。

### FR-3: 事後entry作成（クライアントが作成可否・作成範囲を判断する）

skyshare entryの作成要求を受けたサーバは、その対象が「entryの作成対象としてふさわしいか」を判定しない（[specs/entry/backend/requirements.md FR-1・FR-2](../entry/backend/requirements.md#2-機能要件)）。作成してよいか・どの投稿をsourceに指定するかは、常にクライアント（Timeline）が判断する。

- クライアントは、次の3条件をすべて満たす場合に限り、対象投稿に対する事後entry作成を許可する。いずれか1つでも満たさない場合、その投稿を事後entry作成の対象にしない。
  1. 対象投稿がメインスレッドのルート投稿であること。ルート投稿以外（中間投稿・末尾投稿）を対象にした事後entry作成は行わない。
  2. 対象投稿が自分起点スレッドに属すること。ルート投稿がプロトコルルートである以上、この条件は「メインスレッドのルート投稿であること」（条件1）を満たす時点で常に満たされる（他者起点スレッドはFR-1によりそもそもTimelineに表示されないため、条件1を満たす投稿は必ず自分起点スレッドに属する）。
  3. 対象投稿がAPIの実行ユーザー自身のものであること（他人の投稿を対象にした事後entry作成は行わない）。ルート投稿は常に自分自身の投稿である（FR-1のグルーピング対象が自分自身の投稿に限られるため）ので、この条件も条件1を満たす時点で常に満たされる。
- 事後entry作成が対象とする範囲（entryがカバーする範囲）は、対象ルート投稿から、投稿時間比較で最短差分のリプライポストを繋いだ結果として現在Timeline上に表示されているメインスレッド全体（ルート＋現在表示中の全replies）とする。
- 事後entry作成ボタンは常にスレッドのルート投稿のカードにのみ表示し、中間投稿（replies）のカードに表示することはない。一方、ボタンの表示可否・作成されるentryのVisual（カバー画像）は、ルート投稿自身の画像だけでなく、メインスレッド内の後続投稿（replies）の画像も対象にする。Timeline上にはメインストリーム（メインスレッド）の投稿のみが表示されているため、Visualの生成元はこのメインストリームの中から選ぶ。
  - 次の条件をすべて満たすスレッドグループについて、ルート投稿に「entryを作成」ボタンを表示する。
    1. スレッドグループが2件以上の投稿から成る。
    2. ルート投稿自身に、既にskyshare entryが紐づいていない。
    3. ルート投稿、またはスレッド内のいずれかの後続投稿（replies）が画像を持つ。
  - ルート・repliesのいずれも画像を持たない場合、このボタンはスレッドグループ内のどの投稿にも表示しない。
  - Visualの生成元は、ルート投稿が画像を持てばルート投稿自身、持たなければrepliesのうちルートに最も近い（時系列上最も古い）画像投稿とする。複数の画像を持つ投稿が生成元になる場合、それらを1枚に結合する処理（`createDefaultThumbnail`）は、単独投稿の事後entry作成と同一のロジックを用いる。
- ボタン押下の対象は常にルート投稿である（本節冒頭の通り、ボタンは常にルート投稿のカードにのみ表示される）。これに伴い、ボタン押下時にクライアントがentry作成APIへ送る`source`は常にルート投稿自身のuriであり（サーバはreply chainを辿った自動解決を行わないため、明示的な指定が必要。[specs/entry/backend/requirements.md FR-2](../entry/backend/requirements.md#fr-2-entryのsourceの決定)）、Visualの生成元投稿（前段落）がルート投稿以外の後続投稿になる場合であっても変わらない。Visualの生成元（カバー画像の取得元）とsource（entryが紐づく投稿）は独立した別の関心事であり、後者が前者に引きずられることはない。
- 条件2（ルート投稿自身に、既にskyshare entryが紐づいていない）の判定は、ルート投稿自身が持つentryの有無のみで行い、スレッドグループ内の後続投稿（replies）が既にskyshare entryを持つかどうかは判定に影響しない。本機能の実装前に、スレッド中間の投稿を対象にentryが作成されていたケースがこれに該当しうるが、その場合であってもルート投稿自身がentryを持たない限り、ルート投稿を起点とする新規のentry作成は許可される（結果として、後続投稿に紐づく既存entryと、ルート投稿に紐づく新規entryの2件が同一スレッドグループ内に共存しうる）。後続投稿に紐づくentryへの操作（編集・削除等）はTimelineの対象外とし、[specs/entry/frontend/requirements.md](../entry/frontend/requirements.md)が定めるentry一覧側の既存機能で行う。

### FR-4: スレッド由来entryの視覚的区別（一覧）

- スレッドグループのルート投稿にskyshare entryが紐づいており、かつグループ内に実際に後続投稿が存在する場合、一覧上でそのentryがスレッド由来であることを視覚的に区別できるようにする。
- 単独投稿（reply chainを持たない）由来のentryには、この区別表示を行わない。

### FR-5: リンク・スレッド全体削除

- Timeline一覧上のentry付き投稿カードから、[specs/entry/frontend/requirements.md FR-5](../entry/frontend/requirements.md#3-機能要件)が定めるentry削除確認ダイアログと同一の選択肢（「Skyshareリンクを削除」「リンク・Bluesky投稿を削除」「リンク・スレッド全体を削除」「キャンセル」）を提示する。
- 対象投稿の`source`を起点に、entry所有者自身の後続投稿（reply chain）が実在する場合のみ「リンク・スレッド全体を削除」を選択肢として表示する。後続投稿が存在しない単独投稿では、この選択肢を表示しない（[specs/entry/backend/requirements.md FR-6](../entry/backend/requirements.md#2-機能要件)が定める削除対象導出ロジックと同一の判定を用いる）。
- 「リンク・スレッド全体を削除」を実行すると、対象entryとそのsource、およびsourceを起点にentry所有者自身が投稿した後続投稿がすべて削除される。削除成功後、削除されたスレッドグループ全体（表示上の折りたたみ/展開の対象になっていた投稿すべて）がTimeline一覧から除去される。
- 削除対象の導出はFR-1のメインスレッド選出と同一のロジック（`extractOwnedLinearReplyChain`）を用いるため、スレッドが分岐している場合、削除されるのは常にTimeline上でそのスレッドグループとして表示されていた側（メインスレッド）の投稿のみである。採用されなかった側の分岐（サブスレッド）は削除されない。
- FR-3の通り、事後entry作成は常にメインスレッドのルート投稿を対象に行われ、そのentryの`source`はクライアントが明示的に指定したルート投稿自身になる。サブスレッド（FR-1により非表示）の投稿はTimelineから事後entry作成の対象にできないため、本FRが扱う削除対象がサブスレッド側の投稿を含むことはない。
- 「リンク・Bluesky投稿を削除」（スレッド全体ではなく、ルート投稿の元Bluesky投稿のみを削除する操作）を実行した場合も、削除成功後はそのスレッドグループ全体がTimeline一覧から除去される（NFR-5参照。ルート投稿が失われた時点で、そのスレッドグループの表示単位としての一貫性が失われるため）。

## 4. 非機能要件

### NFR-1: 既存の単発投稿表示への影響最小化

- スレッドグループ化の対象外となる単独投稿の表示・機能（entry表示・編集・削除ボタン等の`PostCardEntryActions`の挙動）は、本機能追加によって変化しないこと。

### NFR-2: ページング方式への影響最小化

- `GET /v2/entries`の1ページあたりの取得件数・カーソルベースのページング方式自体は変更しない。スレッドのグルーピングの結果、1ページの表示上のグループ件数は取得した投稿件数以下になりうる。

### NFR-3: スレッドの完全性（取得元データの欠落への耐性）

- 一覧データの取得元（Bluesky AppViewの`getAuthorFeed`）は、自分自身のスレッドを構成する投稿の一部（プロトコルルート以外の任意の位置・任意の件数）を一覧レスポンスから欠落させる場合がある（既知のAppView側の挙動、原因不明、skyshareの実装に起因しない）。
- `GET /v2/entries`は、このような欠落が発生した場合でも、スレッドのプロトコルルート投稿を取得できている限り、欠落した投稿を別途取得して補い、メインスレッドを完全な形でレスポンスに含めること。
- 上記の判定・補完は、フロントエンドが一覧データから間接的に推測するのではなく、`GET /v2/entries`のレスポンス自体が確定済みのスレッド構造として返すことで担保する（NFR-4参照）。

### NFR-4: スレッド構造判定の責務所在

- どの投稿とどの投稿が同一スレッドを構成するか（グルーピング・メインスレッドの選出・他者起点スレッドの除外）の判定は、`GET /v2/entries`のレスポンス時点でバックエンドが確定させる。フロントエンドは、取得したデータから独自にreply chainを再構築する処理を行わない。
- この方針は、スレッド判定ロジックが単一の実装（バックエンド）に一本化されることで、フロントエンド側での再構築ロジックに起因する不整合（取得元データの欠落を誤って解釈する、判定条件がフロントエンド・バックエンドで食い違う等）を構造的に排除することを目的とする。
- この方針は「どの投稿がどのスレッドグループに属するか」という表示用の構造判定に限定される。entryを作成してよいか・どの投稿をsourceに指定するかという判断（FR-3）はクライアントの責務であり、サーバはこれを検証しない（[specs/entry/backend/requirements.md](../entry/backend/requirements.md)）。両者は別の関心事であり、後者をサーバに持たせない設計が、将来クライアント側でentry作成の挙動を拡張する際の自由度を確保する。

### NFR-5: 削除操作後の表示の一貫性

- スレッドグループのルート投稿に対する削除操作（「リンク・Bluesky投稿を削除」「リンク・スレッド全体を削除」のいずれか）が成功した場合、そのスレッドグループ全体を表示上の単位としてTimeline一覧から除去する。
- 上記のうち「リンク・Bluesky投稿を削除」（スレッド全体の削除ではない）を実行した場合、Bluesky上には後続投稿がなお存在しうるが、それらは次回の一覧再取得時に、新たな独立したスレッドグループとして改めて表示される（現在表示中のページを都度再構成することはしない）。

## 5. 受け入れ条件（Acceptance Criteria）

- [ ] 3件の投稿から成る自分起点スレッドを投稿すると、Timeline一覧上でそれらが1つのスレッドグループとして折りたたみ表示される
- [ ] 折りたたみ表示を展開すると、3件の投稿が時系列順（古い→新しい）にすべて表示される
- [ ] スレッドに関係しない単独投稿は、従来通り1件ずつ個別の投稿カードとして表示される
- [ ] 他人の投稿への返信は、それが自分自身の投稿のみで構成される後続の返信列を持っていても、Timeline一覧に一切表示されない（返信単体としても、独立したスレッドグループとしても表示されない）
- [ ] ルート投稿自身が画像を持ち、既にentryを持たないスレッドでは、ルート投稿に「entryを作成」ボタンが表示される
- [ ] ルート投稿が画像を持たないが、中間投稿（replies）のいずれかが画像を持つスレッドでは、ルート投稿のカードに「entryを作成」ボタンが表示される（中間投稿のカードには表示されない）。Visualはルートに最も近い画像投稿から生成される
- [ ] ルート・repliesのいずれも画像を持たないスレッドでは、「entryを作成」ボタンはどの投稿にも表示されない
- [ ] ルート投稿自身に既にskyshare entryが存在する場合、「entryを作成」ボタンは表示されない
- [ ] スレッド内の後続投稿（replies）のいずれかに既にskyshare entryが存在するが、ルート投稿自身にはentryが存在しない場合（本機能の実装前に中間投稿へentryが作成されていたケースを含む）、ルート投稿が画像を持てば「entryを作成」ボタンは表示される
- [ ] 事後entry作成ボタンを押下すると、`source`としてルート投稿のuriがAPIへ明示的に送信され、作成されたentryの`source`がルート投稿になる（Visual生成元がreplyであっても`source`はルート投稿のまま）
- [ ] スレッド由来（ルート投稿にentryが紐づき、後続投稿が実在する）entryは、一覧上でスレッド由来であることが視覚的に区別できる
- [ ] 単独投稿由来のentryには、スレッド由来を示す視覚的区別が表示されない
- [ ] 既存の単独投稿の表示・entry作成/編集/削除ボタンの挙動に regression が無い
- [ ] entryが紐づくスレッドルート投稿の削除ボタンから、後続の自己投稿が実在する場合のみ「リンク・スレッド全体を削除」の選択肢が確認ダイアログに表示される
- [ ] 「リンク・スレッド全体を削除」を実行すると、そのスレッドグループの投稿すべてがTimeline一覧から除去される
- [ ] 後続の自己投稿が存在しない単独投稿・スレッドでは、「リンク・スレッド全体を削除」の選択肢が表示されない
- [ ] スレッドを構成する投稿の一部（root以外の任意件数）がBluesky AppView側の都合で`getAuthorFeed`から欠落している場合でも、root投稿が取得できている限り、`GET /v2/entries`が欠落投稿をすべて補完し、そのスレッドを構成する投稿すべてが1つのスレッドグループとして折りたたみ表示される
- [ ] スレッドルート投稿の「リンク・Bluesky投稿を削除」（スレッド全体削除ではない）を実行すると、後続投稿を含むそのスレッドグループ全体がTimeline一覧から除去される（NFR-5）
