# Timeline コンポーネント 要件定義書

## 1. 背景・スコープ

- Timeline（`src/components/post/Timeline`、`/`ページに表示される自分の投稿一覧）は、`GET /v2/entries`（`app.bsky.feed.getAuthorFeed`ベース）で取得した自分の投稿を新しい順に一覧表示する。
- スレッド投稿機能（[specs/threadpost](../threadpost/requirements.md)）により、複数のBluesky投稿が1回のリクエストでスレッド（reply chain）として作成できるようになったことに伴い、Timeline一覧上でスレッドをどう表示するか、投稿時にskyshare entryを作らなかった画像投稿に対して事後的にentryを作成する導線をどう提供するかを本書で定める。
- 本書の対象は、Timeline一覧（`/`ページ）のみである。投稿フォーム自体（`ThreadComposer`）は[specs/threadpost](../threadpost/requirements.md)、entry詳細ページ（`entries/[slug].astro`）は[specs/entry/frontend](../entry/frontend/requirements.md)が対象とし、本書では扱わない。

## 2. 用語定義

| 用語             | 意味                                                                                                                                |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| スレッドグループ | Timeline一覧上で、reply chainにより連結された自分自身の投稿群をまとめた単位。1件のみの投稿も、要素数1のスレッドグループとして扱う。 |
| ルート投稿       | スレッドグループのうち、時系列上最も古い（reply chainの起点となる）投稿。                                                           |
| 事後entry作成    | 投稿時にはskyshare entryを作成しなかった画像投稿に対して、後からentryを発行する機能（既存のfrom-post機能をTimeline上で使う導線）。  |

## 3. 機能要件

### FR-1: スレッドのグルーピング表示

- Timeline一覧は、取得した自分の投稿一覧のうち、reply chainで連結された投稿群を1つのスレッドグループとしてまとめて表示する。
- ある投稿の返信先（`reply.parent`）が、一覧内で直前（時系列的に1つ新しい側）に位置する自分自身の投稿と一致する場合に、両者を同じスレッドグループに含める。時系列上で無関係な投稿が間に挟まる場合、またはページング境界をまたいで返信先が取得済み一覧に含まれない場合は、グルーピングを行わず独立した投稿として表示する（無理に遡って取得することはしない）。

### FR-2: スレッド展開表示

- 2件以上の投稿から成るスレッドグループは、既定で折りたたみ表示（ルート投稿のみを表示し、後続投稿の件数を示す）とする。
- ユーザーが折りたたみ表示を操作すると、グループ内の全投稿が時系列順（古い→新しい）に展開表示される。
- 1件のみのスレッドグループ（reply chainを持たない単独投稿）は、従来通り単一の投稿カードとして表示する（折りたたみ表示にはしない）。

### FR-3: 事後entry作成（スレッド中間の画像投稿向け）

- 次の条件をすべて満たすスレッドグループについて、対象投稿に「entryを作成」ボタンを表示する。
  1. スレッドグループが2件以上の投稿から成る。
  2. グループ内のいずれの投稿にも、既にskyshare entryが紐づいていない。
  3. ルート投稿が画像を持たない。
  4. ルート投稿以外のいずれかの投稿が画像を持つ。
- 条件4に該当する投稿が複数ある場合、時系列上最も古いものにのみボタンを表示する。
- ボタン押下により、対象投稿を指定した事後entry作成（既存のfrom-post機能）を実行する。作成されるentryの`source`はバックエンドが自動的にスレッド先頭（ルート投稿）に解決する（[specs/entry/backend/requirements.md FR-2](../entry/backend/requirements.md#2-機能要件)）。
- ルート投稿自身が画像を持つ場合、このボタンは対象外とする（通常の投稿フローで既にentry作成の機会が提供されているため。[specs/entry/frontend/requirements.md FR-1〜FR-3](../entry/frontend/requirements.md#3-機能要件)）。
- スレッドグループ内のいずれかの投稿に既にskyshare entryが存在する場合、このボタンはどの投稿にも表示しない（1スレッドにつきentryは最大1件という制約を一覧上でも維持する）。

### FR-4: スレッド由来entryの視覚的区別（一覧）

- スレッドグループのルート投稿にskyshare entryが紐づいており、かつグループ内に実際に後続投稿が存在する場合、一覧上でそのentryがスレッド由来であることを視覚的に区別できるようにする。
- 単独投稿（reply chainを持たない）由来のentryには、この区別表示を行わない。

## 4. 非機能要件

### NFR-1: 既存の単発投稿表示への影響最小化

- スレッドグループ化の対象外となる単独投稿の表示・機能（entry表示・編集・削除ボタン等の`PostCardEntryActions`の挙動）は、本機能追加によって変化しないこと。

### NFR-2: ページング方式への影響最小化

- スレッドのグルーピングはクライアント側（取得済みの一覧データに対して）で行い、`GET /v2/entries`の1ページあたりの取得件数・カーソルベースのページング方式自体は変更しない。グルーピングの結果、1ページの表示上のグループ件数は取得した投稿件数以下になりうる。

### NFR-3: reply chain情報の取得

- スレッドのグルーピング（FR-1）を行うには、各投稿の返信先（`reply.parent`のuri）が一覧取得時点で判明している必要がある。`GET /v2/entries`のレスポンスに、この情報を含める（詳細は[design.md](design.md)）。

## 5. 受け入れ条件（Acceptance Criteria）

- [ ] 3件のセグメントから成るスレッドを投稿すると、Timeline一覧上でそれらが1つのスレッドグループとして折りたたみ表示される
- [ ] 折りたたみ表示を展開すると、3件の投稿が時系列順（古い→新しい）にすべて表示される
- [ ] スレッドに関係しない単独投稿は、従来通り1件ずつ個別の投稿カードとして表示される
- [ ] ルート投稿が画像を持たず、既にentryを持たないスレッドの中間投稿に画像がある場合、その投稿に「entryを作成」ボタンが表示される
- [ ] 上記条件でルート投稿以外に画像投稿が複数ある場合、最も古いものにのみボタンが表示される
- [ ] スレッド内のいずれかの投稿に既にskyshare entryが存在する場合、他の画像投稿に「entryを作成」ボタンは表示されない
- [ ] ルート投稿自身が画像を持つスレッドでは、本ボタンは表示されない
- [ ] 事後entry作成ボタンを押下すると、対象投稿を指定してentryが作成され、そのentryの`source`はスレッド先頭投稿になる
- [ ] スレッド由来（ルート投稿にentryが紐づき、後続投稿が実在する）entryは、一覧上でスレッド由来であることが視覚的に区別できる
- [ ] 単独投稿由来のentryには、スレッド由来を示す視覚的区別が表示されない
- [ ] 既存の単独投稿の表示・entry作成/編集/削除ボタンの挙動に regression が無い
