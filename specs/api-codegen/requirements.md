# APIスキーマとクライアントの生成 要件定義書

## 1. 目的

APIの入出力の定義を1か所に保ち、そこからOpenAPIのドキュメントとフロントエンド用のクライアントを生成して、サーバーとクライアントの食い違いを防ぐ。

## 2. スコープ

### 2.1 対象

- APIのスキーマの登録と、OpenAPIドキュメントの組み立て。
- 生成したクライアントが通信に使う取得処理とフォームデータの組み立て。
- サーバー側でのフォームデータの復元と、リクエストの補助処理。

### 2.2 対象外

- 個々のAPIのスキーマの内容。
- 生成されたクライアントのコードそのもの。

## 3. 前提

- なし

## 4. 機能要件

- FR-1: OpenAPI 3.1のドキュメントは、登録したすべてのAPIのパスを含めて、スキーマから組み立てる。
- FR-2: 登録するAPIのパスは末尾をスラッシュにし、各操作に識別子を持たせる。
- FR-3: クライアントの取得処理は、抽出APIのパスを抽出サービスのURLへ、旧ページのパスを旧バックエンドのURLへ書き換え、パスの末尾のスラッシュを外す。
- FR-4: クライアントの取得処理は、応答の本文が空でもJSONでなくても例外にせず、本文をデータとして返す。
- FR-5: クライアントの取得処理は、画像のAPIの応答をJSONにせずBlobのまま返す。
- FR-6: クライアントのフォームデータの組み立ては、文字列のフィールドをJSON文字列にし、Blobはそのまま積み、配列は複数のフィールドへ展開し、投稿の配列は添字付きのフィールド名へ展開する。
- FR-7: サーバーのフォームデータの復元は、フィールドの種別の宣言に従って、添字付きのフィールドから複数件のオブジェクトを復元し、JSONの解釈に失敗した値は生の値のまま残す。
- FR-8: 取得件数の指定は、1から100の整数だけを受け付け、範囲外や整数でない値は不正として判定する。
- FR-9: リクエストについて、cookieヘッダの有無と、フォームデータで送られたかを判定できる。

## 5. 非機能要件

- なし

## 6. 受け入れ条件

- AC-1 (FR-1): OpenAPI 3.1のドキュメントに、登録したすべてのパスが含まれる。
- AC-2 (FR-2): 登録したパスがすべて末尾スラッシュで、各操作に識別子がある。
- AC-3 (FR-3): 抽出APIのパスが抽出サービスのURLへ書き換えられ、末尾のスラッシュが外れる。
- AC-4 (FR-3): 旧ページのパスが旧バックエンドのURLへ書き換えられる。
- AC-5 (FR-4): 応答の本文が空のときも、JSONでないときも、例外にならずデータへ格納される。
- AC-6 (FR-5): 画像のAPIの応答が、Blobのまま返る。
- AC-7 (FR-6): 文字列のフィールドがJSON文字列にして積まれる。
- AC-8 (FR-6): Blobの配列が複数のフィールドへ展開される。
- AC-9 (FR-6): 投稿の配列が添字付きのフィールド名へ展開される。
- AC-10 (FR-7): 添字付きのフィールドから、複数件のオブジェクトの配列が復元される。
- AC-11 (FR-7): JSONの解釈に失敗した値が、生の値のまま残る。
- AC-12 (FR-8): 1から100の整数が、そのまま数値として返る。
- AC-13 (FR-8): 範囲外と整数でない値が、不正として判定される。
- AC-14 (FR-9): cookieヘッダがあるリクエストが、あると判定される。
- AC-15 (FR-9): フォームデータの内容種別が、フォームデータと判定される。
