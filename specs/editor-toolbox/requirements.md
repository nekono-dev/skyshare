# EditorToolbox 要件定義書

## 1. 背景・目的

クリエイターモード（[`specs/creator-mode`](../creator-mode/requirements.md)）では、投稿本文編集エリアに対して複数のリッチ編集機能（URLリンク設定・カスタムパラメータ付与・YayText変換・skyshare entry詳細設定）を追加する。これらは個別に浮動UI（ポップオーバー・ダイアログ）を実装するのではなく、Markdownエディタのツールバーに類似した「ボタン列＋クリックで展開する内容」という単一のUIパターンに載せることで、見た目・操作感の統一と、将来の機能追加・既存PostFormへの逆輸入を容易にする。

本要件定義書は、そのUIパターンを担う**独立した共通コンポーネント `EditorToolbox`** について定義する。EditorToolbox自体はクリエイターモード固有の知識を一切持たない、汎用的な「ボタン列＋パネル開閉制御」コンポーネントとして設計・実装し、クリエイターモードはこれを利用する側（クライアント）の1つと位置づける。

**本コンポーネントはクリエイターモードの実装に先行して（または並行して独立に）実装されることを前提とする。** クリエイターモードの要件定義書・設計書・タスク一覧は、本コンポーネントが実装済みであることを前提とした記述になっている。

## 2. 用語定義

| 用語 | 意味 |
| --- | --- |
| ツール | EditorToolboxに登録される1つのボタン単位。押下時の挙動によって「パネル型」と「即時実行型」の2種類がある。 |
| パネル型ツール | ボタン押下で追加のUI（入力フォーム等）を展開するツール（例: URL入力）。 |
| 即時実行型ツール | ボタン押下で追加UIを展開せず、その場で処理を実行する、またはON/OFF状態をトグルするツール（例: Markdownエディタの太字ボタン）。 |
| ホスト側 | EditorToolboxを呼び出し、`tools` 配列を組み立てる側のコンポーネント（クリエイターモードのフォーム、将来的には通常のPostForm等）。 |
| `FloatingBox` | 既存の共通コンポーネント（`src/components/common/FloatingBox`）。アンカー追従型のフローティングコンテナで、`document.body` へのポータル描画・ビューポート内クランプ・スクロール/リサイズ時の自動消去を提供する。 |

## 3. スコープ

### 3.1 対象

- `EditorToolbox` 共通コンポーネント本体（`src/components/common/EditorToolbox/`）の新規実装。
- ツール定義の型（`EditorToolboxTool`、パネル型/即時実行型の2種）の定義。
- ボタン列の表示、折り返しレイアウト、パネルの開閉制御、パネル位置決め、アクセシビリティ（キーボード操作・ARIA属性）。

### 3.2 対象外

- 個々のツールの中身（URL入力パネル、YayText変換パネル等）の実装。これらはEditorToolboxを利用する各機能（クリエイターモードのFR1〜FR4等）の責務であり、`specs/creator-mode` 側のスコープとする。
- テキスト選択範囲の取得・本文編集ロジックとの連携。EditorToolboxはテキストエディタの内部状態を一切関知しない（後述4節参照）。
- 既存PostFormへの実際の組み込み作業（EditorToolboxを使えるようにする準備までを本スコープとし、実際にPostFormへ組み込む作業は`specs/creator-mode`のPhase 8（将来対応）で扱う）。

## 4. 決定事項（ヒアリング結果）

ユーザーへのヒアリングにより、以下を設計上の前提として確定する。

| 項目 | 決定内容 |
| --- | --- |
| ツールの種類 | パネル型（ボタン押下でUIを展開）と即時実行型（ボタン押下でその場で処理実行、またはON/OFFトグル）の両方を第一級（`EditorToolboxTool`のunion型）としてサポートする。 |
| テキスト選択範囲との関与 | EditorToolboxは本文編集領域の選択範囲を一切検知・保持しない。選択範囲の取得・利用は各ツール定義側（ホスト側が組み立てるツールのロジック）の責務とする。EditorToolboxは「ボタン列＋パネル開閉」にのみ徹する、完全に汎用的なコンポーネントとする。 |
| ツール数が多い場合の表示 | 折り返し（複数行表示）を既定の挙動とする。横スクロールや「もっと見る」オーバーフローメニューは採用しない。 |

## 5. 前提条件・現状整理

- 本アプリはCloudflare Workers上で動作するため、Node.js固有APIは使用不可。フロントエンドコンポーネントとしての制約はこれに影響されない（ブラウザ実行のため）。
- 既存の共通コンポーネント `FloatingBox`（`src/components/common/FloatingBox`）が、アンカー位置追従・`document.body`へのポータル描画・ビューポート内クランプ・スクロールやリサイズでの自動消去（`onDismiss`）をすでに提供しており、`src/components/post/SuggestPopover`（メンション/ハッシュタグ候補ポップアップ）がこれを実際に利用している。EditorToolboxのパネル表示は、この既存コンポーネントを流用することで、位置計算・ポータル管理のロジックを重複実装しない方針とする。
- 既存の共通コンポーネント `Overlay`（`src/components/common/Overlay`）は全画面モーダル用であり、本コンポーネントの「ボタン直下に小さく展開するパネル」という用途には適合しないため流用しない（背景クリック閉じ等の実装パターンのみ参考にする）。
- 現在の自動テスト基盤（`vitest.config.ts`）は `environment: "node"` のみで構成されており、React コンポーネントを実際にDOMへレンダリングして検証する仕組み（`@testing-library/react`等）は導入されていない。既存のコンポーネント内ロジックのテスト（例: `src/components/PostForm/shareTogglesReducer.ts`）は、状態遷移ロジックをReactに依存しない純粋関数（reducer）として切り出し、その部分だけをNode環境で単体テストするパターンを採っている。EditorToolboxもこのパターンを踏襲する（詳細は設計書で扱う）。

## 6. 機能要件

### FR1. ツールボタン列の表示

- ホスト側から渡された `tools` 配列の順序通りに、ボタンを横並びで表示する。
- 各ボタンはラベル・アイコン（任意）を表示する。
- `disabled` が指定されたツールはボタンを操作不可にする。
- ツール数が多くボタン列がコンテナ幅を超える場合は、複数行に折り返す。

**受け入れ条件**:
- 4〜8個程度のツールを登録した状態で、狭い画面幅でも折り返し表示され、ボタンが画面外にはみ出さない。

### FR2. パネル型ツール

- パネル型ツール（`kind: "panel"`）のボタンを押下すると、そのツールの `renderPanel` が返すUIを、ボタンの直下にフローティング表示する。
- 同時に開けるパネルは1つとする。あるパネルが開いている状態で別のパネル型ツールのボタンを押すと、開いていたパネルを閉じてから新しいパネルを開く。
- 開いているパネルと同じボタンを再度押すと、パネルを閉じる。
- パネル外側のクリック、Escapeキー押下、スクロール/ウィンドウリサイズ（`FloatingBox`の既定挙動）でパネルを閉じる。
- パネル内の `close()` 呼び出し（ツール側から提供）でも明示的に閉じられる。

**受け入れ条件**:
- パネルを開いた状態で別のツールボタンを押すと、前のパネルが閉じて新しいパネルが開く。
- パネル外側をクリック、またはEscapeキーを押すとパネルが閉じる。

### FR3. 即時実行型ツール

- 即時実行型ツール（`kind: "action"`）のボタンを押下すると、パネルを展開せずに `onClick` を呼び出す。
- `isActive` が指定された即時実行型ツールは、トグルボタンとしての見た目（押下状態の表示、`aria-pressed`）を持つ。

**受け入れ条件**:
- 即時実行型ツールのボタンを押すと、パネルが一切表示されずに指定した処理が実行される。
- `isActive: true` のツールはボタンが押下状態の見た目になる。

### FR4. アクセシビリティ・キーボード操作

- ボタン列全体を `role="toolbar"` とする。
- 矢印キー（左右、および複数行に折り返した場合は上下も検討）でボタン間のフォーカス移動ができる（roving tabindexパターン）。
- Enter/Spaceキーでフォーカス中のボタンを活性化できる（クリックと同じ挙動）。
- パネルを閉じたとき、フォーカスをそのパネルを開いたボタンへ戻す。

**受け入れ条件**:
- キーボードのみでツールボックスの全ボタンへ到達・操作できる。
- スクリーンリーダーでボタンの状態（押下中/無効）が読み上げられる。

### FR5. 汎用性・疎結合性

- EditorToolboxは `tools: EditorToolboxTool[]` というプリミティブな入力のみに依存し、特定の機能（URLリンク設定等）や特定のホストコンポーネント（PostForm、CreatorPostForm等）の内部実装・状態型を一切知らない。
- 新しいツールを追加する際、EditorToolbox自体のコード変更を必要としない。

**受け入れ条件**:
- クリエイターモード側でツールを追加・削除する変更が、EditorToolboxのコードに一切変更を要求しないこと（`tools` 配列の組み立て側だけの変更で完結すること）。

## 7. 非機能要件

- **既存コンポーネントの再利用**: パネルのフローティング表示は既存の `FloatingBox` を流用し、位置計算・ポータル管理ロジックを独自に再実装しない。
- **テスト**: 開閉状態の管理・どのパネルが開くべきかの判定など、Reactに依存しない状態遷移ロジックは純粋関数（reducer）として切り出し、`tests/` 配下にNode環境での単体テストを追加する。DOM描画やキーボード操作そのものの自動テストは、現状のテスト基盤では対応しないため手動確認とする。
- **後方互換性**: 本コンポーネントは新規実装のため既存動作への影響はない。ただし、依存する `FloatingBox` の既存挙動（`SuggestPopover`での利用）に影響を与えないこと。

## 8. 未決事項・リスク

- 複数行に折り返した場合の上下矢印キーでのフォーカス移動（グリッド的なナビゲーション）は実装コストとUXの兼ね合いで、実装時に簡略化する可能性がある（左右矢印キーのみで折り返しをまたいで移動する実装でも要件は満たせる）。設計書で方針を確定する。
- `FloatingBox` は現在 `SuggestPopover` 専用に近い形で使われているが、EditorToolboxからも利用することで、意図しない挙動干渉がないか（同一画面内で両方が同時に開き得るか等）は実装時に確認する。
