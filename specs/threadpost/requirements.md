# スレッド投稿機能 要件定義書

## 1. 背景・目的

Blueskyのスレッド（reply chain）形式で、複数の投稿をあらかじめ作成しておき、順に投稿していく「スレッド投稿機能」を提供する。

バックエンド（skyshareサーバサイド）のAPI仕様（`POST /v2/entry`でのreply対応・複数投稿の原子的作成・所有権検証等）と、下書き（drafts）がスレッド（複数投稿）を表現できるデータ構造・APIは、[`specs/entry/backend`](../entry/backend/requirements.md)が既に定義している。本書はそれを前提として、フロントエンドのUI・アーキテクチャの要件を定義する（詳細は[`design.md`](./design.md)参照）。

## 2. 用語定義

| 用語           | 意味                                                                                                  |
| -------------- | ----------------------------------------------------------------------------------------------------- |
| PostForm       | 既存の投稿フォーム本体（`src/components/post/PostForm`）。                                            |
| skyshare entry | `dev.nekono.skyshare.entry` レコード。画像投稿に付随するheading/caption/cover画像などのマニフェスト。 |
| record         | `app.bsky.feed.post` のレコード本体（Bluesky投稿そのもの）。                                          |
| reply chain    | `app.bsky.feed.post#replyRef`（`root`/`parent`のStrongRef）によるBluesky公式のスレッド接続の仕組み。  |
| セグメント     | スレッド投稿における個々の投稿単位（1スレッド内の1投稿）。                                            |
| StrongRef      | `com.atproto.repo.strongRef`相当。レコードを一意に指す`{ uri, cid }`の組。                            |

## 3. スコープ

### 3.1 対象

- スレッド投稿を実現するためのバックエンドAPI（`POST /v2/entry`。複数投稿の原子的作成、`reply`によるスレッド接続、所有権検証）。
- 下書き（`POST /v2/bsky/drafts` 等）が複数投稿（スレッド）を保持できるデータ構造。
- スレッド投稿のフロントエンドUI・UX要件、および送信方式・下書き連携・画像付きセグメントの扱い・クリエイターモードとの関係性を含むアーキテクチャ方針（具体的な実現方式は[design.md](./design.md)が定める）。

### 3.2 対象外（本書では扱わない）

- クリエイターモード自体（EditorToolbox、FR1〜FR4: 手動リンクfacet・カスタムパラメータ・YayText変換・entry manifest任意設定）。スレッド投稿はクリエイターモードとは独立した機能として実装し、EditorToolboxの機能とは統合しない（引き続き [`specs/creator-mode`](../creator-mode/requirements.md) の範囲）。
- Bluesky公式クライアント・他社クライアントとの相互運用性検証。
- クロスポスト先（Taittsuu/Mastodon/X）側でのスレッド表現の高度化（既存のインテント連携の範囲を超えない）。

## 4. 前提条件・現状整理

- 本アプリはCloudflare Workers上で動作するため、Node.js固有APIは使用不可。
- APIはコードファースト（`src/lib/api/schema/**` のスキーマ定義が単一の真実の源）。
- `POST /v2/bsky/record`（skyshare entryを伴わない投稿専用エンドポイント）は`POST /v2/entry`に統合され、廃止された。テキストのみ投稿・OGPリンク投稿・画像投稿（skyshare entryあり/なし）は、いずれも`POST /v2/entry`の`posts`配列で扱う。
- `POST /v2/entry`は、`posts`配列に複数件を渡すことで、Blueskyのスレッド（reply chain）を1回のトランザクションとして原子的に作成できる（詳細はdesign.md参照）。
- 下書き（`app.bsky.draft.*`）は複数投稿（`posts`配列）を保持できる構造になっている（詳細はdesign.md参照）。

## 5. 決定事項（creator-mode要件定義時のヒアリング結果のうち、スレッド投稿に関わるもの）

| 項目                    | 決定内容                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| セグメントの機能範囲    | 2投稿目以降（リプライ投稿）も1投稿目と全く同じフル機能（画像・OGP・返信/引用設定・自己ラベル等）を使える。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| 各セグメントのentry作成 | entry作成はリクエスト全体（スレッド）につき最大1件であり、`posts[i]`ごとの個別指定はできない（トップレベルの`createEntry`+`visual`のみで指定する）。画像投稿segmentが1件ならそのsegmentの画像がvisual元になる。2件以上ある場合は、そのうち先頭のsegmentの画像が自動的にvisual元として選ばれる。entryの`source`は常にバックエンドが自動解決し（スレッドでは常にスレッド先頭投稿を指す）、クライアントが選択する手段はない（詳細は[specs/entry/backend/design.md §7](../entry/backend/design.md#7-sourceの解決ロジック)・[specs/entry/frontend/requirements.md FR-1〜FR-3](../entry/frontend/requirements.md#3-機能要件)参照）。 |
| 利用対象ユーザー        | ログイン済みの全ユーザーが利用可能（opt-in設定は設けない）。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

上記はクリエイターモードのヒアリングで確定した事項をそのまま踏襲する。加えて、フロントエンドのアーキテクチャに関わる以下の方針を確定する。

| 項目                       | 決定内容                                                                                                                                                      |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 起動導線                   | 専用画面は設けず、既存の投稿フォーム（`PostForm`）を拡張する形で提供する（「スレッドに追加」導線から同一フォーム内にセグメントを追加していく）。              |
| 送信方式                   | スレッド全体を1回の`POST /v2/entry`リクエスト（`posts`配列）にまとめて送信する（バックエンドの原子的作成をそのまま活用し、部分成功状態を発生させない）。      |
| クリエイターモードとの関係 | クリエイターモード（EditorToolbox）とは独立した機能として実装する。                                                                                           |
| 下書きとの連携             | スレッド全体を1つの下書き（`posts`配列）として保存・復元する。セグメント単位の個別下書きは提供しない。                                                        |
| 画像付きセグメントの扱い   | 各セグメントの画像は、既存の単発投稿向け画像圧縮・OGP画像合成パイプラインをセグメントごとに独立して適用する。スレッド全体をまとめて処理する仕組みは設けない。 |

具体的な実現方式（コンポーネント構成・状態管理等）は[design.md](./design.md)が定める。

## 6. 機能要件

### 6.1 FR-THREAD-BE. バックエンド: 投稿作成API（reply・原子的な複数投稿作成）

**概要**: `POST /v2/entry`が、1件の投稿（テキストのみ/OGPリンク/画像付き）、または`posts`配列による複数投稿（スレッド）を原子的に作成する。skyshare entry作成有無は、リクエスト全体につき1回だけトップレベルの`createEntry`+`visual`で指定する（`posts[i]`ごとの個別指定はできない）。トップレベルの`reply`（`{ root: {uri, cid}, parent: {uri, cid} }`）により、既存のスレッドへ継ぎ足すことができる。

**詳細要求**:

- `posts`は1〜100件の配列。各要素は`text`/`facets`/`ogImage`/`ogMeta`/`images`/`imagesMeta`/`langs`/`selfLabels`/`gate`を持つ。
- トップレベルの`createEntry: true`は、`posts`に画像投稿（`images`を持つ要素）が1件以上含まれ、かつ`visual`が指定されている場合のみ有効。いずれか欠けている場合は400を返す。
- `reply`はStrongRef（`{uri, cid}`）の`root`/`parent`から成る任意フィールドで、`posts`と同階層に1つだけ持つ。`reply.root`/`reply.parent`のuriは、呼び出しユーザー自身の`app.bsky.feed.post`レコードを指している必要がある。他人の投稿への不正なreply chain構築を防ぐため、サーバ側でDID一致を検証し、不一致時は400を返す。
- `posts`が2件以上の場合、2件目以降のreply chain（root/parent）はサーバが内部で自動的に組み立てる（クライアントが個別に指定する必要はない）。
- 投稿本体・threadgate/postgate・skyshare entryは原子的に作成され、いずれかが失敗した場合はリクエスト全体が失敗し、投稿は一切作成されない（部分成功状態は存在しない）。

**受け入れ条件**:

- `posts`に複数件を指定して投稿すると、Bluesky上で正しくスレッド（リプライチェーン）として表示される。
- トップレベルの`reply`を指定して投稿すると、既存の投稿へ正しく接続される。`reply.root`/`reply.parent`のいずれかが自分以外の投稿を指す場合、400エラーになり投稿が作成されない。
- gate（threadgate/postgate）の作成に失敗した場合、投稿自体も含めてリクエスト全体が失敗する（500）。

### 6.2 FR-THREAD-DRAFT. バックエンド: スレッド下書き対応

**概要**: 下書き（`app.bsky.draft.*`）が、1投稿だけでなく複数投稿（スレッド予定）を保持できるようにする。

**詳細要求**:

- 下書きの本体を「1件のtext」から「`posts`（1〜100件の`{text, labels?}`）配列」へ変更する。
- `posts`が1件ならテキストのみの下書き、複数件ならスレッド（reply chain予定）の下書きとして扱う。
- 画像等の埋め込みはデバイスローカル参照のため下書きには含めない（既存方針を踏襲）。

**受け入れ条件**:

- 複数セグメント分のtext/labelsをまとめて1つの下書きとして作成・更新・一覧取得・削除できる。

### 6.3 FR-THREAD-FE. フロントエンド: スレッド投稿UI

以下は[`specs/creator-mode/requirements.md`](../creator-mode/requirements.md)のFR5に記載されていた要件レベルの記述を引き継いだ機能要件に加え、投稿フォームの見た目・操作性に関する要件を確定する。**具体的なコンポーネント構成・状態管理方式・API呼び出しタイミングはdesign.mdで定める**（本節はそれらの実現方式を規定しない）。

**機能要件**:

- スレッドに追加する導線を設け、投稿フォームを複数（セグメント）並べられるようにする。各セグメントは1投稿目（PostForm相当のフル機能）と同一の機能を持つ。
- セグメントは追加・削除ができる。
- 投稿順序が保たれること（バックエンドAPI自体が`posts`配列の順序通りにreply chainを組み立てるため、UI上も入力順＝投稿順になるようにする）。
- スレッド全体を1回のAPI呼び出し（`posts`配列）にまとめて送信する（5節の決定事項）。送信結果は「送信中」「成功」「失敗」の状態のみを扱い、セグメントごとの個別進捗表示は行わない（バックエンドが全件成功/全件失敗を保証するため）。
- 画像投稿segmentがあれば、`createEntry`フラグによりskyshare entryが作成される（スレッドにつき最大1件、5節の決定事項）。entry作成対象の選択方針（visual元segmentの選び方・entryの`source`解決）は[specs/entry/frontend/requirements.md](../entry/frontend/requirements.md)が定める。
- 下書き（6.2）との連携: スレッド全体を1つの下書き（`posts`配列）として保存・復元する（5節の決定事項）。

**見た目・操作性の要件（Bluesky公式クライアント準拠）**:

- 投稿フォームは、Bluesky公式クライアントのスレッド作成UIと同様に、全segmentを1つのフォーム内に縦に並べて表示する（segmentごとに別ウィンドウ・別ページを開く方式にはしない）。
- 各segmentの左側にはユーザーのアバターを表示する。後続segmentが存在する場合、アバター間を縦線で接続し、スレッドとしての連続性を視覚的に示す。
- ユーザーは、スレッド中の任意のsegment（先頭・中間・末尾を問わない）を選択して編集できる。特定のsegment（例: 末尾）しか編集できない制約は設けない。
- 現在編集中でないsegmentは、内容を簡略化した上でグレーアウト表示し、編集中のsegmentと視覚的に区別する。これにより、ユーザーは編集中のsegmentがスレッド全体の中でどの位置にあり、後続にどのようなsegmentが控えているかを一目で把握できる。画像が添付されたsegmentの場合、編集中でなくても添付済みであることが分かるよう、読み取り専用のサムネイルプレビューを表示する（実装時に確定。画像添付状態が編集中の切り替えで見えなくなるのはユーザーの実際の混乱を招いたため）。
- 編集中のsegmentの直下には、画像添付・GIF・絵文字・追加(+)・言語選択・文字数カウンターなど、既存の単発投稿用`PostForm`と同等の入力補助UIを表示する。編集中でないsegmentにはこれらの入力補助UIを表示しない。
- 編集中でないsegmentのうち、削除可能なもの（削除ルール上segment自体を削除できるもの）には削除ボタンを表示する。削除ルール（実装時に確定）: 先頭（1件目）segmentはスレッドの起点のため削除できない。2件目以降は編集中かどうかに関わらずいつでも削除できる。
- フォーム上部には、既存の単発投稿と同様に「キャンセル」「下書き」「投稿（すべてポスト）」の操作を配置する。

**受け入れ条件**:

- [x] スレッド投稿フォームで、複数segmentが1つのフォーム内に縦に並んで表示される
- [x] 各segmentのアバター間が縦線で接続され、スレッドであることが視覚的にわかる
- [x] 先頭・中間・末尾を問わず、任意のsegmentを選択して編集できる
- [x] 編集中でないsegmentは内容が簡略化・グレーアウト表示され、編集中のsegmentと区別できる
- [x] 画像が添付されたsegmentは、編集中でなくても読み取り専用のサムネイルプレビューが表示される
- [x] 編集中のsegmentの直下にのみ、画像・GIF・絵文字・言語選択・文字数カウンター等の入力補助UIが表示される
- [x] 編集中でないsegmentのうち削除可能なもの（先頭以外）には削除ボタンが表示され、削除するとスレッドから除外される

## 7. 非機能要件

- **既存機能への影響最小化**: 既存PostFormの投稿フロー（テキスト・OGP・画像投稿）は、`POST /v2/entry`への統合後も同等の挙動を維持する。
- **Cloudflare Workers制約**: バックエンドロジックはNode.js固有APIに依存しないこと（採用するライブラリの実装がpure JSであることを含む）。
- **コードファースト原則の踏襲**: APIフィールドは単一のスキーマ定義を真実の源とすること。フロントエンド実装時はコード生成でクライアントを再生成すること。
- **テスト**: バックエンドロジック（reply所有権検証・複数投稿の原子的作成・下書きのposts配列検証等）は`tests/`配下に分岐網羅レベルの単体テストで担保されなければならない（`tests/README.md`の方針に従う）。
- **セキュリティ**: `reply.root`/`reply.parent`のuriが呼び出しユーザー自身のDIDに属することをサーバ側で検証する。
