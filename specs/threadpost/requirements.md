# スレッド投稿機能 要件定義書

## 1. 背景・目的

Blueskyのスレッド（reply chain）形式で、複数の投稿をあらかじめ作成しておき、順に投稿していく「スレッド投稿機能」を提供する。

バックエンド（skyshareサーバサイド）のAPI仕様・実装（`POST /v2/entry`でのreply対応・複数投稿の原子的作成・所有権検証等）と、下書き（drafts）がスレッド（複数投稿）を表現できるデータ構造・APIは実装済みである（詳細は[`design.md`](./design.md)参照）。フロントエンドのUI・アーキテクチャはこれから設計・実装する。

## 2. 用語定義

| 用語           | 意味                                                                                                  |
| -------------- | ----------------------------------------------------------------------------------------------------- |
| PostForm       | 既存の投稿フォーム本体（`src/components/post/PostForm`）。                                            |
| skyshare entry | `dev.nekono.skyshare.entry` レコード。画像投稿に付随するheading/caption/cover画像などのマニフェスト。 |
| record         | `app.bsky.feed.post` のレコード本体（Bluesky投稿そのもの）。                                          |
| reply chain    | `app.bsky.feed.post#replyRef`（`root`/`parent`のStrongRef）によるBluesky公式のスレッド接続の仕組み。  |
| セグメント     | スレッド投稿における個々の投稿単位（1スレッド内の1投稿）。                                            |
| StrongRef      | `com.atproto.repo.strongRef`相当。レコードを一意に指す`{ uri, cid }`の組。                            |

## 3. スコープ

### 3.1 対象

- スレッド投稿を実現するためのバックエンドAPI（`POST /v2/entry`。複数投稿の原子的作成、`reply`によるスレッド接続、所有権検証）— **設計・実装済み。本書は現状の記録として扱う（詳細はdesign.mdを参照）**。
- 下書き（`POST /v2/bsky/drafts` 等）が複数投稿（スレッド）を保持できるデータ構造 — **設計・実装済み。本書は現状の記録として扱う**。
- スレッド投稿のフロントエンドUI・UX要件 — **要件レベルの再確認のみを本書で行う。具体的なコンポーネント構成・状態管理方式（アーキテクチャ）は別セッションで一から設計する。**

### 3.2 対象外（本書では扱わない）

- クリエイターモード自体（EditorToolbox、FR1〜FR4: 手動リンクfacet・カスタムパラメータ・YayText変換・entry manifest任意設定）。これらは引き続き [`specs/creator-mode`](../creator-mode/requirements.md) の範囲であり、スレッド投稿がクリエイターモードの一部として実装されるか、独立機能として実装されるかは別途判断する。
- フロントエンドの具体的な実装方式の確定（コンポーネント分割・状態管理・API呼び出しタイミング等）。これは別セッションで設計する。
- Bluesky公式クライアント・他社クライアントとの相互運用性検証。
- クロスポスト先（Taittsuu/Mastodon/X）側でのスレッド表現の高度化（既存のインテント連携の範囲を超えない）。
- 画像付きスレッドセグメントの完全対応。`/v2/entry`は各セグメントに`createEntry`フラグでskyshare entryの作成有無を指定できるが、レガシーフロントエンド側の画像圧縮・OGP画像合成フローは1件の投稿を前提にしており、スレッド全体を通した画像付き複数セグメントの送信経路はフロントエンド設計時に別途検討する。

## 4. 前提条件・現状整理

- 本アプリはCloudflare Workers上で動作するため、Node.js固有APIは使用不可。
- APIはコードファースト（`src/lib/api/schema/**` のZodスキーマが単一の真実の源）。
- `POST /v2/bsky/record`（skyshare entryを伴わない投稿専用エンドポイント）は`POST /v2/entry`に統合され、廃止された。テキストのみ投稿・OGPリンク投稿・画像投稿（skyshare entryあり/なし）は、いずれも`POST /v2/entry`の`posts`配列で扱う。
- `POST /v2/entry`は、`posts`配列に複数件を渡すことで、Blueskyのスレッド（reply chain）を`com.atproto.repo.applyWrites`により1回のPDSトランザクションとして原子的に作成できる（詳細はdesign.md参照）。
- 下書き（`app.bsky.draft.*`）は複数投稿（`posts`配列）を保持できる構造になっている（詳細はdesign.md参照）。

## 5. 決定事項（creator-mode要件定義時のヒアリング結果のうち、スレッド投稿に関わるもの）

| 項目                    | 決定内容                                                                                                                     |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| セグメントの機能範囲    | 2投稿目以降（リプライ投稿）も1投稿目と全く同じフル機能（画像・OGP・返信/引用設定・自己ラベル等）を使える。                   |
| 各セグメントのentry作成 | 各セグメントが画像投稿であれば、そのセグメントごとにskyshare entryが作成される（スレッド全体で1つの代表entryに限定しない）。 |
| 利用対象ユーザー        | ログイン済みの全ユーザーが利用可能（opt-in設定は設けない）。                                                                 |

上記はクリエイターモードのヒアリングで確定した事項をそのまま踏襲する。フロントエンドの起動導線（専用ページか、既存投稿フォームの拡張か等）や、スレッド全体の送信方式（1リクエストにまとめるか、セグメントごとに個別リクエストを送るか）は、次セッションのフロントエンド設計時に決定する（バックエンドAPIはどちらの方式にも対応できる。design.md第4節参照）。

## 6. 機能要件

### 6.1 FR-THREAD-BE. バックエンド: 投稿作成API（reply・原子的な複数投稿作成）

**概要**: `POST /v2/entry`が、1件の投稿（テキストのみ/OGPリンク/画像付き、skyshare entry作成有無を`createEntry`で指定可能）、または`posts`配列による複数投稿（スレッド）を、`com.atproto.repo.applyWrites`で原子的に作成する。トップレベルの`reply`（`{ root: {uri, cid}, parent: {uri, cid} }`）により、既存のスレッドへ継ぎ足すことができる。

**詳細要求**:

- `posts`は1〜100件の配列。各要素は`text`/`facets`/`ogImage`/`ogMeta`/`images`/`imagesMeta`/`langs`/`selfLabels`/`gate`/`createEntry`を持つ。
- `createEntry: true`は`images`+`ogImage`が揃っている場合のみ有効。欠けている場合は400を返す。
- `reply`はStrongRef（`{uri, cid}`）の`root`/`parent`から成る任意フィールドで、`posts`と同階層に1つだけ持つ。`reply.root`/`reply.parent`のuriは、呼び出しユーザー自身の`app.bsky.feed.post`レコードを指している必要がある。他人の投稿への不正なreply chain構築を防ぐため、サーバ側でDID一致を検証し、不一致時は400を返す。
- `posts`が2件以上の場合、2件目以降のreply chain（root/parent）はサーバが内部で自動的に組み立てる（クライアントが個別に指定する必要はない）。
- 投稿本体・threadgate/postgate・skyshare entryは1回の`applyWrites`で原子的に作成され、いずれかが失敗した場合はリクエスト全体が失敗し、投稿は一切作成されない（部分成功状態は存在しない）。

**受け入れ条件**（**実装済み・充足確認済み**）:

- `posts`に複数件を指定して投稿すると、Bluesky上で正しくスレッド（リプライチェーン）として表示される。
- トップレベルの`reply`を指定して投稿すると、既存の投稿へ正しく接続される。`reply.root`/`reply.parent`のいずれかが自分以外の投稿を指す場合、400エラーになり投稿が作成されない。
- gate（threadgate/postgate）の作成に失敗した場合、投稿自体も含めてリクエスト全体が失敗する（500）。

### 6.2 FR-THREAD-DRAFT. バックエンド: スレッド下書き対応

**概要**: 下書き（`app.bsky.draft.*`）が、1投稿だけでなく複数投稿（スレッド予定）を保持できるようにする。

**詳細要求**:

- 下書きの本体を「1件のtext」から「`posts`（1〜100件の`{text, labels?}`）配列」へ変更する。
- `posts`が1件ならテキストのみの下書き、複数件ならスレッド（reply chain予定）の下書きとして扱う。
- 画像等の埋め込みはデバイスローカル参照のため下書きには含めない（既存方針を踏襲）。

**受け入れ条件**（**実装済み・充足確認済み**）:

- 複数セグメント分のtext/labelsをまとめて1つの下書きとして作成・更新・一覧取得・削除できる。

### 6.3 FR-THREAD-FE. フロントエンド: スレッド投稿UI（要検討・未確定）

以下は[`specs/creator-mode/requirements.md`](../creator-mode/requirements.md)のFR5に記載されていた要件レベルの記述を引き継いだものであり、**実現方式（コンポーネント構成・状態管理方式・API呼び出し方式）は未確定**。次セッションで設計時に再検討する前提で、要件の出発点として記載する。

- スレッドに追加する導線を設け、投稿フォームを複数（セグメント）並べられるようにする。各セグメントは1投稿目（PostForm相当のフル機能）と同一の機能を持つ。
- セグメントは追加・削除ができる。
- 投稿順序が保たれること（バックエンドAPI自体が`posts`配列の順序通りにreply chainを組み立てるため、UI上も入力順＝投稿順になるようにする）。
- スレッド全体を1回のAPI呼び出しで送るか、セグメントごとに個別のAPI呼び出しを行うかは、バックエンドのどちらにも対応できるため、UI/UXの要件（各セグメントの見せ方、失敗時の挙動等）から決定する。
- 各セグメントが画像投稿であれば、そのセグメントごとにskyshare entryが作成される（`createEntry`フラグ）。
- 下書き（6.2）との連携方法（スレッド全体を1つの下書きとして保存・復元する等）。

**受け入れ条件**: 次セッションでの設計・実装後に定義する。

## 7. 非機能要件

- **既存機能への影響最小化**: 既存PostFormの投稿フロー（テキスト・OGP・画像投稿）は、`POST /v2/entry`への統合後も同等の挙動を維持する。
- **Cloudflare Workers制約**: バックエンドロジックはNode.js固有APIに依存しない（`applyWrites`原子化に使う`@atproto/common-web`・`@atproto/lex-cbor`もpure JS実装であることを確認済み）。
- **コードファースト原則の踏襲**: APIフィールドは`src/lib/api/schema/**`のZodスキーマを単一の真実の源として実装済み。フロントエンド実装時は`npm run codegen`でクライアントを再生成すること。
- **テスト**: バックエンドロジック（reply所有権検証・複数投稿の原子的作成・下書きのposts配列検証等）は`tests/`配下に分岐網羅レベルの単体テストを追加済み（`tests/README.md`の方針に従う）。
- **セキュリティ**: `reply.root`/`reply.parent`のuriが呼び出しユーザー自身のDIDに属することをサーバ側で検証する（実装済み）。

## 8. 未決事項・リスク

- フロントエンドのアーキテクチャ（コンポーネント構成、状態管理、API呼び出し方式）は未確定。次セッションで設計する。
- スレッド投稿とクリエイターモード（EditorToolbox、FR1〜FR4）の関係性（スレッド機能をクリエイターモードの一部として実装するか、既存PostFormの拡張として独立に実装するか）は未確定。
- スレッド全体を1リクエストにまとめて送る設計を採る場合でも、途中経過（何件目まで作成できたか等、UI上の進捗表示）をどう扱うかはフロントエンド設計時に詳細化する（バックエンド自体は全件成功/全件失敗の二値）。
- 下書き（FR-THREAD-DRAFT）とスレッド投稿UIの連携方法（保存/復元のUI・タイミング）は未確定。
- 画像付きスレッドセグメントの完全対応（レガシーフロントエンドの画像圧縮・OGP画像合成フローとの統合）は未確定。
