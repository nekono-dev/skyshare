# 実装計画

## 前提と進め方

- `design.md` を正とし、設計と異なる古い記述は追補で置き換えを示す。
- 設定の退避、production 環境の作成・ブランチ制限・設定登録・一致確認、本番バケットの作成、develop 環境の作成・ブランチ制限、共有の設定の削除、旧ワークフローによる develop の再配備と R2 の確認は**実施済み**。これらを再実行するタスクは設けない。
- 各実行タスクは実作業で 1〜3 時間を目安とする。日次集計や配備の待ち時間は含めない。振る舞いを変えるタスクは、テストを先に書いて失敗を確認してから実装する。
- `(P)` は、未完了の直前のタスクと並列に実行できるものだけに付ける。同じファイルを変更する作業は直列に進める。
- 通常のテストでは偽の外部操作を使う。GitHub・R2 への実操作は 3 と 9 に分け、設計で許可された確認と移行の範囲で行う。
- 秘密、アカウント ID、設定の本文、ハッシュの実値、外部コマンドの出力本文を成果物に記載しない。
- タスク 3・9.1・9.2・9.4 の実行主体は親エージェントまたは利用者とし、Codex や実装サブエージェントに委任しない。認証がなく、外部・破壊的操作を含むためである。
- survey-operations 4.2 の実機確認はこの spec の完了後に運用者が行う。登録済みの develop サンプルを使い、結果は日次集計だけで用意し、R2 へ直接書き込まない。
