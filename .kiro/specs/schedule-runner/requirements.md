# Requirements Document

## Introduction

実行時刻の到来した予約を、利用者のブラウザが閉じていても自動的に利用者の Bluesky へ投稿する。実行は利用料金の発生しない無料枠の実行制限の中で行い、制限で中断しても重複して投稿せずに続きから完了させる。

## Boundary Context

- **In scope**:
  - 実行時刻が到来した予約の定期的な取り出しと実行。
  - 画像・スレッド・返信と引用の制限・entry の作成。
  - 失敗の分類と再試行、中断した実行の再開と回収。
  - 終了した予約の履歴と不要な認証情報の削除。
- **Out of scope**:
  - 予約の作成・取消を受ける API と画面。
  - 動画を含む予約の実行。
  - 投稿の失敗を利用者へ通知する仕組み。
- **Adjacent expectations**:
  - 前提: schedule-store — 予約・進捗・認証情報・画像の保管と取り出しを使う。

## Requirements

### Requirement 1: 定期的な取り出しと実行

**Objective:** As a 利用者, I want 指定した時刻に近いタイミングで予約が投稿されてほしい, so that ブラウザを閉じていても予定どおりに投稿される

#### Acceptance Criteria

1. When 1分ごとの定期実行が起動したとき、the 予約の実行 shall 実行時刻が到来した待機中の予約を、実行時刻の早い順に5件まで取り出して実行し、未到来の予約は実行しない
2. While 実行時刻が到来した予約が5件以内のとき、the 予約の実行 shall 実行時刻から3分以内に投稿の作成を開始する
3. The 予約の実行 shall 1回の実行で行う外部への通信を40回以内にする（10枚の画像を持つ予約を5件実行しても超えない）

### Requirement 2: 認証と投稿の作成

**Objective:** As a 利用者, I want 予約が自分のアカウントで正しい順序・内容で投稿されてほしい, so that 手動の投稿と同じ結果になる

#### Acceptance Criteria

1. When 予約が実行されるとき、the 予約の実行 shall OAuth の更新用トークンでアクセストークンを得て、回転した更新用トークンを投稿より先に暗号化して保管し、PDS への要求に DPoP の証明を付ける
2. If PDS が DPoP の nonce を求めたとき, then the 予約の実行 shall 受け取った nonce を入れた証明で1回だけやり直す
3. The 予約の実行 shall 画像のアップロード、投稿の先頭からの順次作成、投稿ごとの制限の作成、entry の作成の順に実行する
4. The 予約の実行 shall 作成する投稿の日時を実行時の時刻とし、指定された既存の投稿があれば先頭の投稿をその返信にする

### Requirement 3: 実行制限と中断からの再開

**Objective:** As a 運用者, I want 無料枠の実行制限の中で確実に完了させたい, so that 料金が発生せず、重複した投稿も作られない

#### Acceptance Criteria

1. When 外部への通信の回数が上限に達したとき、the 予約の実行 shall 進捗を保ったまま予約を待機中へ戻し、残りを次の実行へ持ち越す
2. When PDS がレート制限を返したとき、the 予約の実行 shall その実行での以降の通信を止め、予約を待機中へ戻して次の実行へ持ち越す
3. When 中断した予約が再実行されたとき、the 予約の実行 shall 保持した進捗から再開し、作成済みの投稿を重複して作らず、同じ位置の投稿を1件ずつにする
4. The 予約の実行 shall 同じ予約から同じ位置の投稿を2件以上作成する件数を0件にする（作成の直後に進捗の保存が失敗しても2件にならない）
5. When 実行中のまま10分以上更新されない予約があるとき、the 予約の実行 shall 待機中に戻し、直近に更新された予約は戻さない

### Requirement 4: 失敗の分類と履歴

**Objective:** As a 利用者, I want 失敗の原因が分かり、書き戻して再投稿できるようにしたい, so that 予約が失われない

#### Acceptance Criteria

1. If 一時的な失敗が発生したとき, then the 予約の実行 shall 最大5回まで再試行し、超えた予約は失敗として終了する（4回目までは待機に戻す）
2. If 認証の失効・入力の不正・画像の欠落の恒久的な失敗が発生したとき, then the 予約の実行 shall 再試行せず、分類コードを記録して失敗とする
3. When 認証の失効で失敗したとき、the 予約の実行 shall 認証情報を再度の許可が必要な印に替え、以後の予約は通信せずに同じ分類で失敗させる
4. When 予約が成功したとき、the 予約の実行 shall 予約を行ごと削除し、保管した画像を削除する
5. When 予約が失敗したとき、the 予約の実行 shall 画像を書き戻せるよう残す

### Requirement 5: 後片付け

**Objective:** As a 運用者, I want 不要になった予約と認証情報を自動で削除したい, so that 利用者の情報を必要以上に保持しない

#### Acceptance Criteria

1. When 後片付けが行われるとき、the 予約の実行 shall 失敗から7日が過ぎた予約を削除する
2. When 後片付けが行われるとき、the 予約の実行 shall 予約がなく30日使われない認証情報を印に替え、最後の使用から180日が過ぎた印と期限を過ぎた認可の途中の状態を削除する
3. The 予約の実行 shall 後片付けを1日に1回だけ行い（1日の1440分のうち後片付けの時刻と判定されるのは1分だけ）、毎分の実行では行わない

### Requirement 6: 実行の経路の安全性

**Objective:** As a 運用者, I want 実行の経路を軽く、秘密が漏れない形に保ちたい, so that 無料枠で安定して動作する

#### Acceptance Criteria

1. The 予約の実行の経路 shall atproto のライブラリを読み込む箇所を0件にする
2. If 実行が失敗したとき, then the 予約の実行 shall トークンと鍵を含む文字列をログと記録に出力しない
