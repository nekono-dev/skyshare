# Research & Design Decisions

## Summary

- **Feature**: `survey-results-public`
- **Discovery Scope**: Extension（既存のビルド・ログイン画面・辞書・wrangler 生成の拡張。統計ファイルの形式は上流 `survey-results-aggregation` が所有）
- **Key Findings**:
  - 結果の保管先のバインディング `SURVEY_RESULTS` は、Astro の静的生成（workerd 内で動く）から `cloudflare:workers` の `env` で読める（brief の PoC）。Node 側の前処理（`build:prepare`）では読めないため、取得はページの生成の中で行う。
  - `remote: true` は認証情報が無い環境で起動を失敗させるため、`scripts/config/render-wrangler.mjs` が認証情報の有無で付ける。ビルドの旗はその生成物（`wrangler.jsonc`）から導けば、「情報の有無」の判定が 1 か所になる。
  - ログイン画面（静的）と結果ページ（静的）は別々のページで、同じビルドの判定を共有する必要がある。ページ間の共有はモジュールの記憶に頼れる保証が無いため、ビルド後の検査で整合を確かめる。
  - 既存のプライバシーポリシーの記述「回答は終了から 1 か月後に削除」は、`survey-results-aggregation` の実装後に事実と合わなくなる。

## Research Log

### 取得の段階（brief が設計に残した判断）

- **Context**: 結果を静的データに変える段階を決める必要がある。
- **Sources Consulted**: brief の PoC の結果、`package.json` の `build:prepare`、`astro.config.mjs`、`scripts/config/render-wrangler.mjs`。
- **Findings**: `build:prepare` は Node で動き、R2 のバインディングを持たない。ページの生成は workerd で動き、実行時の Worker と同じバインディングを読める。
- **Implications**: 取得はページ側（`getStaticPaths` とログイン画面のフロントマター）から呼ぶ共通の関数で行う。`build:prepare` には取得を置かない。

### 依存規則との整合

- **Findings**: `src/pages/` は `cloudflare:workers` を直接 import しない規約（`pagesThin` の検査対象は一部の API だけだが、方針は同じ）。`lib/*/env.ts` が動的 import で包む前例がある。結果の読み取りは `lib/survey`（業務の層）に置き、基盤の層は `lib/i18n`・`lib/platform` の型だけに依存する（`lib/site` には依存しない）。
- **Implications**: 新しい領域は作らず `lib/survey/publicResults/` に置く。部品は新しい領域 `components/survey/` を作る（利用元が `pages/` のため、親の子にできない）。

### ログイン画面のリンクの色・グラフの色

- **Findings**: ブランドのプライマリ色は `--color-bluesky`（リンク・青いボタンが使う）。灰色は `--color-gray`（下地）と `--color-gray-hover`（棒）。ダーク表示でも同名のトークンが上書きされている。
- **Implications**: 新しい色の定義は不要。下地と棒の差は小さい（ライトで約 1.1 対 1）ため、数字を棒の中に置く合意の画面が前提になる。

## Architecture Pattern Evaluation

| Option                                      | Description                                                   | Strengths                                              | Risks / Limitations                                                              | Notes          |
| ------------------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------ | -------------------------------------------------------------------------------- | -------------- |
| A: ページの生成の中で取得（採用）           | `getStaticPaths` とログインのフロントマターが共通の関数を呼ぶ | バインディングをそのまま使える。実行時の経路と同じ設定 | 2 ページが別々に呼ぶ（整合は検査で守る）                                         | PoC で検証済み |

| C: ビルド後に別のスクリプトでページを足す   | 静的ページを後から生成                                        | —                                                      | Astro のルーティングと分離し、二重管理になる                                     | 不採用         |

## Design Decisions

### Decision: 結果を静的データに変える段階

- **Selected Approach**: A。共通の関数 `getPublishedSurveys` を 1 つ置き、ページ側から呼ぶ。
- **Rationale**: バインディングはページ生成の環境にだけある。
- **Trade-offs**: ログイン画面と結果ページが 2 回取得する可能性がある。モジュール内の記憶（同じ約束の共有）と、ビルド後の整合検査で守る。

### Decision: ローカルの固定のサンプル

- **Selected Approach**: 置かない。
- **Rationale**: 本番のコードに偽のデータの分岐を入れると、オプトアウトの規則（情報が無ければ無効）が二重になる。表示はテストの部品データ（`tests/fixtures`）で確かめ、実物の確認は認証情報を付けた開発サーバー（develop の保管先）で行う。

### Decision: 最大の選択肢の色と同率・全て 0 の扱い

- **Selected Approach**: プライマリ色は `--color-bluesky`。同率の最大はすべてプライマリ色。最大が 0（すべて 0%）なら誰も強調しない。
- **Rationale**: 「最大」に当たる複数を区別する根拠が無い。0% だけの質問で 0 を強調すると誤読される。

### Decision: 目録が無いとき・可視フラグが不正なとき

- **Selected Approach**: 目録が無い＝集計済みが 0 件（失敗しない）。可視フラグが無い＝非表示、不正＝ビルド失敗。
- **Rationale**: 運用の初期（まだ 1 件も集計されていない）で配備が止まるのを避ける。一方、不正な旗を黙って非表示にすると「公開したはずが出ない」を見落とすため、`survey-results-aggregation` の「読み手が通らないことを知らせる」責務に従い失敗にする。

## Risks & Mitigations

- 2 つの静的ページが別々の判定をする — 記憶の共有に加え、ビルド後の検査でページとリンクの有無の不一致を失敗にする。
- `getStaticPaths` が `slug` の未指定で `/surveys/` を作らない — 実装のはじめにビルド結果で確かめ、作れない場合は設計へ戻す。
- `remote: true` を含む設定での `wrangler deploy` の挙動 — CI の既存の `wrangler deploy --dry-run` と develop の配備で確かめる。
- 棒と下地の灰色の差が小さい — 合意済みの配色を保つ。プレビューで読めないと分かった場合は、色を変えず利用者へ戻す。
- 2 回の取得の間の更新で内容が食い違う（件数は同じ）— 残余のリスクとして design.md に明記する。
- 過去のプレビューは次のプッシュまで古い — 手順書に書く。

### 結果ページの経路の確認（タスク 1.4、2026-11-13）

- **方法**: 使い捨ての最小のページ `src/pages/surveys/[...slug].astro`（`prerender = true`、`getStaticPaths` が固定の値を返す）を置き、`SURVEY_CONFIG` を設定したまま `npm run build:v2`（`survey:render` を含む）を実行して、`dist/client/surveys/` を調べた。確かめたあと、ページとビルドの出力は消した（リポジトリに残っていない）。
- **確認 1（固定の 1 件で作られる）**: `getStaticPaths` が `[{ params: { slug: undefined } }]` のとき、`dist/client/surveys/index.html` ができた。できた。
- **確認 2（設定の配信物と衝突しない）**: 同じビルドで、設定の配信物 `public/surveys/index.json` が `dist/client/surveys/index.json` として、結果ページと並んで残った。内容は設定のまま（`cmp` で一致）。衝突しない。
- **確認 3（固定の 0 件では作られない）**: `getStaticPaths` が `[]` のとき、`dist/client/surveys/` には `index.json` だけが残り、`index.html` はできなかった。作られない。
- **注意（ビルドの確認の方法）**: ページの生成は workerd の中で動くため、シェルの環境変数（`process.env`）はページから見えない。0 件と 1 件の切り替えを環境変数で試すと、常に 1 件の経路になり、確認として無効になる。切り替えはコードで行う。
- **結論**: 設計の経路（`getStaticPaths` が空なら作らない）は成り立つ。後続のタスクへ進める。

### 最大の棒の文字のコントラスト（タスク 2.6、2026-11-13。利用者が A を選択）

- **事実**: 最大の棒は、合意した配色（`--color-bluesky` の下地に `--color-white` の文字。ボタンと同じ組み合わせ）で、コントラスト比が約 3.66:1（ライト・ダークとも）。通常の大きさの文字に必要な 4.5:1（WCAG の AA）に届かない。
- **実装での緩和（色は変えていない）**: 最大の棒の数字だけを太字・1.25rem（約 20px）にした。WCAG の「大きな文字」（太字で 14pt = 約 18.7px 以上）は 3:1 で足りるため、基準を満たす。最小幅も、拡大した数字（最大で `99.9%` の約 57px）が欠けない 4.5rem にした。
- **選択肢**: (A) 現状のまま（合意した配色。大きな太字で基準を満たす）。(B) `--color-bluesky-hover` の下地に白文字（約 5.37:1）に変える。ボタンと同じ組み合わせではなくなるが、通常の大きさでも 4.5:1 を超える。(C) 青の下地をやめて、灰色の中で太字だけで強調する。
- **決定（2026-11-13、利用者）**: (A) 現状のまま。ライト・ダークとも、ボタンと同じ青の下地に白文字で統一する。ダークで (B) にすると、青いボタン（ライト・ダークとも `--color-bluesky`）と色が違ってしまい、棒と下地のコントラスト比も 2.48:1（図形の基準 3:1 未満）に下がるため。実装の変更は不要。

### develop の保管先での一連の確認（タスク 4.1、2026-11-13）

- **方法**: develop 用バケット（`skyshare-survey-results-develop`。確認前は空）に、形式に従う検証用のデータ（目録・結果 3 件・可視フラグ 3 件。公開 2 件・非表示 1 件・結果なし 1 件）を置き、認証情報つきで `npm run build:v2` を実行した。確認後、置いたオブジェクトはすべて削除し、バケットを空に戻した。本番のバケットには触れていない。
- **公開（認証情報あり）**: `/surveys/` が生成され、ログイン画面に `/surveys/` へのリンクが出た。結果は実施時期の新しい順（`2026/09/01 〜 09/30`、`2025/12/15 〜 2026/01/15`）。非表示のアンケートと結果なしのアンケートは載らない。年をまたぐ期間は終了日も年から表記された。
- **画面（Chromium で撮影。ライト・ダーク・幅 390px）**: 最大の棒だけがボタンと同じ青（同率の 2 つは両方とも青）、ほかは灰色。すべて 0% の質問は青にならない。0.4% の棒でも数字が欠けない。スマホ幅は 1 列で、選択肢の文言が棒の上に来る。ダークでも同じ配色で読める。
- **可視フラグを外した再ビルド**: 公開 2 件を `visible: false` にすると、ビルドは成功し、`/surveys/` もログインのリンクも作られなかった。整合の検査も通った。
- **オブジェクトを壊したビルド**: 結果の形式の不正は `invalid (demo-b)`、目録が `result` なのに結果が無い場合は `missing (demo-a)` で、どちらもビルドが終了コード 1 で失敗した。エラーには種類と識別子だけが含まれ、本文は出ない。
- **認証情報なし**: 認証情報を外して設定を生成し直すと、接続の設定（`remote`）が付かず、ビルドは成功し、ページもリンクも作られなかった。
- **配備の検証**: 接続つきの設定（`remote: true`）で `wrangler deploy --dry-run` が成功した。
- **期待と違う点**: なし（設計へ戻す点はない）。
- **注意（書き込み権限）**: 結果の保管先への書き込みには R2 の編集の権限が要る。CI の読み取り用のトークンのままでは、検証用のデータを置けない。

### プライバシーポリシーの文面の整理と注意書きのリンク（タスク 5.1・5.2、2026-11-14。利用者の指示）

- **指示**: 技術の説明を避け、冗長な文を削る。(1) 回答の扱いは「回答内容は、回答したアカウントとは結びつけず保存します」だけにする。(2) 通常の投稿の保管の注記を削除する。(3) 目的は「サービス品質の向上及び改善」に端的にする（最初は目的の文だけを置き換え、公開の 2 文を要件 9.1 を理由に残した。利用者から「冗長なまま」と指摘があり、案 2 を 2 つの箇条書き「アンケート結果は集計し、サービス品質の向上及び改善に使います。」「アンケート結果は回答の割合を公開することがあります。」に分けると決定した。要件 9.1 はこれに合わせて直した）。(4) 不具合の報告の掲載先の記述は保持期間の側にあるため、短くする。(5) 許可が無効になった後の保持を詳しく書く。(6) 重複判定用ハッシュの削除の行は、回答の削除の行で足りるため削除する。(7) 予約の許可の範囲の行は認可の説明で足りるため削除する。あわせて、回答の画面の注意書きの「プライバシーポリシー」をリンクにする。
- **(5) の事実（実装の確認）**: 許可が無効になる（`markCredentialReauth`）か、予約がないまま 30 日使われない（`purgeIdleCredentials`）と、認可の情報（`token_enc`）は空になる。しかしアカウントの識別子（`did`）を含む行は「再度の許可が必要である印」（`reauth_required = 1`）として残り、`purgeReauthMarkers` が、最後の使用（`updated_at`）から 180 日（`REAUTH_MARKER_KEEP_SECONDS`）を過ぎた行を削除する（待機中・実行中の予約がないときだけ）。「許可が無効になった時点で識別子も消える」わけではない。最初の文面は「識別子と無効の旨だけを 180 日まで」と書いたが、独立したレビューと検証の両方が、実装との不一致を指摘した（行には `service`・`updated_at`・`authorized_at` も残る。削除は 180 日を過ぎた後の日次処理で、待機中・実行中の予約があれば残る）。文面は「識別子と無効の旨などの情報を残し、最後に使ってから 180 日を過ぎた後に削除する」に直し、認可の情報の削除との区別は保った。
- **解釈で決めた点（利用者の確認待ち）**: (4) は「バグ報告または機能提案内容」とだけ指示されたため、共有の項目としての意味が通る「バグ報告または機能提案内容の公開」とした。「GitHub の」を外したので、掲載先は保持期間の節の記述だけが伝える。
- **決定（利用者、2026-11-14）**: `privacy.retention.surveyDevice`（「端末の記録は、ブラウザの保存データを消すまで残ります。」）は削除する。`collected.survey` から端末の説明を外した結果、参照先が無くなるため。あわせて、整理の依頼の趣旨（文面を増やさない）に合わせ、`privacy.retention.item3` は「認可の情報の削除」と「識別子などの削除」の 2 文に短くした。
- **決定（利用者、2026-11-14）**: 案 B（印を残さず、無効になったら行ごと削除する）に実装を変更する。予約の失敗は失敗の記録から判断でき、利用者が再度有効にする導線になる。ポリシーは「認可の情報は、許可が無効になったとき、または予約がないまま 30 日使われないときに削除します。」の 1 文にした。実装はタスク 5.3、設計の「予約の許可の印の廃止」を参照。下は、決定の前の論点の記録。
- **論点（利用者の問い、2026-11-14）**: 許可が無効になった後も、アカウントの識別子を含む行（印）を残す理由と、残さない案の可否。
  - **事実**: 利用者が自分で予約投稿をオフにしたときは、行ごと削除し、Bluesky 側の許可の取り消しも試みる（トークンを取得できる場合。通信の失敗は許容する。`scheduleCredential.ts`。オンにする前と同じ状態）。印が残るのは、利用者の操作ではなく無効になった 2 つの場合（Bluesky 側の失効が予約の実行で分かったとき、予約がないまま 30 日使われないとき）だけ。
  - **残している意図（コードの記述）**: 設定のスイッチをオフに戻さず、「Bluesky での許可が無効になっています。予約するには、もう一度許可してください」と案内するため（`getCredentialStatus`・`ScheduleSetting`）。行が無いと、サーバーは「登録していない」と「登録したが無効」を区別できない。行の主キーが `did` のため、識別子は印の一部になる。
  - **案**: (A) 現状（印を 180 日残す）。(B) 印を残さず、無効になったら行ごと削除する（スイッチはオフに戻る。予約の実行で失効が分かった場合の失敗の理由は、予約の失敗の履歴に残る）。(C) 印を残すが、期間を短くする。(B)・(C) は予約投稿の振る舞いの変更で、`survey-results-public` の境界の外（予約の機能。専用の spec は無い）。

### プライバシーポリシーの文面の全体の整理（タスク 5.1 の追補、2026-11-14。利用者の指示）

- **指示**: 文字どおりに直す。問題があれば質問する。(1) ログイン: `Blueskyアカウントに関する認証情報`。(2) 予約: `予約投稿機能有効化時は、添付画像を含む投稿内容およびBlueskyアカウントに関する認証情報`。(3) 通信: `ホスティングプロバイダが収集するIPアドレスやブラウザ情報`（保持も同じ用語）。(4) 解析: `Google アナリティクスによる利用状況`。(5) 不具合の報告: `不具合の報告・機能の提案フォーム利用時は、入力情報及びアカウント識別情報、利用者端末情報および本サービスに関する情報`（指示の「本アプリケーション」は、回答で「本サービス」に変更）。(6) アンケート: `アンケート回答時は、アンケート回答内容と重複回答防止の為の識別子`。(7) 利用目的のアンケートの項目は、利用状況の把握と本サービスの改善に含まれるため削除。(8) アンケートの結果公表は、情報の共有の最後に `アンケートの結果公表` として足す（匿名であることは、回答の画面の説明と(6)で伝わるため説明しない）。(9) 予約の認証情報の削除: `予約投稿機能有効化時は、認証情報が無効になった、または機能が30日使われていない場合に削除されます。` (10) 通信の情報の保持: `ホスティングプロバイダが定める期間`。(11) 予約の操作と無効化: `予約投稿の変更・取消・削除は…予約機能を無効化した場合、予約内容およびBlueskyアカウントに関する認証情報は削除されます。`
- **文面の調整（私の判断。報告済み）**: (9) の「使われてない」は「使われていない」に、(10) の「ホスティングプロバイダ が」の空白は除いた。
- **質問と回答（利用者、2026-11-14）**: (a) 共有の「Cloudflare での取り扱い」→「ホスティングプロバイダ」に変更する。(b) 「本アプリケーション」→「本サービス」に変える。(c) セキュリティの「予約用の認可の情報」→「認証情報」に変える。いずれも反映済み。あわせて、パスワードの記載はしない（真のユーザーパスワード情報は扱わないようにしており、注意を向けさせる必要がないため）。予約を無効にしたときの Bluesky の許可の取り消しの記述は、「予約内容およびBlueskyアカウントに関する認証情報は削除されます」で伝わるため落ちていない、という判断。セキュリティの「情報を扱うのは運営者に限ります」は断定が広すぎる可能性があり、訂正案を提示して利用者の判断待ち。
