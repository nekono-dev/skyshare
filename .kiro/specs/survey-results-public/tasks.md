# Implementation Plan

- [ ] 1. Foundation: 有効・無効の判定と、結果の保管先への接続の設定
- [x] 1.1 生成した設定から結果公開機能のビルドの旗を決め、ビルドへ渡す
  - 結果の保管先のバインディングが実バケットへつながる設定のときだけ旗が真になる判定を、アンケートの提示・回答の有効判定とは独立に作る
  - ビルドの設定が、その旗を画面・サーバーの両方から読める定数として渡す
  - 同じビルドの設定は上流の仕様（`survey-results-aggregation`）も変更するため、上流の旗の追加を済ませた後に、その隣へ足す（互いに壊さない）
  - 完了の状態: 接続ありの設定は真、接続なし・ほかのバインディングだけ・保管先の宣言なしは偽になることが単体テストで確かめられ、ビルドの定数として読める
  - _Depends: 上流 survey-results-aggregation 2.5_
  - _Boundary: surveyResultsReadable, astro.config_
  - _Requirements: 1.1, 1.2, 1.5_

- [x] 1.2 (P) 認証情報が揃う配備と手元の開発だけで、結果の保管先への接続を付ける
  - 設定の生成に「実バケットへ接続するか」の指定（既定は接続しない）を足し、真のときだけ結果の保管先のバインディングに接続を付ける。ほかのバインディングとプレビューの設定には付けない
  - 本番以外の設定で接続を付けるときは、develop 用のバケット名にそろえ、手元の開発が本番のバケットへつながらないようにする
  - 配備用の生成と手元の開発の準備は、認証情報が 2 つとも揃っているときだけ接続を指定する。E2E の生成は変更せず、手元に認証情報があっても接続しない
  - 完了の状態: 認証情報あり・片方だけ・なし、本番・develop・E2E の組み合わせごとの生成結果が単体テストで確かめられ、認証情報なしの生成結果は従来と同一である
  - _Depends: 上流 survey-results-aggregation 1.1_
  - _Boundary: render-wrangler, render-deploy-config, prepare-local-env_
  - _Requirements: 1.1, 1.3, 8.2, 8.3, 8.4_

- [x] 1.3 (P) 配備のビルドに認証情報を渡す
  - プレビューと配備のワークフローの「Run build」の工程に、2 つの認証情報を渡す。E2E のワークフローには渡さない
  - 運用の手順書（認証情報が無い環境では無効であること、配備する運用者はバケットを先に作ること、手元で実物を確かめる渡し方、手元の開発では `getPublishedSurveys` の記憶が更新されないため保管先の内容を更新したあとは開発サーバーを再起動すること、既存のプレビューは次のプッシュまで更新されないこと）は、設計の変更ファイルの記述どおりに同じ変更で更新する。編集する節は「CI/CD の認証情報」「R2 の節」「ローカルの確認」「プレビューの更新」「本番バケットの先行作成」に限り、`survey-operations` が編集する 3.x・5.x の節には触れず、6.5 節（D1・R2 の表）は `SURVEY_RESULTS` の行だけを編集する。「本番のバケットを先に作る」の 1 行だけは、上流 `survey-results-aggregation` のリリースが必要とするため、aggregation の配備前に先行してよい
  - 完了の状態: 2 つのワークフローのビルド工程が認証情報を受け取り、E2E のワークフローは受け取らない
  - _Boundary: CI workflows_
  - _Requirements: 8.1, 8.4, 8.5_

- [x] 1.4 (P) 結果ページの経路が成り立つことを最小の固定データで確かめる
  - 一時的な最小のページに固定の 1 件を持たせ、ビルドの出力に `/surveys/` の文書ができること、設定の配信物（`/surveys/index.json`）と衝突しないこと、固定の 0 件ではできないことを確かめる。確かめたら一時的なページは取り除く
  - 確かめた結果（できた・できなかった）を、設計の調査記録に追記する。できない場合は後続のタスクへ進まず設計へ戻る
  - 完了の状態: 調査記録に 3 つの確認の結果が書かれ、一時的なページがリポジトリに残っていない
  - _Boundary: surveys page_
  - _Requirements: 4.1_

- [ ] 2. Core: 取り込み・表示の規則・文言・結果の部品
- [x] 2.1 (P) 保管先から公開済みの結果を取り込む部品を作る
  - 保管先の読み取りを引数に受け、目録の取得、結果が「ある」項目ごとの可視フラグの取得、公開のものだけの結果の取得を行う。形式の検証は上流の共有の規則だけを使い、形式を再定義しない。結果が目録と合うかの判定は上流の `resultMatchesIndexEntry`、公開かどうかの判定は上流の `isVisible` を使い、同じ判定を独自に実装しない（上流がこの 2 つを変えたら、この部品と単体テストを見直す）
  - 目録が無いときは 0 件、可視フラグが無いときは `isVisible` により非表示、形が不正な可視フラグはビルドの失敗、回答 0 件の項目は取得しない。取得・検証・結果の欠落・識別子や期間の不一致・上限（所要時間・大きさ・件数）の超過は、種類を持つ失敗にする
  - 開始時刻の新しい順、同じなら終了時刻の新しい順、それも同じなら識別子の昇順に並べる
  - 失敗の通知とログに本文や検証の位置を含めず、失敗の種類と対象の識別子だけにする
  - 完了の状態: 偽の保管先を使う単体テストで、絞り込み（`isVisible` を通ること）・並び・各失敗の種類（不一致は `resultMatchesIndexEntry` の偽から）・目録なしの 0 件・上限・時間切れが確かめられ、失敗のメッセージに本文が現れない
  - _Depends: 上流 survey-results-aggregation 2.1（`resultMatchesIndexEntry`・`isVisible` の公開を含む）_
  - _Boundary: loadPublishedSurveys_
  - _Requirements: 2.1, 2.2, 2.3, 2.4, 2.5, 2.6, 2.7, 2.8, 2.9, 2.10, 3.1, 3.2, 3.3_

- [x] 2.2 (P) 実施時期・割合の表記と最大の選択肢の判定の規則を作る

  - 割合を小数点以下 1 桁までの数字として表記し（整数は小数なし）、表示言語の書式に従う
  - 質問の中で最大の割合の選択肢の集合を求める。同率はすべて含め、最大が 0 のときは空にする
  - 完了の状態: 時期（同じ年・年をまたぐ・終了時刻が日付の境目・オフセット付き）、割合の表記、最大の集合（単独・同率・すべて 0）が単体テストで確かめられている
  - _Boundary: presentation_
  - _Requirements: 5.2, 6.2, 6.3, 6.4_
