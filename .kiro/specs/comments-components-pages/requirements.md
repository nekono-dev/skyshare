# 要件書

## 概要

`src/components`・`src/pages`・`src/` 直下（`env.ts`・`vars.ts`・`worker.ts`・`middleware.ts`・`global.d.ts`）・`src/types`・`src/util`・`src/styles` の各ファイルのコメントを、`.kiro/steering/comments.md`（コメントの基準）に従って書き直す。書き直した後、これらの範囲の違反を許容リスト（`config/comments/allowlist.json`）から消す。

コメントは、現在の振る舞いと、その理由を述べるものにする。経緯・旧 spec への参照・cc-sdd や kiro への言及は残さない。振る舞いは変えない。コードの行は変えない。

2026-11-08 時点の状態:

- 許容リストに、このファイル範囲の項目が 203 件ある（`header-missing` 65、`header-too-long` 73、`header-too-many-bullets` 42、`forbidden:spec参照` 20、`forbidden:AC/FR/NFRタグ` 2、`forbidden:要件番号` 1）。対象のファイルは 144 件。
- 検査（`scripts/architecture/commentRules.ts`）の対象は `.ts`・`.tsx`・`.astro`・`.mjs` だけで、`.css` と `*.d.ts` は含まない。
- `src/styles` の CSS と `src/global.d.ts` などには、検査の対象外の経緯や参照が残っている可能性がある（brief の範囲に含まれるため、確認して直す）。

用語:

- **先頭ヘッダ**: モジュールの先頭にある、目的を書いたブロックコメント（`/** … */`）。規則の詳細は基準の文書の「先頭ヘッダ」の節に従う。
- **禁止パターン**: コメント中に書いてはいけない語の形（spec 参照・要件番号・AC/FR/NFR タグ・cc-sdd・kiro・バッククォートの外の日付）。
- **許容リストの項目**: 既存の違反のうち、まだ直していないものを、所有 spec と理由を付けて記録した項目。
- **経緯の語**: 基準の経緯の語（以前・かつて・旧・移行・経緯）。この spec の確認（要件 3.1 と grep）は、基準の一覧の語だけを使う。基準は変えない。

## 境界の文脈

- **対象内**:
  - `src/components/**`（`.ts`・`.tsx`・`.astro`・`.css`）のコメント。
  - `src/pages/**`（`.astro`・`.ts`）のコメント。
  - `src/env.ts`・`src/vars.ts`・`src/worker.ts`・`src/middleware.ts`・`src/global.d.ts` のコメント。
  - `src/types/**`・`src/util/**`・`src/styles/**` のコメント。
  - 上の範囲にある許容リストの項目（所有が `comments-components-pages` のもの）。
- **対象外**:
  - `src/lib/**`（comments-lib の範囲）、`src/client/**`（生成物）、`tests/**` と `config/test/**`（comments-tests の範囲）、`scripts`・`hack`・`config`・`.githooks`（comments-scripts-config の範囲）、`src/lib/api/schema/**`（comments-api-schema の範囲）。
  - 各 `README.md`（文書であり、コメントの基準の対象ではない。残っている参照は完了の報告に挙げる）。
  - 文字列リテラル（UI 文言・エラー文言）、振る舞い、部品の配置（`structure-components.md` の規約）。
- **隣接する期待**:
  - 許容リストは、この範囲の項目を消すことで解消される。他の comments-* の項目には触れない。
  - 判断の正本は `.kiro/steering/comments.md`。基準の内容は、この作業では変えない。
- **上流と実行の順序**: 先行 spec は comment-policy であり、基準・検査・許容リストの仕組みを作る。comment-policy が実装されるまで、この spec は実行しない。comments-* の spec は共有の許容リスト（`config/comments/allowlist.json`）を使うため、並列にせず、直列に実行する。
- **決めた前提**: CSS と `*.d.ts` は、検査の対象外（基準の「除外」）である。brief の範囲に含まれるため、先頭ヘッダは要求せず、禁止パターンと経緯の記述だけを取り除く。
- **検査の範囲（CSS）**: 基準の検査（`commentRules.ts`）は `.ts`・`.tsx`・`.astro`・`.mjs` だけを扱う。CSS は、先頭ヘッダを要求しない。CSS の禁止パターンの grep と、経緯の語の grep は、検査の判定ではなく、レビューでの確認である。

## 要件

### 1. 先頭ヘッダ

**目的:** 読む人として、ファイルを開いたときに目的と前提を先頭で把握したい。どの部品・どの画面がどの役割かを、コードを追わずに分かるようにするため。

#### 受入基準

1. The 対象範囲の `.ts`・`.tsx`・`.astro` のファイル shall 先頭（シェバン行と Astro のフロントマターの後を含む）に、基準の文書の規則に従う先頭ヘッダを持つ。
2. When 対象範囲のファイルの先頭ヘッダが、目的を書いていない、または import の後にある、または `//` の行コメントだけであるとき, the 作業 shall その違反を解消する。
3. When 対象範囲のファイルの先頭ヘッダが 6 行を超えるとき, the 作業 shall 制約の要点だけに絞り、6 行以内にする。
4. When 対象範囲のファイルの先頭ヘッダの箇条書きが 3 件を超えるとき, the 作業 shall 箇条書きを 3 件以内にする。
5. The 作業 shall 先頭ヘッダに、責務の逐条の説明やコードの言い換えを書かない（基準の文書に従う）。
6. The 作業 shall 先頭ヘッダの追加や削除で、モジュールの import・export・実行の順序を変えない。

### 2. 禁止パターン

**目的:** 開発者として、もう無い文書や要件への参照に迷わないようにしたい。コメントを読んだときに、どの文書を見ればよいかが混乱しないようにするため。

#### 受入基準

1. The 対象範囲のコメント shall `specs/` を含む旧 spec への参照を含まない。
2. The 対象範囲のコメント shall 要件番号（「要件 n.n」の形）を含まない。
3. The 対象範囲のコメント shall AC・FR・NFR のタグ（数字を伴う形）を含まない。
4. The 対象範囲のコメント shall `cc-sdd`・`kiro` への言及を含まない（大文字と小文字を区別しない）。
5. The 対象範囲のコメント shall 日付（`YYYY-MM-DD`）を、バッククォートで囲んだ入力例の中だけに含む。
6. The 対象範囲の `.css`・`*.d.ts` のコメント shall 上の 1〜5 に当たる参照を含まない（検査の対象外のため、検索で確かめる）。

### 3. 経緯と旧実装の記述

**目的:** 利用者の代わりに保守する開発者として、コードを読むだけで今の仕組みと理由が分かるようにしたい。「以前は」「かつては」などの過去の話を読んで、今の動きを取り違えないようにするため。

#### 受入基準

1. When コメントが経緯（導入時期・旧実装・移行の経過・「以前は」「かつては」）を述べるとき, the 作業 shall その経緯を取り除き、現在の振る舞いと理由を現在形で書き直す。
2. When コメントが決定の日付や決定者を述べるとき, the 作業 shall その決定を現在の制約として書き直す（決定の経緯は残さない）。
3. Where 「旧」「移行」「経緯」などの語が製品の用語や外部仕様の名前として正当に使われているとき, the 作業 shall その語を残し、判断を完了の報告に挙げる。
4. The 作業 shall 書き直した内容を、コードの現在の振る舞いで確かめる（コメントの主張をコードで確かめ、コードと一致しない記述を残さない）。

### 4. 残す・削る判断

**目的:** 開発者として、コメントを読んで判断に必要な情報が残っていてほしい。一方で、コードを読めば分かる説明は削ってほしい。判断の基準を揃えるため。

#### 受入基準

1. The 作業 shall 非自明な理由（回避策・外部仕様の癖・順序の制約・セキュリティ上の理由）を残し、現在形で検証できる形に書き直す。
2. The 作業 shall 公開 API の使い方のうち、シグネチャから分からないこと（単位・境界値・失敗のしかた・副作用）を残す。
3. The 作業 shall 外部仕様への参照（公式の仕様・lexicon 名・RFC）を残す。
4. When コメントがコードの言い換え（「値を返す」「変数を宣言する」など）であるとき, the 作業 shall そのコメントを削る。
5. When コメントが担当者や期限のない TODO であるとき, the 作業 shall その TODO を削るか、現在の制約として書き直す。
6. The 作業 shall 機械的な指示のコメント（`eslint-disable`・`@ts-expect-error`・`@ts-nocheck`・`use client`・`@vitest-environment` など、ツールが読むもの）を削らず、変えない。
7. If 残す・削るの判断に迷うコメントがあるとき, then the 作業 shall そのコメントを残し、判断を完了の報告に挙げる（黙って削らない）。

### 5. 振る舞いとコードの不変

**目的:** 利用者として、コメントを整えてもアプリの動きが変わらないでほしい。この作業がコメントだけの変更であると、差分で確かめられるようにするため。

#### 受入基準

1. The 作業 shall コードの行（import・式・型・文字列リテラル・JSX の要素）を変えない。変更は、コメントの行（先頭ヘッダを含む）と空行に限る。
2. The 作業 shall ファイルの追加・削除・移動・改名を行わない（部品の配置は `structure-components.md` の規約のまま）。
3. The 作業 shall 文字列リテラル（UI 文言・エラー文言）を変えない。
4. The 作業 shall 変更の差分（`git diff`）が、コメントと空行だけで構成されていることを、作業の各段階で確かめる。

### 6. 許容リスト

**目的:** 開発者として、この範囲の既存の違反が許容リストから消えていてほしい。解消済みの項目が残ると、検査が失敗し続けるため。

#### 受入基準

1. When 対象範囲のファイルの違反を解消したとき, the 作業 shall そのファイルの、所有が `comments-components-pages` の許容リストの項目を、同じ作業の中で消す。
2. The 許容リスト shall 所有が `comments-components-pages` の項目を、作業の完了時に 0 件にする。
3. The 作業 shall 他の所有（comments-lib・comments-tests・comments-scripts-config・comments-api-schema）の項目を消さない。
4. The 作業 shall 許容リストに新しい項目を追加しない（新しい違反を作らない）。
5. The 作業 shall 許容リストのファイルを機械的に書き出して作り直さない（`--emit-allowlist` の出力で置き換えず、項目を 1 件ずつ消す。`--emit-allowlist` は違反の一覧を見るためにだけ使う）。

### 7. 検証

**目的:** 開発者として、コメントの書き換えが既存の検証をすべて通ることを確かめたい。振る舞いを変えていないことを、テストの結果で示すため。

#### 受入基準

1. When 作業の段階（部品の群ごと）が完了したとき, the 作業 shall その群のファイルについて、検査（`npx tsx scripts/architecture/commentRules.ts --emit-allowlist` の出力）に違反が無いことを確かめる。
2. When 作業の段階が完了したとき, the 作業 shall `npm run test:unit` が通過することを確かめる（検査のテストを含む）。
3. When 作業の全体が完了したとき, the 作業 shall `npm run test:type`・`npm run test:imports`・`npm run test:component`・`npm run test:route`・`npm run test:render` が通過することを確かめる。`npm run test:e2e` は、この spec の検証には含めない（最終の e2e は comments-api-schema が実行する）。
4. When 作業の全体が完了したとき, the 作業 shall 対象範囲の `.css`・`*.d.ts` について、禁止パターンと経緯の語を grep で検索し、残りが無い（または残した理由を報告した）ことを確かめる。この確認はレビューであり、検査（`commentRules.ts`）の判定ではない。
5. The 作業 shall 完了の報告に、残したコメントの判断、正当な用法として残した語、残っている README の参照、検証の結果を含める。

## 注記

- 基準（何を残し何を削るか）は、`.kiro/steering/comments.md` を正本とする。この要件は基準を繰り返さない。
- 作業の単位（部品の群）と順序は、設計と実装計画で決める。
