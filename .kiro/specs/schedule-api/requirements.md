# Requirements Document

## Introduction

利用者が自分の Bluesky アカウントの予約投稿を、作成・一覧・編集・取消できるようにする。投稿時刻に利用者がブラウザを閉じていても投稿できるよう、Bluesky の OAuth で予約に必要な権限だけを許可させ、その認可の登録と削除も扱う。パスワードは受け取らない。

## Boundary Context

- **In scope**:
  - 予約の作成・一覧・内容の取得・置き換え・取消と、失敗した予約の履歴の削除。
  - 予約用の認証情報の OAuth による登録・状態確認・削除と、削除に伴う待機中の予約の取消。
  - 実行時刻の範囲と、アカウントごとの予約件数の検証。
  - 検証に使う制限値の提供。
- **Out of scope**:
  - 予約の実行と PDS への投稿。
  - 動画を含む予約。
- **Adjacent expectations**:
  - 前提: schedule-store — 予約と認証情報の保管と取り出しを使う。
  - 前提: oauth-client — 認可の要求・トークンの交換と更新と取消・戻りの受け渡しを使う。

## Requirements

### Requirement 1: 予約の作成

**Objective:** As a 利用者, I want 投稿を日時指定で予約したい, so that ブラウザを閉じていても指定の時刻に投稿される

#### Acceptance Criteria

1. When 予約の作成が要求されたとき、the 予約 API shall 1件から100件の投稿・実行時刻・entry の作成指定・投稿ごとの返信と引用の制限・画像を指定して作成でき、成功すると 200 と識別子と実行時刻を返す
2. If 投稿が0件または101件の予約が指定されたとき, then the 予約 API shall 400 で拒否する
3. If 動画を含む投稿の予約が指定されたとき, then the 予約 API shall 400 で拒否する
4. If 実行時刻が作成と置き換えの時点から5分後より前、または14日後より後のとき, then the 予約 API shall 400 で拒否し、10分後と14日後は受け付ける
5. If 予約用の認証情報が未登録か再度の許可が必要なアカウントによる作成と置き換えのとき, then the 予約 API shall それぞれの識別子つきの 409 で拒否し、予約を保存しない
6. If 待機中の予約が5件あるアカウントによる作成のとき, then the 予約 API shall スレッドの投稿の件数によらず 429 で拒否する

### Requirement 2: 予約の一覧・取得・置き換え

**Objective:** As a 利用者, I want 自分の予約を一覧し、内容を確認して直したい, so that 予約を管理できる

#### Acceptance Criteria

1. When 予約の一覧が要求されたとき、the 予約 API shall 自分の予約を状態で絞り込み、件数の上限とカーソルを指定して取得でき、他のアカウントの予約を含めず、続きがあるときはカーソルを返す
2. When 自分の待機中または失敗の予約の内容が要求されたとき、the 予約 API shall 作成時と同じ形の投稿内容と状態と、添付した画像を番号ごとに返す
3. If 他人の予約、または待機中でも失敗でもない予約の内容が要求されたとき, then the 予約 API shall 404 を返す（ただし実行中の予約は 409 で拒否する）
4. When 失敗の予約の内容が要求されたとき、the 予約 API shall 内容と画像を取得でき、状態が失敗と示されるようにする
5. When 自分の待機中の予約の置き換えが要求されたとき、the 予約 API shall 作成と同じ入力で実行時刻と内容と画像ごと置き換え、置き換え前の画像を削除する
6. If 実行中の予約の置き換えが要求されたとき, then the 予約 API shall 409 で拒否する
7. If 範囲外の実行時刻での置き換えが要求されたとき, then the 予約 API shall 400 で拒否し、内容を変えない

### Requirement 3: 取消と履歴の削除

**Objective:** As a 利用者, I want 予約の取消と失敗した履歴の削除をしたい, so that 不要な予約や履歴を整理できる

#### Acceptance Criteria

1. When 待機中の予約の取消が要求されたとき、the 予約 API shall 予約を取り消し、画像も削除する
2. When 失敗の予約の削除が要求されたとき、the 予約 API shall 履歴として削除する
3. If 実行中の予約の取消または削除が要求されたとき, then the 予約 API shall 409 で拒否する

### Requirement 4: 予約用の認証情報

**Objective:** As a 利用者, I want 予約に必要な権限だけを Bluesky で許可し、いつでも取り消したい, so that パスワードを渡さずに予約投稿を使える

#### Acceptance Criteria

1. When 認可の開始が要求されたとき、the 予約 API shall ログイン中のアカウントを指定した署名つきの要求を送る
2. When 認可が完了したとき、the 予約 API shall 得た更新用トークンと DPoP の鍵を暗号化して登録し、戻りを許可を始めたページへ渡して完了させる
3. If 認可を始めたアカウントと違う戻り、使用済みの戻り、発行元の違う戻り、拒否の戻り、または持ち主の違うトークンのとき, then the 予約 API shall 何も登録しない
4. When 認可の戻り先が処理されるとき、the 予約 API shall 既知の項目だけを設定のページのフラグメントへ移して 303 で転送し、別のオリジンへ向かうパスを受け付けない
5. If 完了が未ログインのとき, then the 予約 API shall 401 を返し、拒否の戻りでは保存せずに拒否の分類を返す
6. When 認証情報の状態が要求されたとき、the 予約 API shall 登録の有無・再度の許可の要否・有効期限の目安を取得し、登録状態のヒント cookie に保存する
7. The 予約 API shall 有効期限の目安を、最後の使用か最も遅い待機中の実行時刻から30日と許可から2年の早い方とし、再度の許可が必要なときは付けない
8. When 認証情報の削除が要求されたとき、the 予約 API shall 待機中の予約と失敗の履歴を画像とともに削除し、ヒント cookie を失効させる
9. If 実行中の予約があるとき, then the 予約 API shall 認証情報の削除を 409 で拒否する
10. When 認可の完了またはログインの変更があったとき、the 予約 API shall 応答でヒント cookie を失効させる

### Requirement 5: 制限値

**Objective:** As a 実装者, I want 検証に使う制限値を取得したい, so that 画面と API で同じ基準を使える

#### Acceptance Criteria

1. When 制限値が要求されたとき、the 予約 API shall 実行時刻の範囲・待機中の予約の上限・画像の合計容量の上限・投稿の件数の上限を、検証に使う値と同じ値で返す
2. If 未認証で制限値が要求されたとき, then the 予約 API shall 401 を返す

### Requirement 6: 共通の検証・応答・安全性

**Objective:** As a 開発者, I want 入力の検証とエラー応答を一貫させ、秘密が漏れないようにしたい, so that クライアントが失敗を判断でき、認証情報が守られる

#### Acceptance Criteria

1. The 予約 API shall 入力の検証と API 文書を、1つのスキーマ定義から導出する（作成・一覧・取得・置き換え・取消の入力スキーマが文書の生成に使う定義と同一）
2. The 予約 API shall エラー応答を400・401・404・409・429・500・502に分類し、すべての応答にキャッシュを禁止する指定を付ける（未認証は401、不正な入力は400、他人の予約は404）
3. If 認可に失敗したとき, then the 予約 API shall トークン・認可コード・鍵を含む文字列を応答とログに出力しない
4. The 予約の API の経路 shall atproto のライブラリを静的に読み込む箇所を0件にする
