# Implementation Plan

実装順: `surveys`（題・説明の廃止）→ この spec の 1〜3.4 → `survey-operations` 全体 → この spec の 3.5・4.1

- [ ] 1. Foundation: 結果の保管先の宣言と共有の部品
- [ ] 1.1 結果の保管先をテンプレートとテスト設定に宣言する
  - 本番用のテンプレートに、アンケートの結果専用のバケット（`skyshare-survey-results`）を、用途を表すバインディング名（`SURVEY_RESULTS`）で足し、コメントを現行の説明に合わせる
  - route 層のテスト設定にも、同じバインディングのテスト用バケットを足す
  - 生成した設定で、develop は末尾に `-develop` が付いた名前、プレビューは develop と同じバケットを指すことを確かめる（既存の生成の仕組みを使い、生成の部品は変更しない）
  - 結果の保管先の作成や、実バケットを読むための接続の付与はこのタスクで行わない
  - 注意: テンプレートに `SURVEY_RESULTS` を足すと、本番の `skyshare-survey-results` が未作成の環境では `wrangler deploy` が失敗する（作成は運用者の作業）
  - 完了の状態: 生成した本番・develop の設定に、結果専用のバケットが宣言され、リポジトリには統計ファイルが一切無い
  - _Requirements: 5.6, 8.1, 8.2, 8.3, 8.4_

- [ ] 1.2 結果の保管先の構造的な型を共有の型に足す
  - 結果の保管先が使う操作（存在確認・読み取り・条件付き書き込み）だけを、既存の予約画像の型を変えずに構造的に定義する
  - 条件に合わない書き込みが「書かれなかった」ことを返す形にする
  - route・unit テストが共通で使う、失敗を注入できる結果の保管先のフェイク（書き込みを失敗させる・条件の判定を再現する）をテスト用の部品として用意する
  - 完了の状態: 型検査が通り、フェイクが同じ形で作れて、書き込みの失敗を注入できる
  - _Boundary: cfTypes.ts, tests/support_
  - _Requirements: 7.1, 7.3_

- [ ] 1.3 (P) 終了の判定を足す
  - 終了時刻ちょうどで「終了した」になる判定を、既存の「現在のアンケート」の判定と同じ時刻の扱いで足す
  - 完了の状態: 終了時刻の直前・ちょうど・直後の判定が単体テストで確かめられている
  - _Boundary: period.ts_
  - _Requirements: 2.2, 2.3, 6.5_

- [ ] 1.4 (P) 回答の読み取りを足す
  - 指定のアンケートの回答の本文を、すべて読み取る操作を足す（削除の操作は既存のものを使う）
  - 完了の状態: 回答が 0 件・複数件の読み取りが route テストで確かめられている
  - _Boundary: store.ts_
  - _Requirements: 2.1_

- [ ] 2. Core: 形式・集計・保管・有効判定
- [ ] 2.1 統計ファイルの形式と検証の規則を定める
  - 結果・目録・可視フラグの 3 種の形式と版、R2 のオブジェクトの構成（キー名）を 1 つの検証の規則として定め、書く側と読む側が同じものを使えるようにする
  - 定義にない項目（件数・回答者数・回答日・アンケート全体の題・説明など）を拒否する。割合の範囲と桁、識別子の重複、未知の版も拒否する
  - 検証の結果は成否だけを返し、読んだ本文を失敗の内容に含めない
  - 旗が無い・不正なときは非表示として扱う読み手の規則を、同じ場所に定める。純粋関数 `resultMatchesIndexEntry(entry, result): boolean`（id・opensAt・closesAt が目録の記録と一致するとき真）と `isVisible(visibility: SurveyVisibility | undefined): boolean`（undefined や visible が true でないとき偽）を export する。`survey-results-public`（ビルド）と `survey-operations`（publish・status）は、読み手の規則の単一の実装としてこの 2 つを使う
  - ビルドとコマンドラインから読み込めるよう、Worker 専用の部品に依存させない
  - 完了の状態: 正常な 3 種は通り、未知の項目・未知の版・範囲外の割合・重複を含むものは拒否されることが単体テストで確かめられている。`resultMatchesIndexEntry` と `isVisible` の真偽の境界も単体テストで確かめられている
  - _Boundary: results/schema.ts_
  - _Requirements: 4.1, 4.2, 4.4, 4.5, 4.6, 4.7, 5.2, 5.3_

- [ ] 2.2 回答から結果を求める集計の規則を実装する
  - 設定のアンケートと回答の本文から、選択肢ごとの割合（回答者数が分母、小数点以下 1 桁、四捨五入）を求める
  - 複数選択は選択肢ごとに独立に求め、「回答しない」の選択肢は結果に含めない。しきい値による伏せ字や合計の補正はしない
  - 読めない行・設定に合わない行・「回答しない」を含む行は回答者に数えない。回答者が 0 なら結果を作らない
  - 質問の題・選択肢の文言を設定から複写し、アンケート全体の題・説明は含めない
  - 完了の状態: 単一選択・複数選択・0 件・除外される行・丸めの境界の単体テストが通り、出力が 2.1 の検証を通る
  - _Depends: 2.1_
  - _Boundary: results/tally.ts_
  - _Requirements: 3.1, 3.2, 3.3, 3.4, 3.5, 3.6, 3.7, 4.3_

- [ ] 2.3 結果の保管の操作を実装する
  - 目録の読み取り（無ければ空、検証に通らなければ専用の失敗）、結果の存在確認、結果の上書き禁止の作成（既にあれば「ある」と返す）、目録への追記（読んだ版との比較交換。最大 3 回、尽きたら専用の失敗）を実装する
  - 書く前に必ず形式の検証を通し、可視フラグのキーには一切書かない
  - 完了の状態: workerd 上の route テストで、2 回目の作成が上書きしないこと、並行した 2 つの追記が両方残ること、不正な目録は上書きされず失敗すること、旗のキーに書かれないことが確かめられている
  - _Depends: 1.1, 1.2, 2.1_
  - _Boundary: results/store.ts_
  - _Requirements: 4.7, 5.4, 7.1, 7.3, 7.6_

- [ ] 2.4 (P) 機能の有効判定と API の入口の無効化を実装する
  - 回答の保存先と結果の保管先の両方が使えるときだけ有効とする判定を、実行時の唯一の判定として定める
  - 提示・回答・回答済みの API の前処理で、無効なら設定の取得より前に「設定が無い」ときと同じ 404 を返し、回答の保存先に触れない。認証・識別子の形式の判定順は変えない
  - アンケートの環境の型に結果の保管先を足す
  - 完了の状態: route テストで、保管先が無いと 3 つの操作が設定なしと同じ 404 を返して回答の保存先に触れず、有効なときは従来どおり動く
  - _Depends: 1.1, 1.2_
  - _Boundary: feature.ts, request.ts, env.ts_
  - _Requirements: 1.1, 1.2, 1.3_

- [ ] 2.5 (P) ビルドの旗に保管先の宣言の条件を足す
  - アンケート設定がある、かつ、生成済みの設定に回答の保存先と結果の保管先の両方が宣言されているときだけ、入口を出す旗を真にする
  - ビルド設定から、既に読み込んでいる生成済みの設定を使って判定を渡す
  - 完了の状態: 宣言なし・片方だけ・両方・設定なしの組み合わせの単体テストが通り、標準のテンプレートでは従来どおり旗が真になる

- [ ] 2.6 条件付き書き込みを検証用の保管先で早期に確かめる
  - 検証用（develop）のバケットで、上書き禁止の作成と読んだ版との比較交換が、workerd のテストと同じ結果（条件に合わない書き込みが書かれない）になることを確かめる。試験用に作ったオブジェクトは確認後に削除する
  - バケットが未作成・認証が無い場合は、確かめられなかった旨を記録し、後続の着手は止めないが、4.1 の完了条件に残す

- [ ] 3. Integration: 日次の手順と置き換え
- [ ] 3.1 日次の手順の入口と、集合の削除・無効時の動作を実装する
  - 機能が無効なら何にも触れずに戻る。設定が存在しない（変数が無い・空）ときは設定のアンケートを空として扱い、3.2a の掃除は実行する。設定が存在するのに読めないときは、掃除を含め何もせず例外の種類の名前だけを記録して戻る。設定にあり終了済みのアンケートだけを対象にし、設定に無いものは扱わない
  - 対象のアンケートごとに、回答済みの集合を、集計の成否と無関係に先に削除する（失敗は記録して続行）
  - 開始前・実施中のアンケートの回答・集合には触れない
  - 完了の状態: route テストで、無効なら R2 にも D1 にも触れない・終了前は何も変わらない・終了後は集合が消え回答は残る・設定に無いアンケートは扱われない、が確かめられている
  - _Depends: 1.3, 2.4_
  - _Boundary: daily.ts_
  - _Requirements: 1.4, 2.2, 2.4, 6.5, 6.6_

- [ ] 3.2 集計・保存・目録・回答の削除の本流を実装する
  - 目録に記録があり、結果が要るのに在る（または回答 0 件の記録）なら回答の削除だけを行う。記録が無ければ、回答を読み集計し、0 件なら（結果の有無を先に確かめた上で）目録に「結果なし」を足し、0 件でなければ結果を上書き禁止で作ってから目録に足す
  - 目録に「結果あり」とあるのに結果が無い場合は、回答が残っていれば作り直し、回答が無ければ空の結果で上書きせず、不整合として記録するだけにする
  - 結果が在って目録に記録が無い場合は、作り直さず目録に足してから削除する。回答の削除は、保存の成功を確認した後だけ。可視フラグには書かない（常に非表示で作る）
  - 完了の状態: route テストで、終了後に結果と目録ができ回答が消える・保存失敗なら回答が残る・0 件は記録して削除・繰り返しても同じ・結果既存なら上書きせず削除・目録に記録なしで結果既存なら足して削除・不整合の分岐、が確かめられている
  - _Depends: 1.4, 2.2, 2.3, 3.1_
  - _Boundary: daily.ts_
  - _Requirements: 2.1, 2.5, 5.1, 5.5, 6.1, 6.2, 6.3, 6.4, 7.2, 7.7_

- [ ] 3.2a 設定から外れた終了済みの記録の回答を掃除する
  - 設定の各アンケートの処理のあとで、目録を読み直し、各記録について、終了時刻が過ぎていて、かつ現在の設定に同じ識別子のまだ終了していないアンケートが無いときだけ、回答と回答済みの集合を識別子で削除する（冪等。`empty`・`result` の両方が対象。目録には何も書かない）
  - 設定に同じ識別子の未終了のアンケートがある（識別子の再利用）ときは触れない。設定が存在するのに読めないときは掃除しない
  - 記録ごとに独立して失敗を分け、識別子と例外の種類の名前だけを記録して次へ進む。毎日行う（目録は最大 200 件、1 件あたり削除 2 回）。目録が不正なら掃除だけを記録して終わる
  - 完了の状態: route テストで、設定に無く終了済みの記録の回答・集合が消える（`empty`・`result` の両方）・識別子の再利用では触れない・削除の失敗が他の記録を止めない・繰り返しても同じ・設定が無い状態でも目録の終了済み記録の回答が削除される・設定が不正なら削除しない、が確かめられている
  - _Depends: 3.2_
  - _Boundary: daily.ts_
  - _Requirements: 6.8, 6.9, 6.10, 6.11_

- [ ] 3.3 失敗の分離と記録の規則を実装する

  - 目録が不正なときは何も書かずに全体を中断して記録する
  - 完了の状態: route テストで、1 件の失敗が他のアンケートを止めない・ログに本文が出ない・不正な目録では何も書かれず中断する、が確かめられている
  - _Depends: 3.2, 3.2a_
  - _Boundary: daily.ts_
  - _Requirements: 7.4, 7.5, 7.6_
