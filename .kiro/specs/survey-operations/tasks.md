# Implementation Plan

前提（他の spec との順序）:

- `survey-results-aggregation` の統計ファイルの形式の部品と、結果の保管先の宣言が先に要る（2.2 の前提）。
- `survey-results-aggregation` の保持期限の削除は、この spec の 3.1 の完了まで待つ。
- `surveys` の設定の形式の変更（アンケート全体の題・説明の廃止。`surveys` の更新が担当）は、2.1 の前提である。
- この spec の 3.1 が完了すると、`survey-results-aggregation` の 3.5、その後に同 4.1 を進められる。依存の向きは一方向である。
- 実装順: surveys の設定形式変更 → aggregation 1〜3.4 → この spec の 3.1 まで → aggregation 3.5・4.1。この spec の 3.2 以降は自身の依存に従って進める。
- 手順書（運用手順書（skill）と開発の手引き）は、各コマンドの実装と同じ変更で直す。別のタスクにしない。開発の手引き（`docs/DEVELOP.md`）でこの spec が直す見出しは、3.x アンケート（3.1 の `hack/` の説明と 3.2）、5.1 の配備の節、5.4 main への取り込み前のアンケート除去、6.2 の `SURVEY_CONFIG` の行だけにする。`survey-results-public` が直す CI/CD の認証情報・R2・プレビューの各節と 6.5 の `SURVEY_RESULTS` の行には触れない（編集の重なりを避ける）。

- [ ] 3.3 設定からの除去（自動と運用者による）を通す

  - skill と DEVELOP.md に、期間不一致ではなく目録の記録が無い環境への案内を書く。現在の設定をその環境へ配備し、日次集計を待つ。目録の取得失敗は認証・接続・形式を直して再実行する。DEVELOP.md 5.4 は両環境で集計済みだけ除去する新規則に合わせる

  - DEVELOP.md の運用手順に、集計が繰り返し失敗した場合の R2 復旧手順を書く。前提として develop 用バケット `skyshare-survey-results-develop` が最初に作成済みであることを明記する。運用者は R2 の結果本体と目録を退避してから直接確認・修正し、本体の形式不正・目録との内容不一致、目録が `result` を示すのに本体が無い場合などを直す。修正後は共有スキーマと本体・目録の一致を確認し、集計を再実行して `status` で復旧を確かめる。CLI の強制指定は設けない
  - skill に、すでに集計済みのアンケートの終了日時を延ばさず、続けたいときは新しい識別子で登録することを書く
  - 完了の状態: 偽の外部を使った単体テストで、除去・残す（案内つき）・片方の目録の失敗で何も変えないこと・全除去での変数の削除・対象なし・運用者による除去の各分岐が確かめられている
