# Implementation Plan

前提（他の spec との順序）:

- `survey-results-aggregation` の統計ファイルの形式の部品と、結果の保管先の宣言が先に要る（2.2 の前提）。
- `survey-results-aggregation` の保持期限の削除は、3.1 の完了まで待つ（この CLI が保持期限の判定を使わなくなるのが 3.1）。
- `surveys` の設定の形式の変更（アンケート全体の題・説明の廃止。`surveys` の更新が担当）は、2.1 の前提である。
- この spec の 3.1（`hack/survey-cli/lifecycle.ts` から `retentionExpired` と回答の保存先（D1）への参照を削除する）が終わると、`survey-results-aggregation` の 3.5 と 4.1 を進められる。
- 実装順: surveys(題・説明の廃止) → aggregation 1〜3.4 → この spec 全体 → aggregation 3.5・4.1
- 手順書（運用手順書（skill）と開発の手引き）は、各コマンドの実装と同じ変更で直す。別のタスクにしない。開発の手引き（`docs/DEVELOP.md`）でこの spec が直す見出しは、3.x アンケート（3.1 の `hack/` の説明と 3.2）、5.1 の配備の節、5.4 main への取り込み前のアンケート除去、6.2 の `SURVEY_CONFIG` の行だけにする。`survey-results-public` が直す CI/CD の認証情報・R2・プレビューの各節と 6.5 の `SURVEY_RESULTS` の行には触れない（編集の重なりを避ける）。

- [ ] 1. Foundation: 検査の対象と純粋な部品
- [ ] 1.1 (P) 引数の解析と、CLI の検査・テストの置き場を用意する
  - 6 つのコマンドの引数を検証し、環境（本番・develop）・識別子・`--dry-run`・`--no-deploy`・リポジトリの指定を型のあるコマンドに変える。環境の必須・不要の組み合わせ、重複・未知の指定・強制の指定を使い方の失敗にする
  - CLI を型検査の対象に加え、テストの配置の説明（テスト方針の steering）に、CLI のテストは P0 ではなく被覆率の閾値を置かないことを書く。テスト方針の steering で直すのは `hack/` のテストの置き場の節だけにする
  - 完了の状態: 引数の単体テストで、すべての正しい指定が通り、不正な指定がすべて使い方の失敗になり、型検査が CLI を含めて通る
  - _Boundary: args, 型検査の設定, テスト方針の steering_
  - _Requirements: 1.1, 1.2, 1.6, 1.7, 2.1, 2.2, 2.4, 2.5, 5.7, 7.6_

- [ ] 1.2 段階・除去・配備先・表の行の純粋な判定を作る
  - 現在の時刻・設定の期間・目録の記録から 6 つの段階を決める。設定に無く目録にだけあるアンケートも表の行にし、開始時刻の昇順で並べる。題は持たない。可視フラグの状態は「公開・非公開・不正」の 3 通りで受け取り、不正は段階を `hidden` にしたうえで、行の末尾に `!invalid-visibility` を付ける
  - 両環境の集計の有無から、除去の対象と、残すものと足りない環境を決める。運用者による除去の可否（開始前は可、開催中は拒否、終了済みは両環境で集計済みのときだけ可）を決める
  - 最新のリリースブランチ（最後に更新されたもの。同時刻は名前の降順）と、日本標準時の日時の表記を作る
  - 保持期限の判定や回答の行の確認を使わない。旧い判定は 3.1 まで残し、この段階では新しい判定を追加するだけにする
  - 完了の状態: 単体テストで、開始・終了ちょうどの境界、不正な可視フラグが `hidden` で警告の印つきになること、集計済みでも終了前は時刻が優先されること、除去の組み合わせ（両方・片方・なし・開始前・開催中）、ブランチの選択（1 本・複数・同時刻・空）が確かめられている
  - 環境の型は 1.1 で定めたものを使う
  - _Boundary: lifecycle_
  - _Depends: 1.1_
  - _Requirements: 2.3, 3.1, 3.2, 3.3, 3.4, 3.5, 3.6, 3.7, 3.8, 3.9, 3.10, 3.15, 4.3, 4.4, 4.10, 5.3, 6.1, 6.3, 6.4, 6.6, 7.1, 7.2, 7.3, 7.4, 10.1, 10.3_

- [ ] 2. Core: 設定の変換と外部の操作
- [ ] 2.1 (P) 下書きの形式を新しい設定の形式に合わせる
  - 設定の整え直しからアンケート全体の題・説明を外し、質問ごとの題だけにする。登録・更新・開始日時の保持・変更なし・容量超過の動作を新しい形式で保つ
  - 下書きの固定データ（題・説明なしの新規、同じく識別子つきの更新、旧形式の拒否される例）を `tests/fixtures/survey-operation/` に新しく作る。旧い参照先は存在しないため、更新でなく作成である。`tests/fixtures/survey/` は `surveys` の担当で、ここでは作らず直さない
  - 前提: `surveys` の設定の形式の変更が完了していること。旧い入口が全体の題・説明を参照していないことを確かめてから外す（参照が残るなら 3.1 に統合する）
  - 完了の状態: 単体テストで、新しい下書きが登録・更新でき、旧形式の下書きが不正として拒否され、出力に全体の題・説明が出ない
  - _Boundary: config, 下書きの固定データ_
  - _Depends: surveys の設定の形式の変更_
  - _Requirements: 8.1, 8.2, 8.3, 8.4, 8.5, 8.6, 8.7_

- [ ] 2.2 (P) 結果の保管先の読み書きを作る
  - 指定した環境の目録・結果・可視フラグを、共有の検証の規則で読む。無いものは「無い」、形式が不正なものは不正として区別する。可視フラグは、無ければ非公開、検証に通れば共有の `isVisible` で公開・非公開を決め、形式が不正なら例外にせず「不正」の状態で返す（呼び出し側が警告の印と上書きに使う）。バケット名はテンプレートの宣言から読み、検証用の環境には接尾辞を付ける。「キーが無い」と判定する標準エラーの語句は 1 か所の定数にまとめ、4.2 で実機の値に確定する。外部の操作の型は、2.3 の分も含めてこの段階で全メソッド確定する
  - 可視フラグだけを、書く前に検証して書く。ほかのキーには書かない
  - 認証の失敗・利用不可・応答の不正を固定の種類に分け、外部の標準エラーや本文を例外に載せない。旧い入口が使う回答の保存先への問い合わせは、旧い入口が消える 3.1 まで残し、この段階では新しい操作を足すだけにする
  - 前提: `survey-results-aggregation` の形式の部品と保管先の宣言が完了していること
  - 完了の状態: 偽の実行関数を使った単体テストで、外部コマンドの引数、書き込み先のキーが可視フラグだけであること、可視フラグの無い・公開・非公開・不正の 4 通りの読み分け、「無い」と認証・利用不可の分類、本文が例外に載らないことが確かめられている
  - _Boundary: remote_
  - _Depends: survey-results-aggregation の形式の部品と保管先の宣言_
  - _Requirements: 1.5, 1.8, 1.9, 3.7, 3.8, 3.13, 3.15, 4.1, 4.2, 4.6, 4.9, 10.4_

- [ ] 3. Integration: 入口の流れと手順書
- [ ] 3.1 入口を新しい体系に組み替え、状態の確認と登録を通す
  - 引数の解析・設定の取得・変換・外部の操作をつなぎ、結果の組み立てを複数行に対応させる。状態の確認は設定と指定した環境の目録を合わせた表（見出しに設定の大きさと上限）を返し、可視フラグが不正な行の末尾に `!invalid-visibility` を付け（段階は `hidden`）、アンケートが無いとき・目録が不正なときの結果も定める
  - 旧い段階の判定・旧い除去の判定・保持期限の参照・旧い入口の流れ・回答の保存先への問い合わせ（外部の操作の旧い部分）を削除する。これで `survey-results-aggregation` の保持期限の削除が進められるようになる
  - 失敗の種類（使い方・不正・認証・利用不可・容量超過）の行に入力の本文や外部の文言が出ないようにする
  - 実装と同じ変更で、運用手順書（skill） の聞き取りと確認表から全体の題・説明を外し、下書きの参照先と状態確認の説明（6 つの段階）を直し、開発の手引き の 3.x アンケートの項と、6.2 の `SURVEY_CONFIG` の行の説明を新しい体系にする（ほかの見出しは上の前提のとおり触れない）
  - 完了の状態: 偽の外部を使った単体テストで、状態の確認の表・不正な可視フラグの警告の印・アンケートなし・目録の失敗・登録の成功と失敗・秘密の非表示が確かめられ、リポジトリに保持期限の判定と回答の保存先への問い合わせの参照が残らず、型検査が通る
  - _Depends: 1.1, 1.2, 2.1, 2.2, 2.3_
  - _Requirements: 1.3, 1.4, 1.5, 3.1, 3.11, 3.12, 3.13, 3.14, 3.15, 8.1, 8.6, 8.7, 8.8, 6.2, 9.2, 9.3, 9.4, 9.7, 9.11, 10.1, 10.2_

- [ ] 3.2 公開・非公開の切り替えと再配備の起動を通す
  - 対象の段階・結果の検証・配備先の決定を先に済ませ、可視フラグを書き（既に望む状態なら書かない）、続けて配備を起動する。集計前・結果なし・識別子なしを拒否または失敗にする。`publish` は結果を形式の検証に加えて共有の `resultMatchesIndexEntry` で目録と照合し、不一致や不正は `error: invalid` で公開しない。非公開への切り替えは結果が壊れていても通す。可視フラグが不正な形式でも `publish`・`unpublish` は拒否せず、「既に望む状態」とも見なさず上書きする
  - 配備先は開発用なら開発用のブランチ、本番なら最新のリリースブランチ。決まらないときは何も書かない。配備の起動の失敗は、書き換えが保存済みで再実行で配備だけ起動し直せることを示す。配備を起動しない指定と、書き換えのない確認の指定に対応し、確認の結果に起動先を示す
  - 実装と同じ変更で、skill に切り替えと再配備の手順（反映には再配備が要ること、完了は運用者が確かめること）を書き、開発の手引き の配備の節に再配備の起動を書く
  - 完了の状態: 偽の外部を使った単体テストで、各段階の拒否・結果が目録と一致しないときの `publish` の拒否・不正な可視フラグでの上書き・既に望む状態での配備だけの起動・配備先が決まらないときに何も書かれないこと・配備の失敗後の文言・各指定の動作が確かめられている
  - _Depends: 2.3, 3.1_
  - _Requirements: 1.6, 4.1, 4.2, 4.3, 4.4, 4.5, 4.6, 4.7, 4.8, 4.9, 4.10, 5.1, 5.2, 5.3, 5.4, 5.5, 5.6, 5.7, 5.8, 5.9, 9.1, 4.11_

- [ ] 3.3 設定からの除去（自動と運用者による）を通す
  - 両環境の目録を読み、読めなければ何も変えずに失敗する。自動の除去は終了済みで両環境が集計済みのものだけを除去し、足りない環境つきで残すものを示す。運用者による除去は、開始前は除去、開催中は拒否、終了済みは両環境で集計済みのときだけ除去し、設定に無ければ失敗する
  - 除去の結果アンケートが残らないときは設定の変数そのものを削除する。対象が無いときは成功として返し、除去と残した理由を結果に示す。残した理由が「未集計の環境がある」ときは、結果の末尾に手順書の項（集計されていない環境がある場合）への案内を添える
  - 実装と同じ変更で、skill に開催中の取り下げの手順（終了日時を更新して集計を待ち、除去する）と、専用の CLI 以外で直接書き換えない旨を書き、開発の手引き の 5.4 main への取り込み前の手順を新しい規則（両環境で集計済みのものだけ除去。終了の翌日以降に除去する・削除の失敗が出ていないか確かめる、は補助の案内として書き、残った回答は集計側の日次の枠が片付けると添える）に直す
  - skill と開発の手引き（5.4）に、`develop` の目録に記録が無い（`develop` で一度も集計されていない）ために `prune`・`remove` が残した・拒否したときの抜け道を書く: 「`gh workflow run deploy.yaml --ref develop -f dry_run=false` で `develop` を再配備し、翌日の日次の枠を待つ」。結果の `kept` の行の案内はこの項を指す
  - skill に、すでに集計済みのアンケートの終了日時を延ばさず、続けたいときは新しい識別子で登録することを書く
  - 完了の状態: 偽の外部を使った単体テストで、除去・残す（案内つき）・片方の目録の失敗で何も変えないこと・全除去での変数の削除・対象なし・運用者による除去の各分岐が確かめられている
  - _Depends: 3.1_
  - _Requirements: 2.3, 6.1, 6.5, 6.7, 6.8, 6.9, 7.5, 7.7, 7.8, 9.5, 9.6, 9.8, 9.9, 9.10, 9.11_

- [ ] 4.2 実機の確認と、運用中の設定の作り直し（運用者の作業）

  - 前提: 運用者が `gh`・`wrangler` にログイン済みで、検証用バケットに集計済みの結果があり、検証用の配備を手動で起動できること
  - 本番のリリースブランチの選択は、実在のブランチが現れてから確かめる。確かめられない項目は理由を記録し、完了にしない
  - 完了の状態: 実機の結果（または未確認の理由）と、作り直した設定の状態が記録され、判定の定数と 2.2 の単体テストの語句が実機の値に更新されている
