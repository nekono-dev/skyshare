# 要件書

## 概要

運用の資材（`scripts/`・`hack/`・`config/`・`.githooks/`・`.github/workflows/`）のコメントを、`.kiro/steering/comments.md` の基準に従って書き直す。書き直した後のコメントは、スクリプトや設定が今どう動き、どう使うか、そして非自明な理由を述べる。cc-sdd 導入前の仕組み、旧 spec への参照、要件番号、日付入りの経緯は残さない。

振る舞いは変えない。変えるのはコメントだけであり、スクリプトの実行結果も CI の挙動も変わらないことを保つ。

2026-11-08 時点の状態: 許容リスト（`config/comments/allowlist.json`）に、この spec が所有する違反が 43 件（30 ファイル）記録されている。内訳は、先頭ヘッダの欠落 17 件、行数の超過 11 件、箇条書きの超過 9 件、要件番号 5 件、`kiro` 1 件。シェルスクリプトとワークフロー YAML は自動検査の対象外のため、許容リストには無く、レビューで見る。

用語:

- **運用の資材**: ビルド・テスト・秘密情報の登録・開発環境の補助などを行うスクリプトと、その設定、CI の定義。
- **許容リスト**: 既存の違反のうち、まだ直していないものを、所有 spec と理由を付けて記録した一覧。
- **判別の語**: 禁止パターンに当たる語（spec 参照・cc-sdd・kiro・経緯の語など）の一覧の正本は `.kiro/steering/comments.md` の「書くもの・書かないもの」の節にある。この spec は一覧を参照するだけで、語を追加しない。

## 境界の文脈

- **対象内**:
  - `scripts/` 配下の `.ts`・`.mjs` のコメント（`scripts/architecture/commentRules.ts` を除く）。`.sh` はレビューで見る。
  - `hack/` 配下の `.ts` のコメント（`hack/survey-cli`）。
  - `config/` 直下の `.ts`・`.mjs` のコメント（`config/test/` を除く）。`.jsonc` はレビューで見る。JSON はコメントを持たないため対象外。
  - `.githooks/` のシェルスクリプトのコメント（レビューで見る）。
  - `.github/workflows/` の YAML のコメント（レビューで見る）。
  - `config/comments/allowlist.json` のうち、所有 spec が `comments-scripts-config` の項目。
- **対象外**:
  - `src/`・`tests/`・`config/test/` のコメント（他の comments-* spec）。
  - 生成物、文字列リテラル（UI 文言・エラー文言・ワークフローの値）、スクリプトの振る舞い、CI の挙動、ワークフローのトリガーやジョブの構成。
  - 基準（`.kiro/steering/comments.md`）と検査の規則（`scripts/architecture/commentRules.ts`）の内容。これらは comment-policy の成果物であり、この spec では変えない。
  - `scripts/architecture/commentRules.ts` のコメント。comment-policy が所有し、その違反を 0 件に保つ。許容リストの所有の割り当て（`ownerOf`）は `scripts/architecture/` のファイルを `comments-scripts-config` に割り当てるため、`commentRules.ts` もこの割り当てに入る。これは既知の例外であり、`ownerOf` は変えない。この spec は `commentRules.ts` を作業の対象にせず、その項目が出ても comment-policy の報告に回す。
  - ファイルの場所と責務。移動・改名・分割・統合はしない。
- **自動検査の範囲**: 自動検査（`scripts/architecture/commentRules.ts`）が読むのは `.ts`・`.tsx`・`.astro`・`.mjs` だけで、`comments.md` の「対象」と同じ。この spec の `.sh`（`scripts/`・`.githooks/`）、`.jsonc`（`config/`）、`.yaml`（`.github/workflows/`）、拡張子の無い `.githooks/pre-push` は自動検査の対象外で、基準をレビューで確かめるだけである。自動検査が通ったことを、これらの確認の代わりにしない。
- **隣接する期待**:
  - comment-policy: 基準と検査を判断の正本として使う。基準で判別しきれない箇所は、残して報告する。この spec は comment-policy に依存し、comment-policy の実装が終わるまで作業を始めない。
  - ops-tooling-layout・ops-config-secrets: 配置と責務の所有者。コメントに書く責務は、それらの spec が定めた現在の責務と食い違わせない。
  - 他の comments-* spec: `config/comments/allowlist.json` を共有する。この spec は、所有 spec が `comments-scripts-config` の項目だけを消す。他の所有の項目は変えない。全 comments-* spec は、許容リストを共有するため、一度に 1 つずつ（直列に）実行する。
  - 生成の入口（`config/orval.config.ts`・`scripts/build/build-openapi-document.ts`）: この spec はコメントの行だけを変える。comments-api-schema が比べる OpenAPI の JSON と生成物の基準は、この spec の変更の前の状態から保存したものを使う。そのため、この 2 ファイルは、comments-api-schema の基準の保存が済んでから変える。この spec では生成（`npm run codegen`・`apigen`）を実行しない。
  - 検証の範囲: この spec の完了の確認は、`npm run test:type`・`test:imports`・`test:unit`・`test:component`・`test:route`・`test:render` とする。`test:e2e` は、この spec では実行しない（最後の e2e は comments-api-schema が行う）。`test:lexicon` は、他の comments-* spec と同じく、この spec の検証に含めない。この環境では実行できる（確認済み）ため、導入は要らない。

## 要件

### 1. 先頭ヘッダ

**目的:** 運用者として、スクリプトや設定を開いたときに、何のためにあり、どう使うかを先頭で分かるようにしたい。ファイルを読み始める前に、責務と前提を把握できるようにするため。

#### 受入基準

1. The 運用の資材 shall 先頭に、目的を書いたブロックコメント（`/** … */`）を持つ。シェバン行の後にあってもよい。
2. The 先頭ヘッダ shall 目的を 1〜2 行で書き、現在の責務（何をするか）を述べる。
3. The 先頭ヘッダ shall 内容を 6 行以内、箇条書きを 3 件以内にする。
4. Where 起動の形式や主な引数がコードから読み取りにくい, the 先頭ヘッダ shall 使い方を書く。
5. The 先頭ヘッダ shall 責務の逐条の説明や、コードの言い換えを含まない。
6. Where 先頭の直後に import がある, the 先頭ヘッダ shall import より前に置く（import の後のブロックコメントを先頭として扱わない）。

### 2. 経緯と参照の除去

**目的:** 開発者として、今のコードを読むときに、もう無い仕組み・文書・決定に迷わないようにしたい。コメントの記述が現在の状態と一致するようにするため。

#### 受入基準

1. The 運用の資材 shall コメントに、spec への参照（`specs/` を含む記述）、要件番号、AC・FR・NFR のタグを含まない。
2. The 運用の資材 shall コメントから cc-sdd・kiro への言及を取り除く。言い換えでは責務が伝わらない場合に限り、残して報告する（3.3 に従う）。
3. The 運用の資材 shall コメントに、導入時期・旧実装・移行の経緯を述べる記述（「以前は」「かつては」など）を含まない。ただし、現在の振る舞いとして必要な記述（例: 前回の生成物を取り除く動作）は残す。
4. The 運用の資材 shall 日付入りの決定（日付と決定内容の組）を含まない。日付は、バッククォートで囲んだ入力例の中にだけ書く。
5. The 運用の資材 shall 担当者や期限のない TODO を含まない。
6. The 運用の資材 shall コードの言い換え（「値を返す」「変数を宣言する」など）を含まない。
7. The シェルスクリプトと GitHub Actions のワークフロー shall 2.1 から 2.6 の基準を、コメントに当てる（自動検査の対象外のため、レビューで確かめる）。

### 3. 残すコメント

**目的:** 保守する人として、コードを見ただけでは分からない理由と外部仕様の参照が消えないようにしたい。理由が消えると、同じ回避策を誤って外すおそれがあるため。

#### 受入基準

1. Where 回避策・外部仕様の癖・処理の順序の制約・セキュリティ上の理由がある, the 運用の資材 shall その理由を、現在形で、検証できる形で残す。
2. Where 外部仕様（公式仕様の URL、GitHub Actions や Wrangler の仕様、RFC など）を参照している, the 運用の資材 shall その参照を残す。
3. If 2.2 の言い換えで責務が伝わらない語（ツールの名前そのもの）が残るとき, the 運用の資材 shall その語を含むコメントを、判別の一覧として報告する（6.1 に従う）。

### 4. 振る舞いと CI の不変

**目的:** 運用者として、コメントの整理によって、スクリプトの動きも CI の結果も変わらないでほしい。日々の開発と配布の手順が、整理の前と同じに動くようにするため。

#### 受入基準

1. The 運用の資材 shall 変更をコメントの行に限る。コードの行、文字列リテラル、シェバン行、import・export、YAML のキーと値、シェルの命令は変えない。
2. The スクリプト shall 作業の前後で、終了コード・標準出力・標準エラー出力・生成するファイルの内容が同じである。
3. The GitHub Actions のワークフロー shall 作業の前後で、トリガー・ジョブ・ステップ・権限・環境変数・その値が同じである。
4. The 運用の資材 shall 作業の前後で、実行権限と、ファイルの場所と名前が同じである。

### 5. 許容リストの更新

**目的:** 開発者として、許容リストに残る項目が、実際に残っている違反と一致していてほしい。直した項目が残ったり、残すと決めた違反が消えたりしないようにするため。

#### 受入基準

1. When 所有 spec が `comments-scripts-config` の違反を直したとき, the 許容リスト shall その違反の項目（パスと規則の組）を消す。
2. If 所有 spec が `comments-scripts-config` の違反を残すと判断したとき, the 許容リスト shall その項目を、所有 spec と理由を付けて残す。残す項目の理由の文言は、残す理由（許容する例外であること）を明示する文に書き換えてよい。
3. The 許容リスト shall 所有 spec が `comments-scripts-config` 以外の項目を変えない。
4. The 許容リスト shall 機械的に作り直さず、項目の削除だけで更新する（作り直すと、新しい違反が黙って許容されるため）。ただし、5.2 で残す項目の理由の文言の書き換えだけは例外とする。理由の文言を変えるのは、この場合だけである。
5. The 検査の規則と基準 shall この spec の作業で変えない。

### 6. 判別の報告

**目的:** レビューする人として、判断が分かれたコメントと、作業の全体の結果を一覧で確かめたい。残したことや削ったことが、黙って行われないようにするため。

#### 受入基準

1. When 判別に迷って、禁止パターンに当たる語や経緯の記述を残したとき, the 作業の報告 shall そのファイル・行・残した理由を一覧にする。
2. The 作業の報告 shall 書き換えたファイルの数、取り除いた違反の数、残した違反の数、許容リストの項目の増減を示す。
3. The 作業の報告 shall 検査の結果（所有パスの違反が 0 件であること、許容リストの所有項目が残っていないこと、または残した項目の一覧）を示す。
