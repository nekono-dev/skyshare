# 要件書

## 概要

`src/` の依存規約を機械で検査する仕組みを作る。現状は規約が steering に書かれているだけで、違反が増え続けている（2026-11-01 の実測: `lib` の UI 依存 6 ファイル、循環 2 件、相対 import 311 件）。本 spec は、検査の規則と、既存違反の許容リストと、失敗の扱いを定める。違反の修正は後続の spec が行う。利用者に見える振る舞いは変えない。

用語:

- **領域**: `src/lib/<領域>/`、および `src/components/<領域>/<Name>/`（部品フォルダ）。
- **検査**: 本 spec が作る依存規則の検査。
- **許容リスト**: 既存の違反のうち、後続の spec で直すものの一覧。

## 境界の文脈（任意）

- **対象内**: 依存の向き・`lib` の UI 非依存・循環・領域をまたぐ相対 import・`../` の段数・`.js` 拡張子の混在の検査。許容リスト。検査の npm スクリプトと CI での実行。検査規則のステアリングへの明文化。
- **対象外**: 違反の修正（`src-cycles`・`src-lib-ui-boundary` などが行う）。検査ツールの選定と CI のジョブ構成（設計で決める）。`.js` 拡張子の統一の向き（設計で決める）。テストの方針（`testing.md`）。`scripts/` の運用ツール。
- **隣接する期待**: 後続の spec は、許容リストから該当項目を消すことで違反の解消を示す。テストの件数と結果は変えない（`test-foundation` の範囲）。
- **`libLayer` との紐づけ**: `lib-layers` の `libLayer` 規則（`lib` の基盤から業務への import を違反とする規則）は、本 spec の依存規則の検査（要件 1・要件 7）に含めて `npm run test:imports` で実行する。紐づけ先は `lib-layers` の要件 2.1（基盤は業務を import しない）と要件 3.1（許容リストに無い基盤→業務の import を `test:imports` が失敗させる）。層の対応表と許可する辺は `lib-layers` が定め、本 spec は検査の入口と許容リストの枠組みを提供する。

## 要件

### 1. 依存の向きの検査

**目的:** 開発者として、依存の向き（`pages` → `lib` → `util`）に反する import を検査で知りたい。層を越えた依存を増やさないため。

#### 受入基準

1. When 検査が実行されたとき, the 検査 shall `src/lib/` 内の、`src/components/` を参照するすべての import を違反として報告する。
2. When 検査が実行されたとき, the 検査 shall `src/lib/` 内の、`src/pages/` を参照するすべての import を違反として報告する。
3. When 検査が実行されたとき, the 検査 shall `src/util/` 内の、`src/lib/`・`src/components/`・`src/pages/` のいずれかを参照するすべての import を違反として報告する。

### 2. `lib` の UI 非依存の検査

**目的:** 開発者として、`lib` が UI のパッケージに依存しないことを検査で知りたい。業務の判断を画面なしでテストできるようにするため。

#### 受入基準

1. When 検査が実行されたとき, the 検査 shall `src/lib/` 内の、名前が `react` で始まるパッケージ（`react-easy-crop` を含む）の import を違反として報告する。

### 3. 循環 import の検査

**目的:** 開発者として、モジュール間の循環 import を検査で知りたい。変更の影響範囲と読む順番を分かりやすくするため。

#### 受入基準

1. When 検査が実行されたとき, the 検査 shall `src/` 内のモジュール間の循環 import を違反として報告する。
2. Where 循環が許容リストに載っているとき, the 検査 shall その循環を新しい違反として報告しない。

### 4. 領域をまたぐ import の表記

**目的:** 開発者として、領域をまたぐ import の書き方を統一したい。どの領域に依存しているかを import の文から読み取れるようにするため。

#### 受入基準

1. If 異なる領域のモジュールを相対パスで import しているとき, then the 検査 shall その import を違反として報告する。
2. While 取り込み元と取り込み先が同じ領域にあるとき, the 検査 shall 相対 import を許容する。
3. If 相対 import が `../` を 3 段以上含むとき, then the 検査 shall その import を違反として報告する。
4. The 検査 shall `.js` 拡張子の付け方が設計で定めた方式と異なる import を報告する。

### 5. 型だけの import

**目的:** 開発者として、型だけの import も同じ規則で検査したい。実行時には現れない依存の循環や表記の揺れを見逃さないため。

#### 受入基準

1. The 検査 shall 要件 1 から 4 の規則を、型だけの import（`import type`）にも値の import と同じように適用する。

### 6. 許容リスト

**目的:** 開発者として、既存の違反を一覧にして新しい違反だけを止めたい。既存の違反を直しながら増加を止めるため。

#### 受入基準

1. When 検査で見つかった違反が許容リストに載っているとき, the 検査 shall その違反を失敗として報告しない。
2. If 検査で見つかった違反が許容リストに載っていないとき, then the 検査 shall その違反を失敗として報告する。
3. The 検査 shall 許容リストの各項目が、その項目を解消する spec の ID を持っていることを確認する。
4. When 許容リストに載った違反がコードから消えているとき, the 検査 shall その項目を解消済みの古い項目として報告する。

### 7. 実行の入口と CI

**目的:** 開発者として、検査を 1 つの入口から実行し、CI でも止めたい。違反がマージの前に見つかるようにするため。

#### 受入基準

1. The system shall 検査を実行する npm スクリプトを 1 つ提供する。
2. If 許容リストに載っていない違反が見つかったとき, then the npm スクリプト shall 失敗の終了状態で終了する。
3. When CI が実行されたとき, the CI shall 検査を実行し、検査が失敗したらビルドを失敗させる。
4. The 検査 shall `src/` 配下のファイルを変更しない。

### 8. 規約の明文化

**目的:** 開発者として、検査の規則がステアリングに書かれていてほしい。規則の根拠を人間が読んで確かめられるようにするため。

#### 受入基準

1. The ステアリング（`structure.md`） shall 次の規則を明記する: 循環の禁止、`lib` の UI 非依存、領域をまたぐ相対 import の禁止、`../` の段数の上限、`.js` 拡張子の統一の方針。

### 9. 振る舞いと既存の検証の不変

**目的:** 利用者として、検査の追加で画面や API の振る舞いが変わらないでほしい。機能が壊れていないと分かるようにするため。

#### 受入基準

1. The 検査 shall 利用者に見える画面と API の振る舞いを変えない。
2. When 検査が追加されたとき, the 既存のテストスイート shall 追加前と同じ結果を保つ。

### 10. 想定の構成からの独立

**目的:** 開発者として、検査が想定の構成（リファクタリングの目標）に合わせて作られないようにしたい。根拠のない配置を検査が強制しないようにするため。

#### 受入基準

1. The 検査 shall 規則の根拠を steering（`structure.md`）に書かれた規約だけに限り、想定の構成を根拠にした規則を持たない。
2. The 検査 shall 特定のファイル・フォルダの存在、名前、配置を要求しない。
3. The 規則の追加・変更・緩和 shall steering の改訂と同じ変更で行い、想定の構成を理由にしない。
