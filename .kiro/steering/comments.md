# コメントの基準

コメントは、コードを読む人（人間・AI エージェント）が、現在の振る舞いと理由を素早く判断するために書く。経緯・要件・作業の記録は書かない（それらは `.kiro` の brief・spec・roadmap に置く）。

## 対象

- 対象: `src`・`scripts`・`hack`・`tests`・`config` の `.ts`・`.tsx`・`.astro`・`.mjs`。
- 除外: 生成物（`src/client/**`）、`*.d.ts`、テストの fixture。
- 文字列リテラル（UI 文言・エラー文言）は対象外。
- 自動検査の対象外（レビューで見る）: `.githooks`・`.sh` などのシェルスクリプト。

## 先頭ヘッダ

各モジュールの先頭に、ブロックコメント（`/** … */`）で目的を書く。

- 目的を 1〜2 行で書く。
- 制約（不変条件・外部仕様・動作の前提）がある場合だけ、箇条書きを最大 3 項目足す。
- ヘッダ全体は 6 行以内。
- 責務の逐条の説明や、コードの言い換えは書かない（コードを読めば分かることは書かない）。
- シェバン行と、Astro のフロントマター（`---`）の後にあってもよい。import の後に置かない。
- `//` の行コメントでは書かない。

```ts
/**
 * 予約投稿の実行（Cron）から呼ばれる、投稿 1 件分の書き込み。
 *
 * - D1 の状態を更新する前に、外部への書き込みを行う（冪等性のため）。
 * - Free の CPU 制限（10ms）のため、`@atproto` を読まず fetch の XRPC だけを使う。
 */
```

## 書くもの・書かないもの

書く（残す）:

- 非自明な理由: 回避策、外部仕様の癖、順序の制約、セキュリティ上の理由。理由は現在形で、検証できる形で書く（例: 「Free の CPU 10ms のため」）。
- 公開 API の使い方のうち、シグネチャから分からないこと（単位・境界値・失敗のしかた・副作用）。
- 外部仕様への参照（公式の仕様の URL、lexicon 名、RFC）。

書かない:

- 経緯（導入時期・旧実装・移行・「以前は」「かつては」）。
- spec・要件・受入基準への参照（`specs/...`・要件番号・`[spec/AC-n]` などの AC・FR・NFR タグ）。
- cc-sdd・kiro・spec 駆動開発への言及。
- 日付入りの決定（「2026-10-31 に決めた」）。現在の制約として書き直す。
- コードの言い換え（「値を返す」「変数を宣言する」など）。
- 担当者や期限のない TODO。

日付は、バッククォートで囲んだ入力例の中だけ書いてよい（例: `` `2026-01-01T00:00:00Z` ``）。

## API スキーマの説明文（生成物に出る文字列）

`src/lib/api/schema` の route の `summary:`、zod の説明（`description`）は、生成物（`src/client/openapi`）の JSDoc に出る。schema ファイルの JSDoc は生成物に出ない。

- `summary` と `description` は 1 行で、現在形で、そのエンドポイントや項目が何かを書く。
- 制約（最小・最大・件数など）は文章ではなく zod で書く。zod の制約は生成物に自動で出る。
- 上の禁止パターン（spec 参照・要件番号・AC・cc-sdd・kiro・日付）は、この文字列にも当てる。

## 検査

- `tests/unit/scripts/commentRules.test.ts` が、次を検査する: 先頭ヘッダの有無・行数・箇条書きの数、禁止パターン、コメント中の日付。
- 検査の本体は `scripts/architecture/comment-rules.ts`（文字列の判定だけを行う）。
- 許容リスト `config/comments/allowlist.json` には、基準の例外を、所有 spec（`comments-*`）と理由を付けて記録する。既存の違反は全て解消済みで、残るのは言い換えると意味が伝わらない語を含む例外（`scripts/agent/kiro-gate.mjs` の起動例のパス）だけである。
  - 新しいコードは違反を増やさない。テストが新しい違反を失敗にする。
  - 違反を直したら、許容リストから項目を消す。解消済みの項目が残っていると、テストが失敗する。
  - 許容リストを機械的に作り直す（`npx tsx scripts/architecture/comment-rules.ts --emit-allowlist`）のは、規則を追加したときだけ。作り直すと、新しい違反も黙って許容されるため、通常の修正では使わない。
- 禁止パターンに当たる語が正当な用法のときは（例: 「旧」「移行」を製品の用語として使う場合）、テストで失敗にせず、レビューで判断する。

## 例

良い例（先頭ヘッダと、理由を書いたインラインコメント）:

```ts
// Safari は `keydown` の変換中（IME）に `Enter` を送るため、変換中の入力は確定として扱わない
if (event.nativeEvent.isComposing) return
```

悪い例（経緯と spec 参照が混ざる）:

```ts
// 2026-09-30 に決定（specs/post-composer の要件 2.3）。以前は Enter で送信していた
if (event.nativeEvent.isComposing) return
```

## 関連

- 規約の全体（構造・命名・import）: `tech.md`・`structure.md`
- テストの方針: `testing.md`
- 作業の取り決め（判断の置き場所）: `CLAUDE.md`
