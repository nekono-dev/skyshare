# architecture と PoC の手順

`docs/architecture.md`（アーキテクチャ設計書）、機能のくくりごとの `docs/architecture/<くくり>.md`、`poc/<テーマ>/README.md`（PoC）を扱うときの手順と判断基準である。ルールの一覧は `rules.md`、雛形は `templates/architecture.md`・`templates/poc-readme.md` にある。

## 1. 位置づけ

- architecture.md は **下流の文書**である。正本は spec と PoC であり、architecture.md は両者の内容を人間が読める形に要約して構造を示す。矛盾したときは spec を正とする。
- 書けるのは、**根拠のある確定した内容だけ**である。根拠は spec 名か `poc/<テーマ>` で、信頼と検証・技術基盤・横断的制約の各行に必ず書く（S013 が実在を検査する）。根拠のない決定は書けない。
- 複数の spec にまたがる流れ・境界・技術基盤の理由は、architecture が単独の記述を持てる（機能・信頼と検証・技術基盤）。個別の値やルールは spec にあり、architecture に複製しない（W014 が重複を検出する）。同じ事実は 1 か所にだけ書く（全体とくくりの文書の両方に書かない）。
- 経緯・却下案・日付・検証手順は書かない（W009）。PoC の実測の詳細は `poc/<テーマ>/` に置く。

## 2. 新規開発の手順

1. **構想の聞き取り**: サービスの構想を聞く。アーキテクチャの案が出ても確定扱いにせず、検証すべき仮説として扱う。
2. **PoC**: 技術的なリスク（外部サービスの挙動・性能・料金枠・認証方式など）を `poc/<テーマ>/README.md` の「4. 検証項目」に仮説と合格基準として書き、検証して結果（合／否）を記入する。PoC のために spec は作らない（spec は確定した仕様だけを書く文書である）。
3. **確認と提案**: 結果を人間へ提示し、構想の修正や検証項目の追加を受ける。**修正や追加があれば 2 へ戻る**。README は最新の状態に上書きし、履歴は git に任せる。終了条件は、全検証項目に結果が付き、人間が結論を承認したことである。
4. **spec の作成**: 確定した内容で `specs/` を作る（SKILL.md の手順どおり）。実装中に仮説が崩れたら 2 へ戻る（反映先は既存 spec）。
5. **architecture の作成**: 内部の構成要素の数が閾値（初期 8 個）未満なら `templates/architecture.md` から 1 ファイルで、以上なら `templates/architecture-grouped/` から全体とくくりの文書を作る（6 節）。根拠は spec か PoC とする。
6. **承認**: 内容を人間へ提示し、承認を得てから確定する（機械検証できないため、手順として守る）。`npm run lint:spec` を通す。
7. **PoC の完了**: 反映先 spec の全タスクが完了したら、5 節の手順で根拠を spec へ付け替え、PoC を削除する。

## 3. 既存プロジェクトの手順

PoC は必須ではない。根拠はすべて spec にする。

1. **現状の把握**: `npm run lint:spec -- --status` で spec の状態を確認し、`npm run lint:spec` を通す。全タスクが完了した spec は、構成表のパス・テストの実在で実装との乖離を検出する（S006〜S008）。
2. **architecture の作成**: 雛形から作る（1 ファイルかくくり別かは 6 節）。実装と spec を調査し、構成要素・外部インターフェース・機能を spec に基づいて書く。
3. **承認**: 内容を人間へ提示し、承認を得てから確定する。
4. **再検証の要否の判断**: 次のときは再検証が必要になりうる。人間と相談して決める。
   - lint が実装との乖離を検出した（S006〜S008）。
   - 依存や実行環境の版が変わり、前提とした挙動が変わりうる。
   - 外部連携や構成要素を追加する。
5. **再検証が要るとき**: 新規開発の 2・3 の反復を行う。反映先は既存の spec とする。結果に基づいて spec を更新し、architecture.md を更新する。

機械で検出できるのは、architecture ↔ spec の突合（S012・S013）と、spec ↔ 実装の整合（S006〜S008）である。**他コンポーネントとの噛み合いや、挙動が設計どおりかは機械では判定できない**。再検証の判断は人間が行う。

## 4. PoC の README

`poc/<テーマ>/README.md` は固定の章立てで、先頭の「結論」「反映先」「制約値」だけを読めば足りる。手順・ログ・コードなどの詳細は README の外のファイルに置き、「5. 手順と結果」からリンクする（README の外は検査しない）。

- **1 PoC = 1 テーマ = 反映先 1 件**。複数の spec にまたがる仮説は、制約を持つ主たる spec を選ぶか、テーマを分ける。
- **状態は成果物から導出する**（宣言しない）。
  - 検証中: 結論が「- なし」、または検証項目の結果に「-」が残っている。
  - 反映待ち: 結論があり、反映先が「- なし」。
  - 反映済み: 反映先に spec がある。その spec の全タスクが完了していれば削除対象になる。
- 結論は、全検証項目の結果が「合」「否」になってから書く（F-P08）。
- 反映済みでない PoC は、設定の件数（初期 3）を超えて溜められない（S017）。

## 5. PoC の完了と削除

反映先 spec の全タスクが完了すると、S016（削除）と S018（根拠の付け替え）が指摘される。次の順で行う。

1. `npm run lint:spec -- --retarget-poc <テーマ>` で、根拠 `poc/<テーマ>` が反映先 spec に置き換わる差分を確認する。問題なければ `--write` を付けて適用し、`npx prettier --write docs` で表を整える。
   - 置換先は PoC の反映先（1 件）で一意に決まる。置換先の spec が行の主張を本当に支えているかは、目視確認の項目 5 で確認する。
2. `npm run lint:spec -- --check-poc-committed <テーマ>` を実行する。**終了コードが 0 でなければ削除しない**。
   - 1（未コミットの変更あり）／2（git の追跡外）のときは停止し、ユーザーにコミットを依頼する。ユーザーがそのセッションで明示的にコミットを許可している場合だけ、Claude がコミットしてから進める。
   - 削除しても内容は git の履歴に残る。履歴に入っていない PoC を削除すると、内容が失われる。
3. `poc/<テーマ>/` を削除し、`npm run lint:spec` を通す（根拠の付け替え漏れは S013 が検出する）。

### コミットの扱い

- リポジトリのスキルや CLAUDE.md に注意書きがない限り、コミットだけなら許可する（差分の消失を避けるため）。**push は含まない**。push はユーザーの許可を得る。
- 作業ブランチが本番向けでないか（CI の対象でないか）の判断は、本スキルの対象外である。リポジトリのスキルや CLAUDE.md の指示に従う。

## 6. architecture の書き方

### 6.1 1 ファイルかくくり別か

- 内部の構成要素の数（`npm run lint:spec -- --status` で確認できる）が閾値（`architecture.groupMinComponents`。初期 8）**未満**なら、`docs/architecture.md` 1 ファイルで書く。**以上**なら、機能のくくりにまとめ、全体 `docs/architecture.md` とくくりの文書 `docs/architecture/<くくり>.md` に分ける。どちらの形式も閾値で一意に決まる（S019）。
- 章立ては 1 ファイルでも、全体でも、くくりの文書でも**同じ 9 章**（1 目的と範囲／2 構成要素／3 システム構成／4 外部インターフェース／5 機能／6 データ／7 信頼と検証／8 技術基盤／9 横断的制約）。該当しない章は「- なし」と書く（構成要素は不可）。
- 全体では、2 章の**内部の構成要素が機能のくくり**になる（最終列は実装spec の代わりに、くくりの文書へのリンク）。4 章の外部インターフェースは方式と認証を省いた対応表になり、詳細はくくりの文書に書く。

### 6.2 機能のくくりの切り方

くくりは構成要素を束ねる単位で、**構成要素ごと・振る舞いごとに文書を作らない**。次の順で決める。

1. 構成要素を、「利用者（または運用者）から見て 1 つの目的で説明できるまとまり」に分ける。名前は目的で付ける（例: 通知の発行、通知の保管、通知の表示）。実装の層の名前だけ（「UI 部品」「API」）にしない。ただし、他のくくりから使われるだけの基盤（例: 共通基盤）は 1 つのくくりにしてよい。
2. すべての内部の構成要素を、**ちょうど 1 つ**のくくりに所属させる（S012・S020）。
3. くくり間の依存を求め、**循環しないこと**を確かめる（G009・F-A20）。循環するときは、循環の原因の構成要素を片方のくくりへ寄せるか、くくりを併合する。くくりの切り方が悪いことの検出であり、依存の向きを偽って通さない。
4. 1 つのくくりは内部の要素 2〜8 個（`architecture.groupComponents`）、くくりの数は 3〜10 個（`architecture.groupCount`）にする（F-A19）。要素が 1 つだけのくくり、互いに依存で結ばれない要素の集まり（関係図で孤立するもの）は、くくりとして成立しない。他のくくりへ併合する。
5. 他のくくりの要素を呼ぶ・呼ばれるときは、くくりの文書の 2 章に種別「他機能」の行で載せ、3 章の関係図に辺を引く。全体の関係図（3 章）の辺は、この辺から導いた依存と過不足なく一致させる（F-A20）。

### 6.3 何をどこに書くか

| 内容 | 置き場所 |
| ---- | -------- |
| くくりの一覧と責務、くくり間の依存、外部の要素と IF の対応（くくりの単位） | 全体 |
| 外部インターフェースの方式・認証、データ、信頼と検証、技術基盤、制約のうち、1 つのくくりの spec だけを根拠にする行 | そのくくりの文書 |
| 2 つ以上のくくりの spec を根拠にする行（横断的な制約・信頼・技術基盤） | 全体（S022 が置き場所を検査する） |
| 外部との出入りがある流れ、3 つ以上の要素にまたがる流れ | 流れを起こす側のくくりの文書。他のくくりの要素は他機能として参加者にする。3 つ以上のくくりにまたがる主要な流れは全体にも書く（参加者はくくり名） |
| 1 つの要素の内部の挙動、2 つの内部の要素だけの呼び出し | 書かない。その要素の spec の設計書（ワークフロー図）が正本（F-A17） |

- 外部の要素と IF は、**そのくくりの要素が実際に通信するものだけ**を、そのくくりの文書の 2・4 章に載せる。全体の 2 章に外部の要素を 1 回定義し、くくりの文書は自くくりから見た役割を責務に書く（全体と同じ文は重複扱い）。
- 機能は 1 文書に 5 件まで（`architecture.maxFunctions`）。全体の主要な流れだけを書き、薄い流れを増やさない（F-A18）。

### 6.4 書式

- 構成要素は **spec 単位ではなく実行単位・論理単位**で書く。複数の spec が 1 つの構成要素を実装してよい。すべての設計済み spec が、いずれかの構成要素の「実装spec」にちょうど 1 回現れる（S012。くくり別のときは、くくりの文書の内部の行）。
- 外部インターフェースは、システム境界を越える通信を 1 行 1 IF で書く。方式は通信の種類とデータ形式、認証は通信相手の確認方法を書く。受け取った内容の検証は「7. 信頼と検証」に書く（信頼の前提と検証手段を支える spec を根拠の列に書く）。
- 機能の関与は 2〜6 件にする。多いときは機能を分ける。外部の要素を含まない機能は、関与が 3 件以上ないと書けない（F-A17）。関与の集合と図のメッセージ名の集合がどちらも似ている機能（類似度 0.8 以上）は、同じ振る舞いの重複とみなして統合する（関与が同じでも、メッセージが違えば別の機能である。F-A14）。
- 図は構成要素の名前をそのままノード名にする。外部の構成要素は ID を `ext_` で始める。
- 図の説明の 1 文は、**文書ごとに固有の内容**にする（定型句を複数の文書に貼らない。W014 が重複を検出する）。
- 文は主語を省略せず、「。」で終わる 1 文で書く（W010・W012）。指示語（これ・それ・同様・上記など）は使わず、指す対象を名前で書く（W011）。
- 文書の行数は、全体と 1 ファイルが 400 行以内、くくりの文書が 300 行以内、機能（H3）が 80 行以内（F-A13）。超えるときは書く内容を絞る。構成要素が多いのに 1 ファイルで超えるときは、くくり別に分ける（S019）。

## 7. 目視確認（Claude が実施する）

`lint:spec` が合格した後、次を上から順に 1 回ずつ数える。判定は「該当数が 0」か否かのみで行い、好みの指摘は加えない。該当が 0 件なら変更しない（同じ入力には同じ結論になる）。くくり別のときは、全体とすべてのくくりの文書に対して数える。

1. 構成要素表の責務が、実装spec の要件の目的と食い違う行の数。
2. システム構成の関係図のエッジのうち、実装spec の設計に呼び出しの根拠がないものの数（外部とのエッジは数えない）。
3. 機能のワークフロー図のメッセージのうち、関与する構成要素の実装spec に対応する処理がないものの数。
4. 同じ事実を複数の章（または全体とくくりの文書）が述べている組の数。
5. 根拠が spec の行で、その spec の内容と値が食い違う行の数（PoC から付け替えた行を含む）。
6. 外部インターフェースの方式・認証が、内部の要素の実装spec と食い違う行の数。
7. 機能の切り方が妥当でない数（1 つの機能が複数の独立した振る舞いを含む、または 1 つの振る舞いが複数の機能に分かれている）。
8. くくり別のときのみ: くくりの切り方が妥当でない数（1 つのくくりが利用者から見て複数の独立した目的を含む、または 1 つの目的が複数のくくりに分かれている。くくりの名前が目的でなく実装の層だけを指している）。
9. 移行時のみ: 旧文書にあって新文書にも spec にもない決定事項の数。

## 8. 要件のみの spec

要件は確定しているが、設計・実装に着手していない将来の機能は、`specs/<名>/requirements.md` だけを置く。

- 状態は `--status` が「要件のみ」と導出する（進捗の語は書かない）。要件は、実装の有無に依存しない形で書く（SKILL.md の requirements.md の原則）。
- 設計に着手するとき、design.md と tasks.md を**両方**追加する（S003）。
- architecture.md の「実装spec」には載せない（S012）。spec 数の閾値（S010）にも数えない。

## 9. 設定（`.spec-driven.json`）

リポジトリ直下に置く任意のファイルである。調整できるのは数値だけで、語彙・図の記法・章立てなどの質的なルールは調整できない。範囲外の値や未知のキーはエラー（終了コード 2）になる。実効値は `npm run lint:spec -- --show-config` で確認する。雛形は `templates/spec-driven.json`（初期値と同じ）。

| ------------------------------- | ------ | ---------------------------------------------------------------------------------- |
| architecture.minSpecs           | 3      | 1〜50（設計済み spec がこの件数以上なら architecture.md が必須。無効化はできない） |
| architecture.maxLines           | 400    | 200〜800（docs/architecture.md の行数）                                            |
| architecture.maxFunctionLines   | 80     | 40〜150（機能 1 件の行数）                                                         |
| architecture.functionComponents | [2, 6] | 各 2〜10（最小 ≦ 最大）                                                            |
| architecture.groupMinComponents | 8      | 2〜50（内部の構成要素がこの個数以上ならくくり別にする。未満なら 1 ファイル）       |
| architecture.groupCount         | [3, 10] | 各 2〜30（全体の機能のくくりの数）                                                |
| architecture.groupComponents    | [2, 8] | 各 1〜20（くくりの文書の内部の要素の数）                                           |
| architecture.maxGroupLines      | 300    | 150〜600（くくりの文書の行数）                                                     |

## 10. 既存の architecture の移行

1. 旧文書の各決定事項を、spec にあるか・PoC の制約値にするか・削除するかに分類する。
2. spec にも PoC にもない決定事項で、現在も有効なものは、先に該当 spec に追記する（architecture は根拠のない決定を書けない）。
3. 経緯・却下案・日付・進捗・検証手順は削除する（履歴は git に残る）。
4. 将来の機能で要件が確定しているものは、要件のみの spec にする（8 節）。
5. **機能ごとに分割していた旧形式**（`docs/architecture/<機能>.md` が機能 1 件ずつ、全体の 5 章が索引）からは、次のように移す。
   - 構成要素を 6.2 の手順でくくりにまとめ、くくりごとに `docs/architecture/<くくり>.md` を作る。旧ファイルは削除する。
   - 旧い機能は、6.3 の表に従って、くくりの文書の機能・全体の機能・削除のどれかにする。要素の内部の挙動や、2 つの内部の要素だけの呼び出しは削除する（その挙動は spec の設計書にある）。
   - 旧い全体の 6〜9 章の行は、根拠の spec の所属で、全体かくくりの文書へ振り分ける（S022）。
6. 雛形から作り直し、`npm run lint:spec` を通し、目視確認の項目 9 まで実施する。

廃止したルール ID（欠番）: F-A15（内部の要素をいずれかの機能に載せる義務。薄い機能を生む原因だった）、F-A16（機能ごとの分割ファイルの体裁）。
