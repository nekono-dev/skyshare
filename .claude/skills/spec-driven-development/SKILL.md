# 仕様駆動開発（Spec-Driven Development）

機能の追加・修正を行う際は、`specs/<feature-name>/` 配下（プロジェクトの規約に応じて配置は読み替えてよい）に次の3ファイルを整備することを必須の前提とする。3ファイルは役割が明確に分離されており、互いの内容を混同してはならない。

| ファイル | 役割 | 更新頻度 |
|---|---|---|
| `requirements.md` | 何を実現すべきか（要件） | 仕様変更時のみ |
| `design.md` | それをどう実現するか（方針） | 設計変更時のみ |
| `tasks.md` | 具体的に何をするか（作業） | 作業のたびに（チェックボックス更新） |

3ファイルの関係は一方向の依存を持つ: `tasks.md` は `design.md` を達成するための作業計画であり、`design.md` は `requirements.md` を達成するための設計方針である。逆方向（実装や作業の都合で要件・設計を歪める）は避ける。

## requirements.md（要件定義）

**目的**: `design.md`・`tasks.md`を作るにあたっての思想的基礎となる、純粋な要件を定義する。

- 機能要件・非機能要件・受け入れ条件の形でまとめる。
- 「現状の実装がどうなっているか」に一切依存しない書き方をする。実装が存在しない新機能の要件定義と、既存機能の改修の要件定義は、文体・粒度が変わってはならない。
- 記述時点で判断できない事項（「今後の検討事項」「未決事項」「TODO」等）を残したまま完了としない。判断が必要な事項は、要件定義の作業中に意思決定者（人間）に確認し、結論を本文に反映してから確定させる。「検討中」を許容する場は要件定義そのものであり、成果物であるrequirements.mdに残す場所ではない。
- ファイルパス・関数名・クラス名など実装の詳細には立ち入らない（それは`design.md`の役割）。ただし、要件を検証する外部の受け入れ条件（既存のテストファイル等）への参照はあってよい。

## design.md（基本設計〜詳細設計）

**目的**: `requirements.md`が定める要件を達成するための、具体的な方針を示す。

- アーキテクチャ、データフロー、インターフェース、処理フロー、エラー処理方針など、要件を満たすための具体的な設計を記述する。
- **実装状況の整理表であってはならない**。「実装済み／未実装」列、進捗のまとめ表、「〜は今後実装する」といった記述は書かない。design.mdは方針が確定していることを前提にした文書であり、実装が追いついているかどうかは`tasks.md`が扱う。
- **タスクの実行状態を管理する書類であってはならない**。「次セッションで検討」「未決事項」のような先送りの記述を残さない。設計判断が必要な事項は、requirements.mdと同様にこの場で意思決定してから本文に書く。判断を実装時の裁量に委ねると決めたなら、「委ねる」という方針自体を明記し、先送りとして残さない。

## tasks.md（design.mdを達成するための作業内容）

**目的**: `design.md`が示す方針を実現するための、具体的な作業内容・作業方針をまとめる。

- チェックボックス（`- [ ]` / `- [x]`）形式で、作業単位ごとに列挙する。実装状況の追跡・進捗管理はここに一本化する。
- 新たな仕様判断・設計判断をここで行わない。作業中に仕様・設計上の疑問が生じた場合は、`requirements.md`・`design.md`に立ち返って意思決定し、そちらを更新してから作業を続ける。

## 適用ルール

- 機能追加・修正に着手する前に、対象機能の`specs/<feature-name>/`が存在するか確認する。存在しなければ、着手前にこの3ファイルを整備する。
- 既存の`requirements.md`・`design.md`に「今後の検討事項」「未決事項」「TODO」「実装状況」列のような進捗管理的な記述を見つけたら、これらの原則に従って解消する（意思決定が必要なものは確認し、実装状況の追跡は`tasks.md`へ移す）。
- 3ファイルのうちどれかだけを更新して済ませず、要件・設計・作業のどのレイヤーの変更かを判断してから、該当するファイルを更新する。
